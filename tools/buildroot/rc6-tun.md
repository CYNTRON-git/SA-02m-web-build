# СА-02м · модуль TUN для двух профилей rc6

Эти два архива позволяют отдельно проверить TUN/TAP и OpenVPN на контроллере с исправленными ядрами 1.0.8.3. Каждый архив содержит один файл `lib/modules/<release>/extra/tun.ko`. Загрузку выбирает исполнитель конкретного испытания. После загрузки Linux отмечает модуль как собранный вне дерева (taint O).

## Входные данные и сборка

На Linux или macOS нужны Python 3, Docker с поддержкой linux/amd64, сохранённый образ сборщика `sha256:9af56be350d47f08b71df02abac56118fdc3bfa886adc26c64eb612fb3d50e7a` и том с обоими подготовленными деревьями Buildroot. По умолчанию используется локальный том `cyntron-sa-bsp-work`. На другой сборочной машине восстановите его из BSP-снимка с каталогами `profiles/{smp,rt}/output/build/linux-custom` и `profiles/{smp,rt}/output/host`. Параметр `--volume ИМЯ` выбирает существующий том. Сборщик подключает его только для чтения.

Из корня проекта выполните команду с именем нового выходного каталога.

```bash
python3 tools/buildroot/rc6-tun.py build ./out-rc6-tun
```

Для каждого профиля проверяются SHA-256 штатного `drivers/net/tun.c`, `.config`, `Module.symvers`, сгенерированных заголовков, GCC 10.3.1, cc1, ассемблера и линкера. Kbuild собирает модуль отдельно, пользуясь заголовками и таблицей экспортов точного профиля. Макрос `CONFIG_TUN_MODULE` задаётся только при компиляции tun.c. После MODPOST проверяются имя, vermagic, зависимости, хеш модуля и хеш архива. Команда публикует каталог после проверки обоих файлов. Пины входят в [сборщик](rc6-tun.py), базовые проверки запускаются через `python3 scripts/dev/test-rc6-tun.py`. Изменение любого пина требует новой сборки, сверки и отдельного испытания.

## Передача на стенд

Скопируйте `rc6-tun.py` и архив выбранного профиля в отдельный каталог подготовки на СА. До распаковки и загрузки выполните на самом устройстве:

```bash
python3 rc6-tun.py verify-running "sa02m-tun-$(uname -r).tar.gz"
```

Код завершения 0 подтверждает SHA-256 архива, архитектуру ARMv7l, версию **работающего** ядра и GNU build ID из `/sys/kernel/notes`. Ядра с тем же uname встречаются с другими build ID. Команда только читает файлы. В согласованное окно HIL исполнитель может развернуть проверенный модуль, запустить обычный modprobe, проверить появление `/dev/net/tun`, установление VPN и снятие испытательной конфигурации. Принудительная загрузка или игнорирование ошибок MODPOST исключают проверку совместимости.

На точных SMP и RT zImage выполнена загрузка ARM в QEMU с сетями хоста отключёнными. Тест загрузил модуль обычным finit_module, открыл `/dev/net/tun`, создал интерфейс через TUNSETIFF, подтвердил флаги через TUNGETIFF и выгрузил модуль. Эти результаты подтверждают работу интерфейса TUN на двух бинарных ядрах. Физическую приёмку VPN на объекте фиксируют по отдельному протоколу.

Штатное дополнение WireGuard к этим архивам потребовало бы изменения базового ядра. В точной конфигурации rc6 включение WIREGUARD=m выбирает DST_CACHE=y; эта опция меняет структуру ip_tunnel_info. В таблицах экспортов обоих работающих профилей отсутствуют dst_cache_*; CONFIG_MODVERSIONS отключена. Для kernel WireGuard требуется согласованная сборка ядра и модулей. Проверку userspace WireGuard поверх TUN оформляют отдельно.
