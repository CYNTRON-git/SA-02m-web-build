# Модель угроз: веб-интерфейс SA-02m

Кто атакует продукт и что может забрать — стоящая модель, на которую ссылается план
любой security-relevant фичи (AI-Dev threat-discovery). Заведена 2026-07-14 из брифа
(`docs/product.md`) + дерева + диалога с Оператором. Расширена 2026-07-17: облачный
удалённый доступ (cloud-enrollment, frpc reverse-туннель), появившийся с 1.0.5.5+ —
акторы §1 (A5), границы §3 (облачный путь), злоупотребления §4 (A5-строки),
под-заключение §5, вопросы §6, дома правил §7. Cloud-части выведены из дерева и ждут
подтверждения Оператором. Расширена 2026-07-29 (1.0.5.52/54): три строки §4 —
merge-запись сетевых конфигов из панели, закреплённая rm-способность, root-юнит
канонизации имён интерфейсов. Машинно-грамматические имена (файлы, порты, юниты) —
латиницей; пояснения — по `docLanguage: ru`.

Дом технических «floor»-правил — `docs/agent-rules/web-code-rigor.md` (эта модель их
цитирует, а не дублирует). Дом истории регрессий — `CHANGELOG.md`.

## Контекст (из брифа)

Пользователь — наладчики/интеграторы. Развёртывание (подтверждено Оператором) —
**спектр**: заводская LAN общего доступа · удалённо через VPN/интернет · изолированная
сеть объекта. Устройство несёт root-способные CGI, прошивальщик RS-485-модулей и мост
в техпроцесс — то есть цена компрометации высокая, а контур доступа шире «доверенной LAN».

## §1 Акторы (кто атакует) — подтверждены Оператором

| # | Актор | Мотивация / возможности |
|---|---|---|
| A1 | **Сканер из интернета/VPN** | Оппортунист: автоскан открытых устройств, дефолтные пароли, известные CVE. Актуален там, где устройство доступно снаружи. |
| A2 | **Недоверенный узел в LAN** | Скомпрометированный ПК/устройство в общей заводской сети → боковое движение к SA-02m (весь LAN-ввод трактуется как attacker-controlled — `web-code-rigor.md`). |
| A3 | **Инсайдер / персонал** | Доступ к сети объекта; случайная или умышленная порча конфигурации/техпроцесса. |
| A4 | **Конкурент / целевая атака** | Целенаправленно: нарушить техпроцесс, украсть настройки/прошивки, саботаж. |
| A5 | **Скомпрометированное/враждебное облако или MITM на исходящем туннеле** | Появляется ТОЛЬКО при cloud-enrollment (`opt/sa02m-cloud-agent/`): устройство дозванивается в `cloud.cyntron.ru` и держит frpc reverse-туннель. Тот, кто владеет облаком/frps-сервером (или встал в разрыв туннеля), достаёт КАЖДОЕ enrolled-устройство через его же веб-UI. Актуален только когда backend существует и устройство сопряжено. |

> A5 добавлен 2026-07-17 из дерева (cloud-scaffold), НЕ подтверждён Оператором `[?]`.
> Позиционирование против A1–A4: A5 — это не «снаружи через открытый порт» (A1), а
> «изнутри через доверенный по построению облачный канал», который сам продукт
> открывает; ставки те же (S1/S2/S4), но обход организационной компенсации «только
> VPN, без входящих» встроен в фичу (см. §5).

## §2 Активы (что защищаем) — подтверждены Оператором

| # | Актив | Почему ценен |
|---|---|---|
| S1 | **Контроль над техпроцессом** | Через RS-485-шлюз / MQTT-мост / флашер злоумышленник влияет на управляемое оборудование — **физические последствия**. Наивысшая ставка. |
| S2 | **Захват устройства (root)** | root-способные CGI (`services_ctrl`, `kernel_ctrl`, `web_update`, `apply`, `hw_set`, `cpu_profile`) + sudo → полный контроль над узлом и плацдарм в сеть. С 1.0.5.64 добавлена **командная строка** (`cmd_exec.cgi`): произвольные команды от `www-data` за сессией, root-режим за паролем root (`/etc/shadow`-проверка в `sa02m-web-root-cmd.sh`) — это ЯВНЫЙ обход внутренней границы «sudo с пиновкой команд» (§3), осознанная функция для наладчика. |
| S3 | **Подмена прошивки модулей MR-02m** | Флашер заливает `.fw` в модули; враждебная/битая прошивка → кирпич или саботаж на уровне полевого модуля. |
| S4 | **Утечка настроек/доступа** | Учётные данные (`/etc/sa02m_web.env`), конфиг сети, MQTT-топики/пароли — разведка и доступ к смежным системам. |

> **Cloud-расширение активов (2026-07-17, из дерева):**
> - **S2 (root)** — облако НЕ имеет прямого канала команд к устройству (агент
>   `send-only`: из ответа на heartbeat агент использует ТОЛЬКО причину отказа —
>   статус и `error` НЕ-200 ответа; тело `200` разбирается как JSON внутри
>   `api_post` (общий код с claim/enroll), но разобранное значение не достигает
>   никакой логики агента — точка вызова его отбрасывает; прежний root-канал
>   `handle_command` удалён в Phase B — юнит-тесты `opt/sa02m-cloud-agent/tests/`
>   это фиксируют). Но облако проксирует наружу собственный веб-UI устройства (:9999
>   настройки, :80 SCADA), за которым — та же единая парольная сессия и те же root-CGI.
>   То есть S2 достижим ЧЕРЕЗ облако — но через сам UI (§4 A1→S2), не через агент.
> - **S4 (идентичность устройства)** — добавляется новый чувствительный актив:
>   claim-код / enroll-токен (`/etc/sa02m-cloud/activation_token`, 0600) и frp
>   `auth.token` в `frpc.toml` (0600, из enrollment-ответа). Аппаратного корня доверия
>   нет (на A40i нет secure element) — идентичность целиком программная.

## §3 Границы доверия (из дерева)

```
[A1 интернет/VPN] [A2/A3/A4 LAN] ──► nginx :9999 (HTTP, без TLS) ──► fcgiwrap ──► Bash CGI
                                                   │                        │
                                     cookie session_token             sudo -n (pinned)
                                     (1 общая учётка,                  → systemctl / i2c /
                                      /etc/sa02m_web.env)                 kernel-select / …
                                                   │
                        ┌──────────────────────────┼───────────────────────────┐
                   flasher daemon              MQTT broker                RS-485 порты
                   (unix-socket,               1883 local /               (port-lease между
                    группа www-data)           1884 external+auth)         MPLC4/MQTT/флашером)
```

- **Главная граница** — сетевой край до `nginx :9999`. Транспорт — **HTTP без TLS**; за ним
  единая аутентификация (cookie `session_token`, серверное хранилище сессий) охраняет всё
  остальное, включая root-CGI и флашер.
- Внутренние границы: sudo с **аргументной** пиновкой (`etc/sudoers.d/sa02m-www` —
  только пиннованные хелперы и фиксированные векторы; **до 1.0.6.10 строка давала
  raw `tee`/`ifup`/`ifdown`/`kill`/`i2cset` → веб-сессия могла стать root без пароля
  root, закрыто B1** — см. строку A1/A2/A5→S2 и `sudoers-pin-contract`); port-lease
  RS-485 (`sa02m-domain.md`); MQTT 1883 локально без auth / 1884 наружу с auth.

### Облачный путь — исходящий туннель (добавлен 2026-07-17, из дерева)

```
[SA-02m]                                            [интернет / оператор ЦИНТРОН]
  agent (send-only) ── HTTPS /api/v1 ──►  cloud.cyntron.ru  (claim/enroll/heartbeat)
  frpc ── исходящий, порт задаёт облако ─►  frps @ cloud  ◄── публичный TLS ── клиент
        туннель несёт localPort :9999 (настройки, nginx HTTP) и :80 (SCADA-web),
        localIP 127.0.0.1, type http — набор проксей приходит из enrollment-ответа
```

- **Инверсия границы.** До cloud-enrollment граница — только входящая (§3 выше:
  снаружи → `nginx :9999`). Cloud переворачивает её: устройство ДОЗВАНИВАЕТСЯ наружу,
  входящего порта и публичного IP нет — НО reverse-туннель делает :9999/:80
  достижимыми со стороны облака. Это **inbound-эквивалент через облако**: сильнейшая
  организационная компенсация «только VPN, без прямой экспозиции» (§5) превращается в
  продуктовую функцию, которая сама открывает путь снаружи.
- **Облако видит UI-трафик.** frpc-прокси `type http` на `localPort 9999` — это nginx
  БЕЗ TLS (§3). Публичный TLS терминируется облаком → облако видит session_token и
  пароль в открытом виде на своей стороне.
- **Набор портов предлагает облако, но устройство его фильтрует.** Enrollment-ответ
  рендерится в `frpc.toml`, однако device-side allow-list локальных портов ЕСТЬ:
  `ALLOWED_LOCAL_PORTS = frozenset({80, 9999})` (`opt/sa02m-cloud-agent/sa02m-cloud-agent.py`),
  и `render_frpc_toml` отбрасывает любой другой прокси (fail-closed: пустой набор
  прокси, а не открытый порт). Так что `:22` или `:1883` облако протуннелировать не
  может. Остаточный риск — сами `:80`/`:9999`, то есть тот же веб-UI (см. пункт выше).
- **Канала команд нет.** Агент только шлёт heartbeat. Из ответа агент использует
  ТОЛЬКО причину отказа: HTTP-статус и поле `error` НЕ-200 ответа. Тело `200`
  разбирается как JSON внутри `api_post` (парсер общий с claim/enroll —
  поверхность парсера на ответе `200` есть), но разобранное значение не достигает
  никакой логики агента: точка вызова heartbeat результат `api_post` не
  захватывает, а `_note_heartbeat` на `200` принудительно ставит `error = None`;
  `200` с неразбираемым телом записывается как статус `0` — не успех и не отказ
  (`active_loop`, юнит-тесты `test_agent.py::test_heartbeat_response_not_interpreted`,
  `test_revoke_standdown.py::test_success_body_is_never_read_by_the_refusal_channel`,
  `::test_unparseable_200_is_neither_success_nor_refusal`).
  Прежний root-канал `handle_command` (обозначался F1 в плане облачного доступа)
  удалён в Phase B вместе с WireGuard. Root достижим только через сам веб-UI, не
  через агент.
- **Новая поверхность (1.0.6.26): отказ, названный облаком, стирает облачную
  привязку платы.** Три подряд отказа одного вида (heartbeat `403` с известным
  `error`, либо строка отказа frps в журнале frpc) переводят агент в stand-down:
  туннель остановлен, `device_secret`/`frpc.toml`/`device_id` стёрты, `enrolled =
  false`. Это единственное действие, которое облако может вызвать на плате, и оно
  ограничено ТОЛЬКО облачной привязкой — конфигурация устройства, MQTT, сеть,
  MPLC4/CODESYS, RS-485 и учётные записи не затрагиваются (тесты
  `test_revoke_standdown.py::test_stand_down_keeps_configuration_not_identity`);
  восстановление — кнопка «Привязать заново», без SSH. Актор A5 мог бы вызвать
  его подделкой ответа облака — этот путь закрыт TLS-проверкой `urllib`
  (сертификат сервера, системные корни) на `api_url`; журнал frpc пишет сам frpc
  по ответу frps через аутентифицированный (`auth.token`) транспорт. Легитимно
  скомпрометированное облако (владелец A5) привязку стереть МОЖЕТ — и не может
  ничего сверх неё. Остаточный риск учтён: `[частично]`, наследует §5.

## §4 Злоупотребления (abuse cases) и текущие меры

| Актор→Актив | Сценарий | Текущая мера (дата аудита — когда меру ЧИТАЛИ; «держится» без теста её не доказывает — см. `A2→S1`) |
|---|---|---|
| A1→S2 | Дефолтный/слабый/утёкший единый пароль снаружи → вход → root-CGI | Сессионная модель (sha256-токен, серверное хранилище); **но** пароль один и общий, TLS нет — `[частично]` |
| A2→S2 | Инъекция из QUERY_STRING/POST/cookie в shell-слово/путь/unit | Allow-list валидация до shell; auth-before-mutation на мутирующих CGI — **держится** (аудит) |
| A2→S1 | Гонка/повтор действия шлюза/флашера, мид-поллинг | Кнопки disable на pending; port-lease (flock + stop/restore служб) — **держится**. `flasher_busy` — **держится с 2026-08-06**, до этого был МЁРТВ с 2026-07-12: проба в `sa02m-web-service-ctl.sh` слала выведенный из обращения статический токен, демон отвечал 401, а `curl` без `-f` выходит с кодом 0 — гейт всегда сообщал «не занято». Строка «проверено аудитом 2026-07-14» в заголовке таблицы этот факт НЕ поймала (аудит проверил наличие кода, не его действие). Сейчас: проба читает `poll_locked` с неавторизованного `/health` (`docs/contracts/flasher-health.md`), при нечитаемом ответе — fail closed, регрессия закрыта тестами `port-lease-gate` + `no-retired-session-token` |
| A4→S3 | Заливка враждебной прошивки через флашер | За единой auth; формат `.fw` валидируется в MR-02m-репозитории `[?]` цепочка доверия прошивки |
| A1/A4→S4 | Кража `sa02m_web.env`/конфигов | Файлы 640/сессии в setgid-каталоге; **но** нет TLS → перехват в недоверенной сети `[частично]` |
| A3→S1 | Инсайдер меняет конфиг/останавливает службы | Нет per-user учёток и **нет журнала доступа** — не атрибутируется `[не покрыто]` |
| A2→S1/S2 | Инъекция в сетевой конфиг через «Сеть»: с 1.0.5.52 `apply.cgi` не перегенерирует `interfaces.d/*.conf`, а СЛИВАЕТ (root-запись через `sudo tee`), перенося «чужие» строки существующего root-конфига дословно — вредоносная строка попала бы в исполняемый ifupdown-контекст | Управляемые значения — только через allow-list (`valid_ipv4*`) до записи; переносимые строки происходят ИЗ root-владельческого файла (не из запроса), ограничены 64 строк/8 КБ/512 Б, CR/control-символы отбрасываются; бэкап `.sa02m-bak` перед каждой записью — **держится** (ревью 1.0.5.52 + функциональная обвязка `iface-conf-merge`) |
| A2→S1 | Злоупотребление новой rm-способностью панели (удаление произвольного файла от root) | С 1.0.5.54 у `www-data` нет raw `rm`: sudoers выдаёт ровно `sa02m-conf-rm.sh` — `case`-allow-list из 4 имён LAN-конфигов, отказ по symlink, бэкап перед удалением — **держится** (контракт §5.4) |
| A2/A3→S1 | Подмена имени интерфейса/гонка именования на загрузке (root-юнит `sa02m-iface-canonical` переименовывает `end0/1`→`eth0/1` до networking) | Жёсткий 4-имённый allow-list в скрипте (никаких glob по `/sys`), конвергентный только legacy→канон, `Before=` — лишь порядок (упавший юнит не блокирует сеть); вход из сети/запроса в юнит не существует — **держится** (контракт `ethernet-iface-naming.md`) |
| A5→S2 | Скомпрометированное облако проксирует веб-UI устройства (:9999) наружу → единая парольная сессия → root-CGI | Канал команд отсутствует (агент send-only — держится, тесты); НО за туннелем — та же модель, что для A1→S2 (единый пароль, HTTP), и облако видит креды в открытом виде → `[частично]` |
| A5→S1 | Тот же UI-туннель → вкладки шлюза/флашера/MQTT → контроль техпроцесса | Меры те же, что для LAN-доступа к UI (auth-before-mutation, port-lease держатся); но дверь теперь открыта из облака `[частично]` |
| A5→S1/S2/S4 | Враждебное облако запрашивает туннель на «лишний» локальный порт (:1883 mosquitto без локальной auth, флашер-сокет и т. п.) | Прокси `type http`/`localIP 127.0.0.1` (ограничение frps authz) ПЛЮС device-side allow-list локальных портов `ALLOWED_LOCAL_PORTS = {80, 9999}` (`opt/sa02m-cloud-agent/sa02m-cloud-agent.py`), fail-closed в `render_frpc_toml` — «лишний» порт отбрасывается, **держится**. Остаётся экспозиция самих :80/:9999 — тот же веб-UI (строка A5→S2 выше) `[частично]` |
| A5→S4 | MITM на пути frpc→frps / краже транзитного трафика | API `claim/enroll/heartbeat` — HTTPS (urllib TLS-verify); туннель аутентифицируется shared `auth.token`; TLS-шифрование транспорта туннеля задаётся на frps — **вне репозитория** `[?]`; облако в любом случае видит UI-креды (см. §3) `[частично]` |

## §5 Заключение — сильнейшая НЕЗАКРЫТАЯ угроза (честно)

> «Это сейчас открыто» — юридический вердикт; модель, не способная его вынести, — театр.

**Устройство спроектировано под доверенную LAN, но по подтверждению Оператора
разворачивается с доступом через интернет/VPN и в общих заводских сетях. При этом:
транспорт — HTTP без TLS, аутентификация — единый общий пароль, нет per-user учёток,
нет журнала доступа, а за этой единственной дверью — root-способные CGI, прошивальщик,
мост в техпроцесс и (с 1.0.5.64) командная строка с произвольным shell от `www-data`
и root-режимом за паролем root, который по HTTP уходит открытым текстом.**

Значит: **экземпляр, доступный из интернета/VPN (или из недоверенной заводской LAN) с
дефолтным/слабым/утёкшим паролем → A1/A4 → S2 (root-захват) → S1 (контроль техпроцесса) и
S3 (подмена прошивки).** Это НЕ гипотеза — это текущая экспозиция везде, где развёртывание
не компенсирует модель внешними средствами. Меры, которые ДЕРЖАТСЯ (allow-list ввода,
auth-before-mutation, **валидация argv внутри привилегированных хелперов — с 1.0.6.24, после
того как аудит 2026-08-28 нашёл два обхода пиновки (H1/H2); пиновка пути появилась в 1.0.6.10,
когда B1 нашёл, что прежняя строка давала root без пароля через raw `tee`. Каждый раз проверка
отставала от реальности: ранний аудит смотрел НАЛИЧИЕ строки, а не её действие; гейт 1.0.6.10
смотрел один файл прав из шести. Сейчас проверка читает все шесть и требует, чтобы исправление
доезжало до платы по всем трём путям доставки**), закрывают инъекции, эскалацию через sudo и неавторизованную телеметрию,
но **не** закрывают связку «нет TLS + единый пароль + внешняя экспозиция + root/флашер за
одной дверью».

### Компенсации, на которые продукт сейчас опирается (organizational, не в коде)

- Развёртывание **только за VPN**, без прямой интернет-экспозиции.
- **Смена дефолтного пароля** при пусконаладке (наладчик — актор доверенный).
- Сегментация: устройство в изолированной техносети.

Эти компенсации — **вне продукта** и не гарантированы кодом. Продуктовые кандидаты,
закрывающие разрыв (для отдельного решения Оператора, НЕ выполнены здесь): TLS «из
коробки» (self-signed/ACME), обязательная смена дефолт-пароля при первом входе, per-user
учётки + журнал доступа (закрывает A3-атрибуцию), явная политика «только VPN» в
`docs/deployment.md`.

### Под-заключение: облачный удалённый доступ (A5) — сейчас ЛАТЕНТНО, потом доминирует

**Латентно сегодня.** Backend (`cloud.cyntron.ru/api/v1` + frps-сервер) и контракт
enrollment живут в ОТДЕЛЬНОМ репозитории и, судя по дереву, ещё не работают: агент
стартует в `standby` (`enrolled=false`), а по заметке инсталлятора (`scripts/05-cloud-agent.sh`)
туннель и heartbeat на стенде поднимались ВРУЧНУЮ. Пока backend не отвечает — вся
облачная поверхность инертна. Это НЕ значит «безопасно», это значит «взведено».

**Доминирует, как только активно.** Cloud-enrollment — это не просто ещё одна дверь: он
**инвертирует модель угроз**. §5 держался на организационной компенсации «только VPN,
без прямой экспозиции»; cloud превращает её в продуктовую функцию, которая сама делает
:9999/:80 достижимыми из интернета через reverse-туннель. Значит связка §5 (HTTP без
TLS + единый пароль + root-CGI/флашер за одной дверью) становится достижимой **через
облако**, а не только из LAN/VPN — и сразу для ВСЕХ enrolled-устройств, если облако
скомпрометировано.

**Честно про острейший край.** Он НЕ в root-канале команд — этот канал (прежний F1)
**удалён в коде** (агент `send-only`, `handle_command` вырезан, юнит-тесты стерегут его
невозвращение). Острейший край теперь — **облако как единый trust anchor, фронтящий
собственный HTTP + единый-пароль веб-UI устройства из интернета**, плюс два не-закрытых
кодом момент: облако видит UI-креды в открытом виде (публичный TLS терминируется на
облаке, за туннелем nginx HTTP). Набор туннелируемых портов облако НЕ диктует свободно —
device-side allow-list `{80, 9999}` держится (A5→S1/S2/S4). Продуктовые кандидаты (решение
Оператора, НЕ выполнены здесь): TLS на
самом UI (тогда облако не видит креды); привязка идентичности к чему-то прочнее
программного токена; явные требования к харденингу/владению backend в контракте.

- Цепочка доверия прошивки MR-02m: подписывается/валидируется ли `.fw` криптографически,
  или только формат? (владелец — репозиторий MR-02m).
- Встречаются ли у заказчиков требования ИБ (TLS/per-user/аудит) как контрактные?
- Есть ли развёртывания с ПРЯМОЙ интернет-экспозицией (без VPN) — тогда §5 уже «открыто».

Облачные (A5, из дерева 2026-07-17):

- Кто владеет и харденит cloud backend (activation API + frps-сервер)? Контракт
  enrollment (`docs/contracts/cloud-enrollment.md`) живёт в облачном репозитории — его
  безопасность здесь не проверяется.
- Модель аутентификации канала: шифруется ли транспорт туннеля frpc→frps (TLS), или
  защищён только shared `auth.token`? (Задаётся на стороне frps.)
- Должен ли device-side allow-list локальных портов быть шире `{80, 9999}` (например,
  под будущие роли туннеля) и кто это решает — Оператор или enrollment-контракт?
  Сам allow-list уже энфорсится устройством.
- Жизненный цикл идентичности без аппаратного корня доверия (нет secure element на
  A40i): ротация/отзыв frp-токена и device-id, поведение при factory reset.
- Доверие к frps-серверу и владельцу домена `cloud.cyntron.ru` (единая точка ко всем
  enrolled-устройствам).
