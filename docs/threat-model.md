# Модель угроз: веб-интерфейс SA-02m

Кто атакует продукт и что может забрать — стоящая модель, на которую ссылается план
любой security-relevant фичи (AI-Dev threat-discovery). Заведена 2026-07-14 из брифа
(`docs/product.md`) + дерева + диалога с Оператором. Расширена 2026-07-17: облачный
удалённый доступ (cloud-enrollment, frpc reverse-туннель), появившийся с 1.0.5.5+ —
акторы §1 (A5), границы §3 (облачный путь), злоупотребления §4 (A5-строки),
под-заключение §5, вопросы §6, дома правил §7. Cloud-части выведены из дерева и ждут
подтверждения Оператором. Расширена 2026-07-29 (1.0.5.52/54): три строки §4 —
merge-запись сетевых конфигов из панели, закреплённая rm-способность, root-юнит
канонизации имён интерфейсов. Расширена 2026-09-27: мост Apple HomeKit — актор A7
(§1), второй входящий LAN-слушатель (§3 «Мост HomeKit»), строки §4 с A7 и сопряжением.
Расширена 2026-09-28: клиент BSH Home Connect — актор A8 (§1), исходящий канал в
облако BSH (§3 «Клиент Home Connect»), строки §4 с A8, токеном и клоном; в тот
же день оба демона выведены из группы `www-data` (§3, аудит стендовой сессии).
Машинно-грамматические имена (файлы, порты, юниты) — латиницей; пояснения — по
`docLanguage: ru`.

Дом технических «floor»-правил — `docs/agent-rules/web-code-rigor.md` (эта модель их

## Контекст (из брифа)

Пользователь — наладчики/интеграторы. Развёртывание (подтверждено Оператором) —
**спектр**: заводская LAN общего доступа · удалённо через VPN/интернет · изолированная
сеть объекта. Устройство несёт root-способные CGI, прошивальщик RS-485-модулей и мост
в техпроцесс — то есть цена компрометации высокая, а контур доступа шире «доверенной LAN».

## §1 Акторы (кто атакует) — подтверждены Оператором

| # | Актор | Мотивация / возможности |
|---|---|---|
| A1 | **Сканер из интернета/VPN** | Оппортунист: автоскан открытых устройств, дефолтные пароли, известные CVE. Актуален там, где устройство доступно снаружи. |
| A2 | **Недоверенный узел в LAN** | Скомпрометированный ПК/устройство в общей заводской сети → боковое движение к SA-02m (весь LAN-ввод трактуется как attacker-controlled — `web-code-rigor.md`). |
| A3 | **Инсайдер / персонал** | Доступ к сети объекта; случайная или умышленная порча конфигурации/техпроцесса. |
| A4 | **Конкурент / целевая атака** | Целенаправленно: нарушить техпроцесс, украсть настройки/прошивки, саботаж. |
| A5 | **Скомпрометированное/враждебное облако или MITM на исходящем туннеле** | Появляется ТОЛЬКО при cloud-enrollment (`opt/sa02m-cloud-agent/`): устройство дозванивается в `cloud.cyntron.ru` и держит frpc reverse-туннель. Тот, кто владеет облаком/frps-сервером (или встал в разрыв туннеля), достаёт КАЖДОЕ enrolled-устройство через его же веб-UI. Актуален только когда backend существует и устройство сопряжено. |

| A6 | **Скомпрометированный/враждебный шлюз умного дома** | Появляется ТОЛЬКО при привязке к Алисе (`opt/sa02m-alice`, профиль `yandex`): плата дозванивается в `alice.cyntron.ru` и держит Socket.IO-сессию поверх mTLS. Владелец шлюза — вторая сторона, выдавшая плате идентичность (клиентский сертификат), и с 1.0.6.32 может событием `controller_unlink` заставить плату стереть ЭТУ привязку. Не путать с A5: другое облако, другая идентичность, другой канал; пересечения по возможностям нет — ни один из двух не может стереть привязку другого. |
| A8 | **Облако BSH Home Connect (или MITM на нём)** | Появляется ТОЛЬКО при установленном и включённом клиенте `sa02m-homeconnect` (`install.sh --with-homeconnect`, по умолчанию выключен, в заводской образ не входит). Сторона, которой плата верит в **состоянии бытовых приборов** (что посудомойка «закончила», что дверь духовки «открыта»), и держатель аккаунта, который представляет refresh-токен. Входящего канала нет: плата сама ходит по HTTPS к `api.home-connect.com`; клиент только читает — команд прибору нет (решение Q-E). |
| A7 | **Участник HomeKit** | Появляется ТОЛЬКО при включённом мосте Apple HomeKit (`opt/sa02m-homekit`, необязательная установка, по умолчанию выключен). (а) Любой узел LAN, видящий mDNS-объявление `_hap._tcp` и достающий порт моста (по умолчанию 21064) на выбранном интерфейсе; (б) сопряжённый контроллер — iPhone/iPad семьи — и через домашний центр Apple (Apple TV / HomePod) iCloud-аккаунт семьи **из интернета**: новый удалённый путь к S1, который не проходит ни через пароль панели, ни через наше облако. |
| A9 | **Держатель API-токена / скомпрометированный ИИ-агент** | Появляется ТОЛЬКО при включённой службе `sa02m-agent-api` (ставится установщиком, по умолчанию выключена) и выпущенном токене. Процесс на компьютере оператора (Cursor, Claude Desktop, скрипт), которому оператор сам выдал `X-SA02M-Token`. Видит и делает ровно то, что разрешают scope'ы токена (`read` / `control` / `config` / `admin`). Флаг `root_capable` — отдельное согласие: без него `admin` — это оболочка `www-data`, не root. Токен не выпускает токены. Через облачный туннель токен виден облаку так же, как сейчас пароль панели (§3, §5). |

## §2 Активы (что защищаем) — подтверждены Оператором

| # | Актив | Почему ценен |
|---|---|---|
| S1 | **Контроль над техпроцессом** | Через RS-485-шлюз / MQTT-мост / флашер злоумышленник влияет на управляемое оборудование — **физические последствия**. Наивысшая ставка. |
| S2 | **Захват устройства (root)** | root-способные CGI (`services_ctrl`, `kernel_ctrl`, `web_update`, `apply`, `hw_set`, `cpu_profile`) + sudo → полный контроль над узлом и плацдарм в сеть. С 1.0.5.64 добавлена **командная строка** (`cmd_exec.cgi`): произвольные команды от `www-data` за сессией, root-режим за паролем root (`/etc/shadow`-проверка в `sa02m-web-root-cmd.sh`) — это ЯВНЫЙ обход внутренней границы «sudo с пиновкой команд» (§3), осознанная функция для наладчика. |
| S3 | **Подмена прошивки модулей MR-02m** | Флашер заливает `.fw` в модули; враждебная/битая прошивка → кирпич или саботаж на уровне полевого модуля. |
| S4 | **Утечка настроек/доступа** | Учётные данные (`/etc/sa02m_web.env`), конфиг сети, MQTT-топики/пароли — разведка и доступ к смежным системам. |

> **Cloud-расширение активов (2026-07-17, из дерева):**
> - **S2 (root)** — облако НЕ имеет прямого канала команд к устройству (агент
>   `send-only`: из ответа на heartbeat агент использует ТОЛЬКО причину отказа —
>   статус и `error` НЕ-200 ответа; тело `200` разбирается как JSON внутри
>   `api_post` (общий код с claim/enroll), но разобранное значение не достигает
>   никакой логики агента — точка вызова его отбрасывает; прежний root-канал
>   `handle_command` удалён в Phase B — юнит-тесты `opt/sa02m-cloud-agent/tests/`
>   это фиксируют). Но облако проксирует наружу собственный веб-UI устройства (:9999
>   настройки, :80 SCADA), за которым — та же единая парольная сессия и те же root-CGI.
>   То есть S2 достижим ЧЕРЕЗ облако — но через сам UI (§4 A1→S2), не через агент.
> - **S4 (идентичность устройства)** — добавляется новый чувствительный актив:
>   claim-код / enroll-токен (`/etc/sa02m-cloud/activation_token`, 0600) и frp
>   `auth.token` в `frpc.toml` (0600, из enrollment-ответа). Аппаратного корня доверия
>   нет (на A40i нет secure element) — идентичность целиком программная.

## §3 Границы доверия (из дерева)

```
[A1 интернет/VPN] [A2/A3/A4 LAN] ──► nginx :9999 (HTTP, без TLS) ──► fcgiwrap ──► Bash CGI
                                                   │                        │
                                     cookie session_token             sudo -n (pinned)
                                     (1 общая учётка,                  → systemctl / i2c /
                                      /etc/sa02m_web.env)                 kernel-select / …
                                                   │
                        ┌──────────────────────────┼───────────────────────────┐
                   flasher daemon              MQTT broker                RS-485 порты
                   (unix-socket,               1883 local /               (port-lease между
                    группа www-data)           1884 external+auth)         MPLC4/MQTT/флашером)
                                                       │
                                            мост Modbus→MQTT (root) ─► Modbus TCP клиент
                                            (исходящий в LAN, с 1.0.6.56; только template/carel)
                   + проверка связи из окна панели: CGI (www-data) ─► Modbus TCP, один FC03 (1.0.6.67)
```

- **Главная граница** — сетевой край до `nginx :9999`. Транспорт — **HTTP без TLS**; за ним
  единая аутентификация (cookie `session_token`, серверное хранилище сессий) охраняет всё
  остальное, включая root-CGI и флашер.
- Внутренние границы: sudo с **аргументной** пиновкой (`etc/sudoers.d/sa02m-www` —
  только пиннованные хелперы и фиксированные векторы; **до 1.0.6.10 строка давала
  raw `tee`/`ifup`/`ifdown`/`kill`/`i2cset` → веб-сессия могла стать root без пароля
  root, закрыто B1** — см. строку A1/A2/A5→S2 и `sudoers-pin-contract`); port-lease
  RS-485 (`sa02m-domain.md`); MQTT 1883 локально без auth / 1884 наружу с auth.

### Облачный путь — исходящий туннель (добавлен 2026-07-17, из дерева)

```
[SA-02m]                                            [интернет / оператор ЦИНТРОН]
  agent (send-only) ── HTTPS /api/v1 ──►  cloud.cyntron.ru  (claim/enroll/heartbeat)
  frpc ── исходящий, порт задаёт облако ─►  frps @ cloud  ◄── публичный TLS ── клиент
        туннель несёт localPort :9999 (настройки, nginx HTTP) и :80 (SCADA-web),
        localIP 127.0.0.1, type http — набор проксей приходит из enrollment-ответа
```

- **Инверсия границы.** До cloud-enrollment граница — только входящая (§3 выше:
  снаружи → `nginx :9999`). Cloud переворачивает её: устройство ДОЗВАНИВАЕТСЯ наружу,
  входящего порта и публичного IP нет — НО reverse-туннель делает :9999/:80
  достижимыми со стороны облака. Это **inbound-эквивалент через облако**: сильнейшая
  организационная компенсация «только VPN, без прямой экспозиции» (§5) превращается в
  продуктовую функцию, которая сама открывает путь снаружи.
- **Облако видит UI-трафик.** frpc-прокси `type http` на `localPort 9999` — это nginx
  БЕЗ TLS (§3). Публичный TLS терминируется облаком → облако видит session_token и
  пароль в открытом виде на своей стороне.
- **Набор портов предлагает облако, но устройство его фильтрует.** Enrollment-ответ
  рендерится в `frpc.toml`, однако device-side allow-list локальных портов ЕСТЬ:
  `ALLOWED_LOCAL_PORTS = frozenset({80, 9999})` (`opt/sa02m-cloud-agent/sa02m-cloud-agent.py`),
  и `render_frpc_toml` отбрасывает любой другой прокси (fail-closed: пустой набор
  прокси, а не открытый порт). Так что `:22` или `:1883` облако протуннелировать не
  может. Остаточный риск — сами `:80`/`:9999`, то есть тот же веб-UI (см. пункт выше).
- **Канала команд нет.** Агент только шлёт heartbeat. Из ответа агент использует
  ТОЛЬКО причину отказа: HTTP-статус и поле `error` НЕ-200 ответа. Тело `200`
  разбирается как JSON внутри `api_post` (парсер общий с claim/enroll —
  поверхность парсера на ответе `200` есть), но разобранное значение не достигает
  никакой логики агента: точка вызова heartbeat результат `api_post` не
  захватывает, а `_note_heartbeat` на `200` принудительно ставит `error = None`;
  `200` с неразбираемым телом записывается как статус `0` — не успех и не отказ
  (`active_loop`, юнит-тесты `test_agent.py::test_heartbeat_response_not_interpreted`,
  `test_revoke_standdown.py::test_success_body_is_never_read_by_the_refusal_channel`,
  `::test_unparseable_200_is_neither_success_nor_refusal`).
  Прежний root-канал `handle_command` (обозначался F1 в плане облачного доступа)
  удалён в Phase B вместе с WireGuard. Root достижим только через сам веб-UI, не
  через агент.
- **Новая поверхность (1.0.6.26): отказ, названный облаком, стирает облачную
  привязку платы.** Три подряд отказа одного вида (heartbeat `403` с известным
  `error`, либо строка отказа frps в журнале frpc) переводят агент в stand-down:
  туннель остановлен, `device_secret`/`frpc.toml`/`device_id` стёрты, `enrolled =
  false`. Это единственное действие, которое ФЛОТОВОЕ облако может вызвать на
  плате (до 1.0.6.32 — единственное вообще; вторую такую поверхность добавил
  шлюз Алисы, см. ниже), и оно ограничено ТОЛЬКО облачной привязкой — конфигурация устройства, MQTT, сеть,
  MPLC4/CODESYS, RS-485 и учётные записи не затрагиваются (тесты
  `test_revoke_standdown.py::test_stand_down_keeps_configuration_not_identity`);
  восстановление — кнопка «Привязать заново», без SSH. Актор A5 мог бы вызвать
  его подделкой ответа облака — этот путь закрыт TLS-проверкой `urllib`
  (сертификат сервера, системные корни) на `api_url`; журнал frpc пишет сам frpc
  по ответу frps через аутентифицированный (`auth.token`) транспорт. Легитимно
  скомпрометированное облако (владелец A5) привязку стереть МОЖЕТ — и не может
  ничего сверх неё. Остаточный риск учтён: `[частично]`, наследует §5.
- **Вторая такая поверхность (1.0.6.32): событие шлюза Алисы стирает привязку к
  Алисе.** Та же гарантия, то же ядро (`opt/sa02m-cloud-agent/binding_core.py`,
  побайтовая копия в пакете умного дома, строка реестра `binding-reset-parity`),
  другая дверь: событие `controller_unlink` на **проверенной mTLS-сессии** →
  стереть `device.crt.pem`, `device.key.pem`, `pending_claim.json`, `ca.crt.pem`
  и sidecar'ы `*.tmp` в каталоге идентичности, плюс маркер в
  `sa02m-alice-client.conf`. **Порог здесь 1, а не 3, и это не ослабление:** по
  этому каналу приходит ВЕРДИКТ, доставленный один раз по каналу, подлинность
  которого дал взаимный TLS, а не улика, требующая подтверждения; шлюз рвёт
  соединение сразу после события. Подлинность — свойство канала: обработчик не
  читает НИ ОДНОГО поля тела (тело по контракту доставки необязательно), поэтому
  подделать событие можно только владея клиентским сертификатом платы или самим
  шлюзом. Радиус поражения замкнут и закреплён побайтовыми проверками
  (`test_binding_reset.py::TestN5Boundary`): документ устройств
  (`sa02m-alice-devices.conf`), `sa02m-alice-server.conf`, остальные ключи
  клиентского INI, MQTT, сеть, MPLC4/CODESYS, RS-485, учётные записи и
  `/etc/sa02m-cloud/*` НЕ затрагиваются; рекурсивного удаления нет. Восстановление
  — кнопка «Привязать» на карточке, без SSH (флаг `client_enabled` намеренно
  остаётся включённым). **Остаточный риск, честно:** владелец шлюза (актор A6)
  может в любой момент отвязать плату от Алисы — это, как и у A5, свойство самой
  фичи, а не дефект; ограничение в том, что он не может ничего сверх ЭТОЙ
  привязки и не может тронуть облачную привязку A5. `[частично]`, наследует §5.
  Что закрыто в обратную сторону (стирание по СОМНЕНИЮ — опасное направление,
  ведь линк на объекте разрывается десятки раз в сутки): разрыв соединения,
  таймаут, `403`, недоступный шлюз и любое другое событие привязку НЕ стирают —
  шесть негативных тестов (N1–N6) и общая с флотовой дверью батарея.

### Облако → сценарный движок (добавлен 2026-09-08, аудит 1.0.6.39)

```
[облако / шлюз Алисы]  ── Socket.IO alice_devices_scenarios ──►  sa02m-cloud-control
        (профиль cloud, opt-in)                                        │ sa02m_rules.store (валидация, /etc/sa02m-rules/scenarios.json)
                                                                        ▼
                                                              sa02m-rules (root)
                                       type=block/scene/logic ──► MQTT /devices/<id>/controls/<cap>/on  (реальные выходы)
                                       type=code  ──► ограниченный Python в процессе демона
                                       action http / Http ──► исходящий HTTP с платы

[A2/A3 LAN] [A6 «Алиса, включи <сцена>»] ── MQTT 1883 ──►  sa02m-rules (root)
        /devices/sa02m-rules-<sid>/controls/run/on           (вторая входящая нога, 1.0.6.41)
```

- **Третья поверхность, на которой облако меняет поведение платы** — и
  единственная, где оно поставляет **исполняемый код**. Предусловие: Оператор
  включил и привязал облачный стек (`sa02m-cloud-control` ставится `off`,
  `06-alice.sh`); сам `sa02m-rules` ставится `on`, но без канала он исполняет
  только локально сохранённые сценарии. Актор — A5 (владелец/захватчик облака)
  или A6 (владелец шлюза Алисы) с аутентифицированной сессией; подлинность
  канала — свойство транспорта (см. выше), здесь модель описывает, что
  аутентифицированный peer может сделать ПОСЛЕ.
- **Что закрыто с 1.0.6.39** (история — `CHANGELOG.md` §1.0.6.39,
  контракт `docs/contracts/cloud-scenarios.md`): (A1) у `type=code` не было
  вообще никакого ограничения времени — `while True: pass` навсегда вешал
  однопоточный движок вместе со всеми аварийными авто-выключениями, юнит без
  `WatchdogSec`, `Restart=on-failure` не срабатывал (процесс не падал); теперь
  жёсткий дедлайн `RUN_S` внутри процесса. (A6) `'{0._state}'.format(Hub)`
  обходил запрет `_`-атрибутов и читал весь граф объектов вплоть до
  `__import__` (только чтение, но утечка состояния через `Notify` в облако);
  `.format`/`.format_map` запрещены целиком. (A5) действие `http` и `Http`
  в песочнице принимали любой адрес — плата работала прокси в собственный LAN
  и на loopback-сервисы (CGI, флашер, `sa02m-devices-api`, mosquitto);
  теперь резолв + отказ по loopback/link-local/reserved/`user:pass@`,
  allow-list `/etc/sa02m-rules/http-allow.json`, ≤3 редиректов, ≤64 КиБ.
  (A2) `cap` не валидировался по charset — wildcard из облака ронял `publish`
  из `on_boot()` в бесконечный restart-loop; charset-пиновка + publish не
  выходит из `tick()`. (A3) юнит получил блок паритета с соседями плюс
  `ProtectSystem=strict`/`ReadWritePaths=/etc/sa02m-rules`.
- **Вторая входящая нога с 1.0.6.41 — из LAN, а не из облака.** `sa02m-rules`
  подписывается на `/devices/+/controls/+/on` локального брокера
  (`service.py` `SUBSCRIPTIONS`), и публикация в
  `/devices/sa02m-rules-<sid>/controls/run/on` **запускает сценарий** (payload
  `1`/`on`/`true`) или **выключает** те его выходы `on_off`, которые он ставит
  в единицу. По замыслу этим ходит шлюз Алисы (`sa02m-alice-client`
  публикует, когда пользователь говорит «включи <сцена>»), но брокер 1883
  локальной аутентификации не имеет — публиковать может **любой узел LAN**
  (A2/A3). Что ногу ограничивает: движок отвечает только за строку, которая
  существует, имеет `type: scene` и не выключена (`Engine._live_scene` — один
  дом правила для обоих глаголов, `run_scene`/`run_off`), поэтому `block` /
  `logic` / `code` из LAN не стартуют, а действие `scenario`/`scene` внутри
  сцены отказывает на потомке `logic`/`code` (`bad child`) — **песочный Python
  этой ногой недостижим**; `sid` не интерполируется никуда, а ищется в store,
  и до поиска `ID_RE` ограничивает и id устройства, и `sid`; расход тот же,
  что у любого прогона (`MAX_WRITES` = 8 записей на прогон, глобальное окно
  `WRITE_WINDOW_MAX` = 8 записей / 10 с, действие `http` — под `http_guard` и
  `HTTP_PER_RUN_MAX`); каждый прогон пишет запись в журнал `runs`
  (`source="external"`, у выключения `reason: "off"`), то есть след остаётся.
  `RulesApp.pub` отказывается публиковать `/on` под `sa02m-rules-*`, так что
  сценарий не перезапускает сам себя через брокер. Новой привилегии нога не
  даёт: узел LAN и раньше мог писать `/devices/<id>/controls/<cap>/on` тем же
  реальным выходам напрямую — новым стало то, что **одна** публикация
  запускает сохранённую композицию и что для неё нужно знать не выход, а
  только id сценария. Форма топика и семантика обоих глаголов —
  `docs/contracts/cloud-scenarios.md` §MQTT mirror; проекция сцены в
  устройство Алисы — `docs/contracts/alice-mqtt-mapping.md` §Scene devices.
  Гейт `py-unit-rules` (`SceneCommandIntakeTests`, `RunOffTests`). **Остаток,
  честно:** флаг `alice_expose` эту ногу НЕ ограничивает — гейт движка «сцена
  и включена», поэтому из LAN стартует любая включённая сцена, помечена она
  «в Алису» или нет; забором служит тип сценария, а не аутентификация,
  которой у 1883 нет. `[частично]`, наследует §5
- **Что изменилось в 1.0.6.41:** политика исходящего HTTP **выровнена с
  облаком** (совместное решение 2026-09-09): RFC1918/ULA-цели РАЗРЕШЕНЫ —
  сценарий Оператора может дозваниваться до своего NAS или панели, — а
  отказ остаётся по loopback (во всех написаниях: `2130706433`,
  `0177.0.0.1`, `127.1`, `[::1]`, `[::ffff:127.0.0.1]`), link-local
  (169.254.169.254), multicast/reserved/`0.0.0.0/8`, именам `localhost` и
  `*.localhost`, `user:pass@`, не-http(s) схемам и URL длиннее 500 символов.
  Allow-list стал средством РАЗРЕШИТЬ loopback-цель явно. Добавлен предел
  **8 исходящих запросов на один прогон** (`HTTP_PER_RUN_MAX`, общий счётчик
  действия `http` и песочного `Http`, включая вложенные сценарии): 9-й
  отказывается с `last_error="http cap"`. `RulesApp.pub` — последняя линия
  перед проводом для обоих путей (`block` и `code`) — сам проверяет
  `device`/`cap` по `ID_RE`/`CAP_RE`. Юнит получил `CPUQuota=50%` и
  `TasksMax=32`.
- **Остаток, честно:** код всё ещё исполняется **от root** в процессе демона
  (denylist-песочница, не изоляция процесса/namespace); дедлайн не прерывает
  C-вызов (`sum(range(10**12))` считается до конца одного байткода — системные
  `MemoryMax=32M`, `CPUQuota=50%`, `TasksMax=32` и `Nice=10` ограничивают
  ущерб, но не время); LAN достижим ПО ЗАМЫСЛУ (см. решение выше) —
  непреднамеренная LAN-служба остаётся принятым риском; DNS-rebinding
  между проверкой и соединением не защищён. Тем, что закрыто, гейтится
  `py-unit-rules` (`test_security.py`). `[частично]`, наследует §5.

### Мост HomeKit — второй входящий LAN-слушатель (добавлен 2026-09-27, из дерева)

```
[A2 LAN] [A7а LAN-узел] ── mDNS _hap._tcp (UDP 5353) + TCP <port, 21064> ──►  sa02m-homekit
          (только IPv4 выбранного eth0|eth1; модем и 0.0.0.0 — никогда)        (User=sa02m-homekit,
[A7б iPhone семьи] ── HAP (пара = авторизация) ──────────────────────────────►   не root)
[A7б iCloud] ── домашний центр Apple в LAN ── HAP ─────────────────────────►        │
                                                                     MQTT 127.0.0.1:1883
                                                                     /devices/<id>/controls/<x>/on
[A1/A2 → nginx :9999] ── сессия + CSRF ── sa02m_homekit_api.cgi ── sudo -n (4 глагола) ── trigger
```

- **Первый слушатель продукта, не стоящий за паролем панели.** nginx :9999 —
  единая дверь (§3 выше); HAP — отдельный TCP-сервер, не проксируется nginx и не
  публикуется облачным туннелем (allow-list `{80, 9999}` не меняется). Его
  авторизация — сама пара HomeKit: читать и писать характеристики может только
  контроллер, держащий пару (Ed25519, протокол HAP в библиотеке HAP-python).
  Предусловие: модуль установлен (`install.sh --with-homekit`, в заводской образ не
  входит) и включён на карточке — до этого ничего не слушает.
- **Окно сопряжения.** Pair-setup (SRP, 8-значный код) принимается, только пока у
  моста нет ни одной пары; после первой пары новый контроллер добавляется только
  уже сопряжённым владельцем. Библиотека блокировки перебора не имеет —
  добавлена своя: 100 неудачных доказательств кода → `MaxTries` до перезапуска
  демона.
- **Код сопряжения — только аутентифицированной веб-сессии.** Код живёт в
  хранилище пар (0600, пользователь демона) и выходит наружу только файлом
  `/run/sa02m-homekit/setup.json` (0640, группа `www-data`) пока мост работает и
  не сопряжён; CGI отдаёт его только на POST с сессией и CSRF-токеном,
  `no-store`. В журнал код не пишется (штатный вывод библиотеки заменён).
  Предупреждение: по HTTP без TLS (§5) код, показанный на карточке, идёт по сети
  открытым текстом — как и пароль панели.
- **`www-data` ключей не читает.** Демон работает от собственного пользователя
  `sa02m-homekit` (`ProtectSystem=strict`, запись только в свои два каталога);
  `www-data` в его группу не входит; каталог пар 0700, файлы 0600. Привилегии
  CGI → root — четыре закреплённых глагола хелпера (`etc/sudoers.d/sa02m-homekit`),
  argv проверяется внутри хелпера.
- **Демон не в группе `www-data`** (изменено 2026-09-28 по аудиту стендовой
  сессии, MED). Раньше юнит давал ему `SupplementaryGroups=www-data`, а
  установщик — членство в `/etc/group`: захваченный через разбор HAP до
  сопряжения процесс читал бы пароль панели (`/etc/sa02m_web.env`), YAML шлюза,
  все конфиги Алисы и файлы CSRF. Теперь группы нет ни там, ни там; нужное
  выдано обычными группами Unix — setgid-каталог `/run/sa02m-homekit` (файлы
  для CGI получают группу `www-data` без членства), каталог конфига
  `www-data:sa02m-homekit` 2750 (конфиг, сохранённый CGI, всегда получает
  группу моста; мост его только читает) и группа `sa02m-alice-devices` ровно
  из моста и `www-data` на документ устройств (`/etc/sa02m-alice` — 0771, вход
  без списка); POSIX ACL не используются — в продуктовом RT-ядре их нет
  (`docs/decisions/homekit-home-connect.md`). Действие выдачи проверяется
  действием: `sa02m-daemon-access.sh` пробует от
  имени моста каждое нужное чтение и каждое запрещённое (пароль панели,
  остальные конфиги Алисы, членство в `www-data`) — последним шагом установки
  (провал останавливает модуль) и перед каждым стартом юнита (провал — в
  журнале и `conf_unreadable` на карточке). Гейты: `daemon-least-privilege`
  (строки: нет `www-data`, нет `SupplementaryGroups=`, нет строки ACL, группы
  и режимы закреплены) и `daemon-access-effect` (действие на настоящих файлах
  от не-root uid). Остаток: мост читает документ устройств (имена и топики —
  то, что он и так проецирует) и больше ничего в `/etc/sa02m-alice`; `www-data`
  состоит в `sa02m-alice-devices`, но эта группа открывает только документ,
  который `www-data` и так пишет; сброс, образ и восстановление без документа
  создают его `root:www-data`, и группа возвращается при ближайшем старте
  моста; на плате новая выдача ещё не перепроверена `[частично]`.
- **Запись в реле идёт тем же путём, что у Алисы** (`DeviceRegistry.apply_actions`,
  `writable:false` не публикуется, `/on` без retain) — новой привилегии над
  брокером мост не даёт: узел LAN и без него пишет в 1883 (строка `A2/A3→S1` §4).
  Новое — что писать в реле может ещё и сопряжённый контроллер, в том числе из
  интернета через домашний центр (A7б), и только в устройства, которые оператор
  отметил «Показывать в HomeKit» (по умолчанию — ни одного).
- Контракт и его проверки — `docs/contracts/homekit-bridge.md`.

### Клиент Home Connect — исходящий канал в облако BSH (добавлен 2026-09-28, из дерева)

```
sa02m-homeconnect (User=sa02m-homeconnect, не root) ── HTTPS (TLS по системным корням,
   без прокси, без перенаправлений) ──►  api.home-connect.com  [A8]
        │  токены: /var/lib/sa02m-homeconnect/tokens.json 0600 (только демон)
        ▼
MQTT 127.0.0.1:1883  /devices/hc-<id>/controls/<x>  (retained, только чтение, без /on)
[A1/A2 → nginx :9999] ── сессия + CSRF ── sa02m_homeconnect_api.cgi ── sudo -n (4 глагола) ── trigger
```

- **Нового входящего слушателя нет.** Клиент только ходит наружу к хостам из
  закрытой таблицы (`constants.HOSTS`); конфиг называет ключ хоста, не URL, так
  что правка конфига не уведёт токен на чужой сервер; перенаправление — ошибка,
  а не переход (иначе заголовок `Authorization` ушёл бы на хост из ответа).
- **Облако — источник данных, не команд.** Клиент не подписан на MQTT и не
  умеет ничего, кроме `GET`; права — `IdentifyAppliance Monitor`. Каждое
  значение облака проходит закрытую таблицу контролов, строки облака не
  становятся сегментами топиков без очистки до `[a-z0-9-]`. Худшее, что может
  A8, — ложное состояние прибора в `hc-*`, а через него — срабатывание
  сценария, который интегратор сам на эти топики повесил (этап 3), но не
  прямая запись в реле.
- **`www-data` токенов не читает.** Каталог состояния 0700, файлы 0600
  пользователя демона; `www-data` в его группу не входит; CGI-диспетчер файл
  токенов не открывает, ни один ответ не несёт ни токена, ни `device_code`;
  токена нет в журнале, в `/run`, в веб-бэкапе, в клоне образа. Привилегии CGI →
  root — четыре закреплённых глагола хелпера (`etc/sudoers.d/sa02m-homeconnect`).
- **Демон не в группе `www-data`** (изменено 2026-09-28, то же правило, что у
  моста HomeKit): файлы для CGI получают группу от setgid-каталога
  `/run/sa02m-homeconnect`, свой конфиг демон читает через свою группу
  (каталог конфига `www-data:sa02m-homeconnect` 2750, конфиг 0640, без ACL). Процесс, захваченный через ответ облака, не читает
  пароль панели, веб-конфиги и документ устройств Алисы — это пробуется от его
  имени при установке и перед каждым стартом (`sa02m-daemon-access.sh`), гейты
  `daemon-least-privilege` и `daemon-access-effect`; на плате новая выдача ещё
  не перепроверена `[частично]`.
- Контракт и его проверки — `docs/contracts/home-connect.md`.

## §4 Злоупотребления (abuse cases) и текущие меры

| Актор→Актив | Сценарий | Текущая мера (дата аудита — когда меру ЧИТАЛИ; «держится» без теста её не доказывает — см. `A2→S1`) |
|---|---|---|
| A1→S2 | Дефолтный/слабый/утёкший единый пароль снаружи → вход → root-CGI | Сессионная модель (sha256-токен, серверное хранилище); **но** пароль один и общий, TLS нет — `[частично]` |
| A2→S2 | Инъекция из QUERY_STRING/POST/cookie в shell-слово/путь/unit | Allow-list валидация до shell; auth-before-mutation на мутирующих CGI — **держится** (аудит) |
| A2→S1 | Гонка/повтор действия шлюза/флашера, мид-поллинг | Кнопки disable на pending; port-lease (flock + stop/restore служб) — **держится**. `flasher_busy` — **держится с 2026-08-06**, до этого был МЁРТВ с 2026-07-12: проба в `sa02m-web-service-ctl.sh` слала выведенный из обращения статический токен, демон отвечал 401, а `curl` без `-f` выходит с кодом 0 — гейт всегда сообщал «не занято». Строка «проверено аудитом 2026-07-14» в заголовке таблицы этот факт НЕ поймала (аудит проверил наличие кода, не его действие). Сейчас: проба читает `poll_locked` с неавторизованного `/health` (`docs/contracts/flasher-health.md`), при нечитаемом ответе — fail closed, регрессия закрыта тестами `port-lease-gate` + `no-retired-session-token` |
| A6→S1 | Владелец/захватчик шлюза Алисы шлёт `controller_unlink` → плата стирает привязку к Алисе и перестаёт отвечать на голосовые команды | Радиус замкнут списком стирания (документ устройств, конфиги, MQTT, сеть, MPLC4/CODESYS, RS-485 не тронуты — побайтовые тесты `TestN5Boundary`); подлинность даёт mTLS-канал, ни одно поле тела не читается; стирание по сомнению закрыто N1–N6; восстановление — кнопка «Привязать» без SSH. ## §5 Заключение — сильнейшая НЕЗАКРЫТАЯ угроза (честно)

> «Это сейчас открыто» — юридический вердикт; модель, не способная его вынести, — театр.

**Устройство спроектировано под доверенную LAN, но по подтверждению Оператора
разворачивается с доступом через интернет/VPN и в общих заводских сетях. При этом:
транспорт — HTTP без TLS, аутентификация — единый общий пароль, нет per-user учёток,
нет журнала доступа, а за этой единственной дверью — root-способные CGI, прошивальщик,
мост в техпроцесс и (с 1.0.5.64) командная строка с произвольным shell от `www-data`
и root-режимом за паролем root, который по HTTP уходит открытым текстом.**

Значит: **экземпляр, доступный из интернета/VPN (или из недоверенной заводской LAN) с
дефолтным/слабым/утёкшим паролем → A1/A4 → S2 (root-захват) → S1 (контроль техпроцесса) и
S3 (подмена прошивки).** Это НЕ гипотеза — это текущая экспозиция везде, где развёртывание
не компенсирует модель внешними средствами. Меры, которые ДЕРЖАТСЯ (allow-list ввода,
auth-before-mutation, **валидация argv внутри привилегированных хелперов — с 1.0.6.24, после
того как аудит 2026-08-28 нашёл два обхода пиновки (H1/H2); пиновка пути появилась в 1.0.6.10,
когда B1 нашёл, что прежняя строка давала root без пароля через raw `tee`. Каждый раз проверка
отставала от реальности: ранний аудит смотрел НАЛИЧИЕ строки, а не её действие; гейт 1.0.6.10
смотрел один файл прав из шести. Сейчас проверка читает все шесть и требует, чтобы исправление
доезжало до платы по всем трём путям доставки**), закрывают инъекции, эскалацию через sudo и неавторизованную телеметрию,
но **не** закрывают связку «нет TLS + единый пароль + внешняя экспозиция + root/флашер за
одной дверью».

### Компенсации, на которые продукт сейчас опирается (organizational, не в коде)

- Развёртывание **только за VPN**, без прямой интернет-экспозиции.
- **Смена дефолтного пароля** при пусконаладке (наладчик — актор доверенный).
- Сегментация: устройство в изолированной техносети.

Эти компенсации — **вне продукта** и не гарантированы кодом. Продуктовые кандидаты,
закрывающие разрыв (для отдельного решения Оператора, НЕ выполнены здесь): TLS «из
коробки» (self-signed/ACME), обязательная смена дефолт-пароля при первом входе, per-user
учётки + журнал доступа (закрывает A3-атрибуцию), явная политика «только VPN» в
`docs/deployment.md`.

### Под-заключение: облачный удалённый доступ (A5) — активен с 1.0.6.2x; доминирует

**Активен.** Backend (`cloud.cyntron.ru/api/v1` + frps-сервер) и контракт enrollment
живут в ОТДЕЛЬНОМ репозитории, но с 1.0.6.2x платы реально привязаны и backend отвечает:
собственные записи §3 — stand-down по реальному отзыву (1.0.6.26), поверхность отвязки
Алисы, движок сценариев из облака (1.0.6.39+); контракты —
`docs/contracts/cloud-enrollment.md`, `docs/contracts/cloud-agent-status.md`,
`docs/contracts/cloud-scenarios.md`. Агент по-прежнему стартует в `standby`
(`enrolled=false`) до привязки — это состояние НОВОЙ платы, а не всего парка.

**Доминирует, как только активно.** Cloud-enrollment — это не просто ещё одна дверь: он
**инвертирует модель угроз**. §5 держался на организационной компенсации «только VPN,
без прямой экспозиции»; cloud превращает её в продуктовую функцию, которая сама делает
:9999/:80 достижимыми из интернета через reverse-туннель. Значит связка §5 (HTTP без
TLS + единый пароль + root-CGI/флашер за одной дверью) становится достижимой **через
облако**, а не только из LAN/VPN — и сразу для ВСЕХ enrolled-устройств, если облако
скомпрометировано.

**Честно про острейший край.** Он НЕ в root-канале команд — этот канал (прежний F1)
**удалён в коде** (агент `send-only`, `handle_command` вырезан, юнит-тесты стерегут его
невозвращение). Острейший край теперь — **облако как единый trust anchor, фронтящий
собственный HTTP + единый-пароль веб-UI устройства из интернета**, плюс два не-закрытых
кодом момент: облако видит UI-креды в открытом виде (публичный TLS терминируется на
облаке, за туннелем nginx HTTP). Набор туннелируемых портов облако НЕ диктует свободно —
device-side allow-list `{80, 9999}` держится (A5→S1/S2/S4). Продуктовые кандидаты (решение
Оператора, НЕ выполнены здесь): TLS на
самом UI (тогда облако не видит креды); привязка идентичности к чему-то прочнее
программного токена; явные требования к харденингу/владению backend в контракте.

- Цепочка доверия прошивки MR-02m: подписывается/валидируется ли `.fw` криптографически,
  или только формат? (владелец — репозиторий MR-02m).
- Встречаются ли у заказчиков требования ИБ (TLS/per-user/аудит) как контрактные?
- Есть ли развёртывания с ПРЯМОЙ интернет-экспозицией (без VPN) — тогда §5 уже «открыто».

Облачные (A5, из дерева 2026-07-17):

- Кто владеет и харденит cloud backend (activation API + frps-сервер)? Контракт
  enrollment (`docs/contracts/cloud-enrollment.md`) живёт в облачном репозитории — его
  безопасность здесь не проверяется.
- Модель аутентификации канала: шифруется ли транспорт туннеля frpc→frps (TLS), или
  защищён только shared `auth.token`? (Задаётся на стороне frps.)
- Должен ли device-side allow-list локальных портов быть шире `{80, 9999}` (например,
  под будущие роли туннеля) и кто это решает — Оператор или enrollment-контракт?
  Сам allow-list уже энфорсится устройством.
- Жизненный цикл идентичности без аппаратного корня доверия (нет secure element на
  A40i): ротация/отзыв frp-токена и device-id, поведение при factory reset.
- Доверие к frps-серверу и владельцу домена `cloud.cyntron.ru` (единая точка ко всем
  enrolled-устройствам).
