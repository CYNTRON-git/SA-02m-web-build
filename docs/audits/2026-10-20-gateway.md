# Независимый аудит шлюза и владения RS-485

Объект: текущее дерево на коммите `7399d9dd279d2e9e201d957c03014716ef9c7b91`.
Это аудит существующего продукта по ТЗ оператора, не подтверждение готовности отдельного изменения.
Плата в этом направлении не использовалась. Продуктовый код не изменялся.
Обнаруженные нарушения блокируют утверждение о корректном восстановлении служб во всех сценариях.

## Findings

### G1 — P1: завершение одной задачи возобновляет общий опрос во время другой задачи

Доказательства: `opt/sa02m-flasher/sa02m_flasher/mplc_lease.py:534` пропускает уже остановленную службу; `:538` учитывает только первую остановку; `:548`–`:554` запускает службу при выходе первого владельца. Счётчика пользователей нет. `opt/sa02m-flasher/sa02m_flasher/jobs.py:149` запрещает задачи только на одном порту, поэтому COM1 и COM2 могут работать параллельно.

Воспроизведение выполнено вызовами настоящего `port_lease` с подменёнными системными операциями: войти в lease COM1, войти в lease COM2 для одной активной MQTT-службы, завершить COM1. Получено `start_service.call_count == 1` при ещё открытой lease COM2.

Ожидание: общая служба возобновляется после последней зависимой задачи. Факт: первая задача запускает её преждевременно. Последствие: повторные попытки открытия занятого UART и риск вмешательства опросчиков, не соблюдающих тот же механизм исключения; одинаково опасно для сканирования и прошивки.

Исправление: учитывать владельцев/ссылки на каждую приостановленную службу либо применять адресную паузу по порту. Регрессия должна перекрывать две задачи и завершать их в обоих порядках.

### G2 — P1: аварийный обработчик запускает ранее выключенный MPLC и не восстанавливает MQTT

Доказательства: `etc/sa02m-flasher.service:18` безусловно выполняет `start` для каждого установленного `mplc.service`/`mplc4.service`. Проверяется только наличие юнита, не исходное состояние. Останавливаемый набор включает MQTT (`etc/sa02m_flasher.conf:27`), но `ExecStopPost` его не содержит. Учёт остановленных служб хранится в памяти (`mplc_lease.py:30`).

Статический сценарий: MPLC установлен, но был остановлен оператором; остановить либо перезапустить флашер. `ExecStopPost` запустит MPLC. Другой сценарий: флашер остановил MQTT и получил SIGKILL; Python finally/atexit не выполняются, а `ExecStopPost` MQTT не восстанавливает.

Последствие: изменение исходного состояния управления либо длительная потеря MQTT-опроса после падения флашера. Комментарий о гарантированном восстановлении в `etc/sa02m-flasher.service:17` не обеспечен реализацией.

Исправление: журналировать исходное состояние и принадлежность паузы, восстанавливать только записанные службы после освобождения портов. Регрессия: inactive MPLC остаётся inactive; active MQTT восстанавливается после принудительной смерти владельца. На плате эти сценарии не исполнялись.

### G3 — P1: неудачное восстановление забывается

Доказательства: `opt/sa02m-flasher/sa02m_flasher/mplc_lease.py:552` игнорирует возвращённый `False` от `start_service`; `:554` всегда удаляет запись из `_STOPPED_SERVICES`. `:561` также очищает весь список перед аварийными попытками восстановления.

Воспроизведение: реальный `port_lease`, успешная остановка, `start_service=False`. После выхода `released_services()` вернул `[]`. Задача не получает исключения восстановления, повторное `/ports/restore` больше не знает об обязанности запуска.

Ожидание: ошибка видима, запись сохраняется для повторной попытки. Последствие: операция выглядит завершённой, а служба остаётся выключенной. Регрессия должна проверять ошибку запуска, сохранение записи и успешную повторную попытку.

### G4 — P1: включение шлюза не реализует требуемую паузу служб

Доказательства: `opt/sa02m-serial-gateway/serial_gateway.py:932`–`:940` берёт собственную блокировку и сразу открывает UART; остановки или адресной lease опросчиков в этой цепочке нет. Собственная блокировка — `sa02m-gateway-COMn.lock` (`:520`), блокировка флашера — отдельная `sa02m-flasher-COMn.lock` (`opt/sa02m-flasher/sa02m_flasher/runner.py:68`). CGI управления только вызывает systemctl (`www/network_config/cgi-bin/gateway_ctrl.cgi:30`).

Сценарий: MQTT уже держит COM, пользователь включает шлюз для этого COM. При соблюдении `exclusive=True` обеими Python-сторонами (`serial_gateway.py:398`; `bridge_serial.py:434`) открытие шлюза откажет, а не приостановит MQTT. Для внешнего владельца без совместимой блокировки этот механизм не доказывает исключение конфликта. Прямой поиск флашера также не включает шлюз в список останавливаемых служб (`etc/sa02m_flasher.conf:27`).

Ожидание по ТЗ: явно управляемый переход и последующее восстановление исходного владельца. Факт: раздельные блокировки и отказ открытия вместо такого перехода. Исправление требует общего контракта владения UART, включая шлюз, MQTT, MPLC/CODESYS и флашер. Проверять физическую коллизию на рабочем оборудовании не следует; сначала нужен fake/PTTY-интеграционный тест.

Дополнительно прослежены оба входа. Кнопка в `www/network_config/static/js/gateway.js:248` вызывает `_svcCtrl`, который в `:532` посылает POST прямо в gateway_ctrl; тот в `gateway_ctrl.cgi:26` вызывает systemctl. Юнит `etc/sa02m-serial-gateway.service:9` запускает Python напрямую, `:11` обрабатывает reload через SIGHUP; `ExecStartPre`/зависимостей, останавливающих опросчики, нет. Сохранение в `gateway.js:489` вызывает gateway_config, затем `sa02m-gateway-config-apply.sh`; helper в `usr/local/sbin/sa02m-gateway-config-apply.sh:133`–`:134` только перезагружает конфигурацию шлюза. Скрытого координатора паузы в этих цепочках не обнаружено.

### G5 — P2: не поднявшийся TCP-порт публикуется как работающий

Доказательства: `serial_gateway.py:949` записывает `_gw` до `await start()`; обработчик ошибки `:953`–`:958` не сбрасывает `_gw`; `:975` возвращает `_gw is not None`, а `:991` публикует это как `running`.

Воспроизведение выполнено на извлечённом AST реального класса `PortGateway`, с зависимостями-заглушками и исключением `OSError("Address already in use")` из запуска TCP-сервера. Получено `start() == False`, `is_running() == True`.

Ожидание: `running=false` и ошибка bind. Последствие: JSON статуса одновременно утверждает, что порт работает, хотя слушателя нет. Регрессия: занятый TCP-порт и ошибка адреса bind не должны давать `running=true`.

### G6 — P2: RTU-over-TCP зависит от границ TCP-чтения

Доказательства: `serial_gateway.py:749` читает произвольный кусок через `read(512)`; `:759`–`:761` немедленно передаёт его в отдельный RTU-обмен. Сборки полного кадра нет.

Воспроизведение выполнено на AST реального `RtuOverTcpGateway`, с двумя чтениями одного корректного запроса `010300000001840a`: `010300` и `000001840a`. Worker получил два отдельных вызова; счётчик ошибок остался нулевым. TCP допускает такое дробление одного write отправителя.

Последствие: запрос может завершиться тайм-аутом на реальном устройстве из-за паузы между фрагментами; объединённые кадры также не разделяются. Реальный UART в этой проверке не использовался. Исправление: определить и проверить правила накопления RTU-кадров либо честно документировать ограничения режима. Регрессия: дробление каждого кадра во всех позициях, несколько кадров в одном TCP-чтении, неполный кадр и его тайм-аут.
