# Независимый аудит обновлений SA-02m, 20 октября 2026

Проверяемое дерево: `7399d9dd279d2e9e201d957c03014716ef9c7b91`, версия `1.0.7.1`. Это аудит существующего продукта, а не разрешение на выпуск новой сборки. При начале проверки имелись изменения `.ai-dev/launch`, `AGENTS.md` и неотслеживаемые `.agents/`, `.codex/`, `.opencode/`, `.tmp-mic-extract.md`; продуктовые файлы обновляющего механизма в `git status` не фигурировали. Стендом управляет основной агент; этот аудитор к нему не подключался.

**Вывод:** офлайн-обновление через панель не готово к эксплуатации. Обнаружены независимые ошибки соединения CGI с Python-библиотекой. Исправление только первого импорта не восстановит функцию. Интернет-обновление требует отдельной стендовой приёмки; результаты unit-тестов не доказывают его устойчивость при отключении питания.

## Дефекты

### UPD-01 — высокая: загрузка `.sa02m` не достигает приёмника файла

**Доказательства:** `www/network_config/cgi-bin/web_update_upload.cgi:168` импортирует `UploadError` из `lib.upload_receive`, которого в модуле нет. Реальный класс исключения — `PackageError`, `opt/sa02m-update/lib/__init__.py:37`. Импорт находится до `try`, поэтому обработчики CGI его не перехватывают.

Далее `web_update_upload.cgi:170` передаёт только `os.environ`. Приёмник требует объект потока `wsgi.input` (`opt/sa02m-update/lib/upload_receive.py:188`), иначе отвечает исключением `E_UPLOAD: wsgi.input missing` на строке 190. Кроме того, Python запущен с исходником через heredoc на stdin (`web_update_upload.cgi:164`): этот канал уже занят программой и не содержит HTTP-тело.

**Воспроизведение:** извлечён дословный встроенный Python-блок CGI; путь импорта заменён на локальный `opt/sa02m-update`; заданы POST, multipart Content-Type и ненулевой Content-Length. Исполнение завершилось с кодом 1, `ImportError: cannot import name 'UploadError'`, stdout пуст. Отдельный вызов реального приёмника с таким же словарём окружения завершился `E_UPLOAD: wsgi.input missing` до файловых операций. Авторизация и доставка HTTP-тела в этих пробах не испытывались.

**Ожидание:** корректный авторизованный multipart-запрос принимается, пакет проверяется, возвращается структурированный результат. **Факт:** выполняемый Python-блок падает до обработки файла; внешний CGI преобразует пустой результат в общий отказ загрузки.

**Задача исправления:** согласовать исключения и потоковый интерфейс; разделить канал исходника Python и канал тела запроса. Добавить тест реального CGI с multipart stdin, проверкой полученных байтов и отказами повреждённого/обрезанного тела. Сначала зафиксировать RED на текущем коде.

### UPD-02 — высокая: применение и отмена офлайн-пакета вызывают отсутствующий API транзакций

**Доказательства:** `web_update_apply.cgi:321` вызывает `txnmod.load`, строка 335 — `new_transaction`, строка 348 — `save`. `web_update_cancel.cgi:51`, 71 и 75 вызывают `load`, `_iso_now`, `save`. Маркировка загруженного файла также использует неверные имена (`web_update_upload.cgi:90`, 99).

Реальный API: `default_transaction` (`opt/sa02m-update/lib/transaction.py:57`), `load_transaction` (158), `save_transaction` (169), `utc_now_iso` (53). Аргументы тоже требуют согласования: вызов создания из CGI передаёт `signature_ok`, которого нет в сигнатуре `default_transaction`.

**Воспроизведение:** исполнены точные встроенные Python-блоки apply и cancel с локальным путём импорта и аргументами на существующие пути проекта. Оба завершились кодом 1, `AttributeError: module 'lib.transaction' has no attribute 'load'`, stdout пуст; до записей и systemctl исполнение не дошло.

**Ожидание:** подтверждённый пакет запускает транзакцию, допустимая отмена возвращает JSON и прекращает операцию. **Факт:** оба блока аварийно завершаются до этого. Проблема воспроизводится независимо от UPD-01, например при заранее размещённом пакете.

GET статуса скрывает ту же ошибку широким `except` и самостоятельным чтением JSON (`web_update_apply.cgi:106`–113). Работающий GET поэтому не является доказательством исправного apply/cancel.

**Задача исправления:** перевести все вызывающие места на один реальный API, проверить параметры и обработку ошибок; не ограничиваться добавлением алиаса `load`. Добавить интеграционные тесты upload → inspect → confirm → status → cancel с настоящей библиотекой транзакций и подменённым systemctl. Проверить конфликт операций и отмену на границе `backing_up`/`applying`.

### UPD-03 — высокая для старых установок: bootstrap-путь может сообщить успех после отказа установки root-хелпера

**Доказательства:** резервный путь выбирается при отсутствующем/несовместимом shared runner (`etc/sa02m-web-update-apply.sh:308`, 311, 416). Скрипт использует `set -uo pipefail`, без `errexit` (строка 6). Возвращаемые коды `atomic_install_script` при доставке библиотек и раннера не проверяются (449–465); после вызовов записывается сообщение об обновлении. Аналогично обрабатывается доставка привилегированных хелперов (488). Затем пишутся маркеры коммита и окончательный успех (577–578). Сбой копирования `/opt/sa02m-update` явно подавлен через `|| true` (512–515).

**Последствие:** при нехватке места/ошибке записи новая веб-часть может сосуществовать со старым или отсутствующим backend, а состояние обновления показывает `done`. Это особенно важно для перехода старой установки на общий раннер.

**Воспроизведение:** статически прослежен путь отказа `atomic_install_script` → непрерванный цикл → финальный `done`. Ошибка диска в полном launcher на стенде не вводилась; данный пункт не представлен как стендовая репродукция.

**Задача исправления:** сделать ошибки обязательных доставок терминальными, запретить публикацию успешного маркера при неполной поставке, определить восстановление частичного bootstrap. Закрепить тестом launcher с отсутствующим runner и принудительным отказом копирования каждого обязательного компонента.

## Риски и незакрытые сценарии

- Интернет-канал устанавливает неподписанный код из разрешённого репозитория: `etc/sa02m-update-runner.sh:947`–949. Это зарегистрированное решение `docs/decisions/github-ota-unsigned.md`, а не новый скрытый дефект. Остаточный риск компрометации источника сохраняется; наличие подписи в офлайн-канале не закрывает его.
- Источники обновлений и цепочки старых runner нельзя считать взаимозаменяемыми. Ограничения перехода с версии ≤ `1.0.6.51` описаны в `docs/contracts/web-update.md` и `docs/deployment.md`; свежий код после доставки не доказывает, что доставлявший его старый процесс работал по новым правилам.
- Не проверены физический сбой питания, DNS/TLS-отказы на плате, заполнение её накопителя, полное восстановление с резервной копии, длительный прогон и поддерживаемые старые версии. Матрица их подтверждённой совместимости пока отсутствует в результатах этого аудита.
- Наличие защиты подписи, allowlist и сохранения конфигурации не является общим вердиктом безопасности: гонки upload/cancel с работающим runner требуют отдельного динамического теста после восстановления самих CGI.

Приоритет исправлений: UPD-01 и UPD-02 вместе с интеграционным тестом офлайн-цепочки; затем UPD-03 и приёмка bootstrap. До этого успешный запуск unit-suite недостаточен для заявления о полнофункциональном OTA.
