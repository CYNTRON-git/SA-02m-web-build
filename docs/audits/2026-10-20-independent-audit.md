# Независимый аудит SA-02m от 20 октября 2026 года

**Промежуточный вердикт: не готово к эксплуатации в объёме заявленных требований. Аудит не завершён.** Найдены воспроизводимые нарушения офлайн-обновления, восстановления служб и достоверности статусов. Это не означает отказ каждой функции устройства: исправные локальные тесты и наблюдаемая работа стенда перечислены отдельно. Суточное наблюдение продолжается; 100 аппаратных переключений и испытания с отключением питания не выполнены.

## Подтверждённые препятствия и порядок исправлений

Идентификаторы, подробные шаги, ожидаемый/фактический результат и регрессионные требования определены в отчётах направлений. Высокая серьёзность ниже соответствует P1, средняя — P2; это приоритет устранения, не утверждение о частоте отказа.

| Приоритет | Дефекты | Последствие и основание |
| --- | --- | --- |
| P1 | UPD-01, UPD-02 | Офлайн upload/apply/cancel вызывают несовместимые интерфейсы Python; исполнение точных блоков CGI падает до полезной операции. |
| P1 | G1, G2, G3 | Общая служба возобновляется раньше завершения всех задач; аварийное восстановление не сохраняет исходное состояние; неудачный запуск забывается. G1/G3 воспроизведены с системными заглушками, G2 прослежен статически. |
| P1 | G4 | Включение шлюза не реализует требуемый переход владения UART и паузу прежнего опросчика. Статический анализ цепочки управления и раздельных блокировок. |
| P1 | S1, S2 | Незавершённое тело HTTP может остановить очередь статусов; старые метрики не получают явного признака устаревания. Локальные пробы текущих функций. |
| P1 для старых установок | UPD-03 | Bootstrap может опубликовать успех после ошибки доставки обязательного backend. Статический путь ошибки; отказ накопителя на плате не вводился. |
| P2 | G5, G6 | Ошибка bind оставляет ложный `running`; RTU-over-TCP трактует произвольные TCP-фрагменты как отдельные обмены. Изолированные пробы текущих классов. |
| P2 | S3, S4, S5, S6 | `activating` выглядит активным; облачный статус допускает гонку ответов; GET с HTTP 200 unauthorized не переводит на вход; в управлении выключенный автозапуск скрывает текущую активность. Локальные пробы и Chromium; точные границы — в отчёте статусов. |

Первый пакет исправлений должен восстановить офлайн-цепочку и контракт владения UART, затем устранить зависание и ложную актуальность статусов. Для каждого подтверждённого дефекта требуется тест RED на текущем коде и GREEN после исправления. Приёмку OTA проводить также через настоящий CGI с HTTP-телом, а не только прямым вызовом Python-библиотеки. Переходы владения сначала проверить на fake/PTTY, включая два порта, оба порядка завершения, смерть владельца и отказ повторного запуска службы.

## Стендовые измерения и проверки качества

Исходно MQTT, flasher, MPLC4, VPLC и stand API были active; serial gateway — inactive/disabled, CODESYS — inactive. Для MPLC4 `MainPID=0` при active: один systemd-статус не доказывает работающий процесс или обмен. Владельцы всех UART и перечень физических модулей в доступном baseline не зафиксированы полностью.

Позднейшая контрольная точка (`service-checkpoint-135.txt`, `service-checkpoint-136.txt`) уточнила владение: на 135 COM2/3/4 открыты PID 7706 `sa02m-modbus-mqtt`, COM5 — PID 1589 из cgroup `sa02m-test-trigger.service` (стендовая служба), COM1 свободен. На 136 открытых COM не обнаружено; gateway исходно masked, MPLC disabled, vPLC active. Нельзя считать все COM принадлежащими только продуктовым опросчикам. На обеих платах failed units = 0, исходные состояния проверенных служб сохранены.

В 09:53:24 MSK: `MemTotal=503216 kB`, `MemAvailable=126876 kB`, swap отсутствует; load average `3.61 / 3.90 / 3.73`; thermal raw `80795` (при шкале millidegrees — 80,795 °C); journald занимает 18,6 MB. Одного среза недостаточно для вывода об утечке памяти, тепловом throttling или устойчивой перегрузке.

Накопленные UART-счётчики baseline: UART3 `oe=206`; UART4 `fe=1192, pe=3, brk=221`; UART5 `oe=84630`. Они ненулевые, но накоплены до начала аудита. Причину и текущую скорость прироста должен установить временной ряд; приписывать их новому сценарию нельзя.

В первых отсчётах sampler координатор наблюдал рост UART5 overrun с 84633 до 84642 за две минуты, температуру 78–80 °C и значения максимальной задержки bridge 9556/15505/10807 ms. Это уже прирост в окне наблюдения, но не установленная причина ошибок и не сравнение режимов. Поле `rtcpuload` существующего sampler получает HTML: измерение недоступно, это не нулевая нагрузка. Для независимого временного ряда запущен `sa02m-audit-20261020-vmstat`, данные сохраняются в `/root/bench/audit-20261020/vmstat.txt`. Первая строка vmstat отражает среднее с загрузки; её исключить из выводов об изменении нагрузки за окно аудита.

На 10:20:52 MSK оба sampler-юнита оставались active. За интервал от 09:55:29 UART5 OE вырос с 84633 до 84688 (+55), UART3 OE с 206 до 210 (+4). Это подтверждённое накопление ошибок при фактической смешанной нагрузке; принадлежность COM5 стендовому процессу требует учитывать этот фактор до вывода о причине. Суточный результат ещё отсутствует.

По `http-status.json` получено по три последовательных ответа каждой части, все HTTP 200. Прямой `main` последовательно собирает восемь частей без TTL-кэша. **Текущий frontend не запрашивает `part=main`: `fetchStatusMain` координирует раздельные части.** Поэтому 11,5–13,4 секунды прямого main не доказывают такую же задержку dashboard. Холодный services и отдельные выбросы требуют трассировки и повторного измерения; его timeout зависит от ожидания очереди (8–16 секунд), поэтому нельзя утверждать автоматический обрыв каждого ответа дольше восьми секунд. Порог приемлемости аудитом не установлен: полная сопоставимая матрица режимов, включая шлюз и поиск, не выполнена; короткие браузерные пробы ниже не устанавливают SLA.
