# Решение: не переписывать боевые version-ветки (мост самообновления отменён)

**Дата:** 2026-08-19. **Статус: действует.**

Дом решения о том, как обновлять платы со старых веб-версий (< 1.0.5.75), которые
не видят обновления через интернет (проверка обновлений на такой плате смотрит в
собственную version-ветку, а не в `main` — причина в `CHANGELOG` 1.0.5.75). Ссылается
на `docs/deployment.md` (пути деплоя) и `docs/decisions/update-mechanism-vs-wirenboard.md`.
Машинная грамматика (команды, имена веток) — латиницей (`PROTOCOL.md` invariant 5).

## Контекст

Для плат < 1.0.5.75 рассматривался **мост самообновления**: в боевую version-ветку
(например `1.0.3.34`) force-push'ом клался коммит = `main` с одним заменённым файлом
(`etc/sa02m-repair-web-env.sh` → лаунчер), чтобы старый веб-апдейтер платы сам
скачал его и запустил полную установку. Инструментарий собран и лежит в репозитории
(`tools/update-bridge/`, `scripts/offline-full-update.sh`), протестирован в WSL.

## Решение

**Мост НЕ используется. Боевые version-ветки на origin НЕ переписываются
(ни force-push, ни изменение вершины).** Ветка `1.0.3.34` (и любая другая
`N.N.N[.N]`) остаётся неизменной; тег `archive/*` и коммит-мост не публикуются.

Старые платы обновляются **офлайн-архивом всего дерева**:
`git archive --format=tar.gz -o SA-02m-full-<ver>.tar.gz origin/main` → на плату в
`/tmp` → `bash scripts/offline-full-update.sh` (единственный дом процедуры —
`docs/deployment.md` «Полный деплой» → «Офлайн-вариант»). Доставка по SSH/USB.

## Почему

- **Риск для флота.** Force-push ~90 боевых веток переписывает историю, на которую
  может ссылаться внешний инструментарий и сами платы; ошибочный лаунчер ломает
  OTA-путь сразу на всех клонах этой версии, а откат — только через тег `archive`,
  который тоже надо публиковать. Цена ошибки — массовая, откат ручной.
- **Проще и уже работает.** Офлайн-архив + `offline-full-update.sh` не трогают
  origin, идемпотентны, дают бэкап `/etc` и таблицу пост-проверок, и доставляются
  адресно на конкретную плату наладчиком. Тот же результат (полная установка →
  новая проверка обновлений смотрит в `main`) без переписывания веток.
- **Обратимость.** Ничего не опубликовано наружу — решение отменяемо без следов.

## Что с кодом

`tools/update-bridge/` (`repair-web-env-launcher.sh`, `publish-bridge.sh`) и флаги
`--unattended`/`--status-file`/`--log` в `offline-full-update.sh` **остаются в
репозитории как непубликуемый инструмент** (deprecated): `publish-bridge.sh` по
умолчанию dry-run и `--push` отказывается работать без ручного подтверждения — сам
по себе он ничего не ломает. Не удаляем сейчас, чтобы не раздувать диф; при
следующей уборке `tools/update-bridge/` можно снять целиком (эта запись —
основание). `offline-full-update.sh` остаётся рабочим (офлайн-путь его использует).

## На будущее

Любой сценарий «доставить обновление на плату, не видящую интернет» решается
офлайн-архивом, а НЕ модификацией боевых version-веток. Если когда-нибудь
понадобится OTA для старых плат — делать это через нормальный релиз в `main` и
починку проверки обновлений на плате (полная установка), не через переписывание
истории веток.
