# Решение: какие версии Node-RED и Node.js закреплять для СА-02м (armv7l)

**Дата исследования:** 2026-08-06. **Статус:** решение принято, репозиторная
часть реализована — пин 4.1.13 / Node 22 живёт в коде и гейтится строкой
`nodered-pin-consistency`; форма payload'а и его сборка — в
`docs/vendor-integrations.md`, процедура на устройстве — в `docs/deployment.md`.
Сборка payload'а на плате и обновление стенда — отдельные шаги, ещё не сделаны;
измеренные размеры/время появятся в `BUILD-INFO.txt` и заменят оценки ниже.
Порядок шагов на устройстве принят обратный рекомендованному в §4: сначала
Node 22 (на нём проверяется прежний Node-RED), потом Node-RED 4.1.13 — так у
каждого шага ровно один подозреваемый.
**Платформа:** Allwinner A40i, `armv7l` / Debian `armhf`, ~512 MiB RAM, Armbian,
ядро 6.1. Текущее состояние устройства (со слов Оператора): Node.js v20.19.1
(apt, NodeSource) + Node-RED 3.1.15, работает.

Все версии, команды и URL — в английском виде (машинные факты). Проза русская
(`docLanguage: ru`).

---

## Короткий ответ

1. **Node-RED 3.1.15 — НЕ правильный пин: линия 3.x снята с поддержки 30.06.2025.**
   Она работает, но фиксов и security-обновлений не получает уже больше года.
2. **Рекомендуемый пин: Node-RED `4.1.13`** — последний релиз линии 4.x
   (опубликован 2026-07-30, то есть за неделю до этого исследования), требует
   Node.js `>=18.5`, а значит **запускается на уже установленном Node 20.19.1
   без единого изменения в Node.js**.
3. **Node-RED 5.x (5.0.4) действительно неприменим сейчас**: жёсткое требование
   Node.js `>=22.9` с `process.exit(1)` при несоответствии; апстрим при этом
   перестал собирать для 5.x образы `linux/arm/v7`.
4. **Потолок Node.js для armv7l — линия 22.x.** С Node.js 24 официальных
   сборок `linux-armv7l` больше нет, а сама платформа armv7 понижена до
   «экспериментальной».
5. **Предпосылка «самое новое больше не поддерживается» — верна по сути, но
   неверна буквально.** Не поддерживается как раз *старое* (Node-RED 3.x, EOL;
   Node.js 20, EOL). Новое (5.x) поддерживается — просто не запускается на этом
   железе. Подробности в разделе «Проверка предпосылки».

Рекомендуемая пара для оффлайн-пакета: **Node-RED 4.1.13 + Node.js 20.19.1
(уже на устройстве)**, с запланированным переходом на **Node.js 22.23.x
(официальный armv7l tarball)** — он снимает EOL-долг по Node и открывает путь
к Node-RED 5.x без смены железа.

## 1. Node.js на 32-битном ARM

**Проверено в вебе (nodejs.org, github.com/nodejs, deb.nodesource.com).**

| Мажор Node.js | Официальный `linux-armv7l` | Статус линии | End-of-life |
|---|---|---|---|
| 18 (Hydrogen) | да | EOL | 2025-04-30 |
| 20 (Iron) | да (последняя v20.20.2) | **EOL** | 2026-04-30 |
| 22 (Jod) | да (последняя v22.23.2) | Maintenance LTS | 2027-04-30 |
| 24 (Krypton) | **нет** | Active LTS | 2028-04-30 |
| 26 | **нет** | Current | 2029-04-30 |

- Наличие/отсутствие файлов проверено по машинному индексу дистрибутива
  <https://nodejs.org/dist/index.json>: у v20.20.2 и v22.23.2 в `files` есть
  `linux-armv7l`, у v24.19.0 и у 26.x — нет. Косвенно подтверждается листингом
  <https://nodejs.org/dist/latest-v24.x/> (только `linux-arm64`) против
  <https://nodejs.org/dist/latest-v22.x/> (есть `node-v22.23.2-linux-armv7l.tar.xz`).
- Границу задаёт PR <https://github.com/nodejs/node/pull/58071> — *«build:
  downgrade armv7 support to experimental»*, semver-major, попал в **Node.js
  24.0.0** (2025-05-06, <https://nodejs.org/en/blog/release/v24.0.0>). Мотивация
  автора: «There are a bunch of issues on that platform with recent V8 versions
  and we don't have the capacity to fix them». Сопутствующая задача о
  прекращении официальных armv7l-сборок — nodejs/build#4071.
- Даты EOL — машинный график релизов
  <https://raw.githubusercontent.com/nodejs/Release/main/schedule.json>.

**Вывод по Node.js: последняя линия с официальными 32-битными ARM-бинарниками —
22.x, и она же последняя. Node.js 20 на устройстве уже EOL (с 2026-04-30).**

### NodeSource (.deb, `armhf`)

NodeSource формально заявляет `armhf` (ARM 32-bit hard-float, ARMv7 and up) как
поддерживаемую архитектуру (<https://github.com/nodesource/distributions>,
DEV_README). Фактическое наполнение репозиториев (проверено чтением индексов
`dists/nodistro/main/binary-armhf/Packages`):

| Репозиторий | Максимальный пакет `nodejs` для `armhf` |
|---|---|
| `https://deb.nodesource.com/node_20.x` | **20.19.1-1nodesource1** (при апстриме 20.20.2) |
| `https://deb.nodesource.com/node_22.x` | **22.15.0-1nodesource1** (при апстриме 22.23.2) |
| `https://deb.nodesource.com/node_24.x` | **пакета `nodejs` нет** — в индексе только `nsolid` (сборки N\|Solid) |

То есть версия 20.19.1 на устройстве — это ровно потолок NodeSource для armhf,
и это объясняет, почему устройство «застряло» именно на ней. Отставание armhf
подтверждено открытым баг-репортом
<https://github.com/nodesource/distributions/issues/1881> (от 2025-07-30,
на момент проверки без ответа мейнтейнеров).

**Практический вывод: apt-путь NodeSource для armhf — тупиковый и отстающий.
Для управляемого пина надёжнее официальный tarball с nodejs.org.**

## 2. Требования самого Node-RED (`engines.node`)

**Проверено в вебе (registry.npmjs.org, unpkg, raw.githubusercontent.com).**

| Node-RED | `engines.node` | Проверка в рантайме (`red.js`) | Работает на Node 20? |
|---|---|---|---|
| 3.1.15 | `>=14` | (не проверено, см. ниже) | да |
| 4.0.0 | `>=18.5` | — | да |
| 4.1.13 | `>=18.5` | `semver >=18.0.0`, иначе `process.exit(1)` | **да** |
| 5.0.4 (`latest`) | `>=22.9` | `semver >=22.9.0`, иначе `process.exit(1)` | **нет** |

- 3.1.15: `{"node":">=14"}` — подтверждено и в метаданных реестра
  (<https://registry.npmjs.org/node-red/3.1.15>), и в самом опубликованном
  `package.json` (<https://unpkg.com/node-red@3.1.15/package.json>). **Утверждение
  Оператора о `">=14"` в `package.json` на устройстве — верное.**
- 4.1.13: `{"node":">=18.5"}` (<https://registry.npmjs.org/node-red/4.1.13>,
  <https://unpkg.com/node-red@4.1.13/package.json>).
- 5.0.4: `{"node":">=22.9"}` (<https://registry.npmjs.org/node-red/latest>).
- Стартовая проверка версии живёт в
  `packages/node_modules/node-red/red.js`; для 5.x (ветка `master`) это
  `>=22.9.0` с сообщениями `Unsupported version of Node.js: <v>` /
  `Node-RED requires Node.js v22.9 or later` и выходом с кодом 1 — ровно тот
  отказ, который описан в комментарии `scripts/07-nodered.sh:86-88`. Для тега
  `4.1.13` та же проверка — `>=18.0.0` / `Node-RED requires Node.js v18 or later`.
- Официальная таблица проекта (<https://nodered.org/docs/faq/node-versions>):
  5.x → Node 22, 4.x → Node 18, 3.x → Node 14, 2.x → Node 12; рекомендуемая
  проектом версия Node — 24.x (для armv7l недостижима, см. раздел 1).

**Ключевой факт для этого репозитория: Node-RED 4.x требует Node ≥18, а не
≥22.9.** Условие в `scripts/07-nodered.sh:96` (`NR_MAJOR >= 4` → откат на `v3`)
и в `etc/sa02m-web-service-ctl.sh:856-881` (жёсткий пин `node-red@3` на armhf)
откатывает больше, чем нужно: на Node 20 полностью работоспособна вся линия
4.x. Это найдено чтением репозитория, не проверено на устройстве.

| 4.x | 2024-04-30 | 2026-06-09 | **2026-12-31** | 4.1.13 (2026-07-30) |
| 5.x | 2026-06-09 | — | — | 5.0.4 (2026-07-30) |

- Ответ на вопрос «самый новый Node-RED, который запускается на Node.js 20 /
  armv7l без предупреждений и без отказа»: **4.1.13**.

## 4. Рекомендация

### Что пинить

| Компонент | Пин | Почему |
|---|---|---|
| Node-RED | **4.1.13** | последняя в поддерживаемой линии 4.x; `engines >=18.5` → идёт на текущем Node 20.19.1; апстрим для 4.1.x ещё собирает образы `linux/arm/v7` |
| Node.js (сейчас) | **20.19.1** (как есть на устройстве) | ничего не трогаем — Node-RED 4.1.13 стартует; риск нулевой |
| Node.js (цель) | **22.23.x**, официальный tarball `node-v22.23.x-linux-armv7l.tar.xz` | последняя линия с официальными armv7l-сборками, поддержка до 2027-04-30; снимает EOL-долг и открывает Node-RED 5.x |

**Подтверждение того, что 3.1.15 — «уже правильный ответ», дать нельзя.**
3.1.15 работает, но линия мертва с 30.06.2025: никаких исправлений, включая
security. Переход 3.1.15 → 4.1.13 — это не «изменение ради изменения», а выход
из EOL, и он не требует ни смены Node.js, ни изменения архитектуры установки.

### Почему не 5.0.4

Технически 5.0.4 запустился бы на Node 22.23.2 armv7l (22.23 > 22.9). Но:

- апстрим-образы Docker для 5.0.4 существуют только для `amd64`/`arm64` —
  вариант `linux/arm/v7` исчез (для 4.1.13 он ещё публикуется:
  `4.1.13-20-minimal` есть в `arm/v7`). Проверено через Docker Hub API
  (`https://hub.docker.com/v2/repositories/nodered/node-red/tags/`). Это
  сигнал, что armv7 в линии 5.x проектом не тестируется;
- переход требует одновременно и смены Node.js, и смены Node-RED — два
  изменения вместо одного, на устройстве без интернета.

Разумная лестница: **4.1.13 на Node 20 сейчас → Node 22.23.x в следующем
образе → 5.x после этого, если понадобится.** До 2026-12-31 (EOL 4.x) время
есть.

### Проверка предпосылки Оператора

Формулировка «самое новое больше не поддерживается» **не подтверждается**:
Node-RED 5.x — это как раз текущая поддерживаемая линия. Не поддерживается
Node-RED 3.x (EOL 2025-06-30) и Node.js 20 (EOL 2026-04-30) — то, что стоит
на устройстве сейчас.

Что действительно верно и что, видимо, и имелось в виду: **самое новое
неприменимо на этом железе** — 32-битный ARM выпадает из официальной поддержки
Node.js начиная с 24, и Node-RED 5 требует Node ≥22.9. То есть ограничение
идёт от платформы, а не от «плохой новизны».

## Часть 2. Оффлайн-установка: осуществимость

Раздел о том, *как* это может работать, без реализации.
Прочитанное в репозитории отмечено ссылками на файлы; веб-факты — URL.

### Что сейчас в репозитории

- `scripts/07-nodered.sh` — install-time путь. Строки 42-49: два `curl`-пробника
  (`registry.npmjs.org` и raw.githubusercontent.com) с `exit 1` при недоступности
  — это и есть наблюдаемый `[ERR] Нет доступа к registry.npmjs.org`. Строка 76:
  установка пайпом `bash <(curl -fsSL "$INSTALLER_URL")` — официальный
  `update-nodejs-and-nodered`. Оффлайн-ветки нет вообще.
- **Оффлайн-путь уже существует в рантайм-половине**:
  `etc/sa02m-web-service-ctl.sh`, функция `nodered_install_offline()`
  (строки 889-944). Она ищет `/opt/vendor-installers/nodered/` и ожидает:
  `node-*-linux-armv7l.tar.*` (распаковывается в `/usr/local`, **только если
  `node` отсутствует**), `node-red-*.tar.*` либо `node_modules*.tar.*`
  (распаковывается в `/usr/lib/node_modules`), `nodered.service`, опционально
  `settings.js`. Затем создаётся симлинк `/usr/bin/node-red` → `red.js`.
  `nodered_install()` (строки 946-957) сначала пробует онлайн, при отсутствии
  сети — оффлайн, иначе отдаёт `{"error":"no_internet"}`.
- Формат payload уже задокументирован: `docs/vendor-integrations.md:145` —
  «Node armhf tarball + собранное дерево `node-red@3` + `nodered.service`
  (+`settings.js`)».

**Следствие: изобретать механизм не нужно, но и «просто положить файлы» не
получится — не хватает трёх вещей:**

1. **собранного payload** (дерево Node-RED + `nodered.service`, опционально Node
   tarball и `settings.js`) — его сегодня не существует;
2. **симметричной оффлайн-ветки в `scripts/07-nodered.sh`** — install-time путь
   сейчас безусловно требует сеть (строки 42-49) и оффлайн-ветки не имеет вовсе;
3. **поддержки `vendor/nodered/` в сборщике rootfs** — сейчас её нет, см. ниже.

Пин во всех местах должен быть один (предупреждение в
`docs/vendor-integrations.md:136-137` о синхронизации 07/08/09 и ctl-скрипта).

**Важно: `tools/debian-rootfs/create-sa02m-rootfs.sh` НЕ копирует `vendor/*`
целиком.** Это жёстко заданный перечень из двух каталогов: условие на строке 307
— `[ -d "$REPO_ROOT/vendor/codesys" ] || [ -d "$REPO_ROOT/vendor/mplc4" ]`,
цикл на строке 310 — `for sub in codesys mplc4; do`. Каталог `vendor/nodered/`
будет **молча проигнорирован**: ни ошибки, ни предупреждения. То же ограничение
зафиксировано и в `docs/vendor-integrations.md:18-21`, где перечислено ровно
`vendor/{codesys,mplc4}/`.

Практический эффект: если подготовить payload ровно так, как описано ниже, и
запечь образ, то `/opt/vendor-installers/nodered/` в rootfs не появится, и
`nodered_install_offline()` вернёт `staging_missing`. Каталог придётся либо
доставлять на устройство вручную (`pscp` в `/opt/vendor-installers/nodered/`,
как в рецепте `docs/vendor-integrations.md:103-107`), либо добавить `nodered` в
перечень на строке 310 (и в условие на 307). Это отдельная правка сборщика —
в объём данного исследования она не входит.

### Что именно надо вендорить: `npm pack` не годится

- `npm pack node-red@4.1.13` даёт только верхний пакет:
  `dist.unpackedSize` = **97 615 байт, 8 файлов**
  (<https://registry.npmjs.org/node-red/4.1.13>). Это обёртка, кода Node-RED в
  ней практически нет.
- Прямых зависимостей у верхнего пакета — **12** (перечислены в его
  `package.json`, см. раздел 2). Полное разрешённое дерево — **сотни пакетов**;
  точное число **не установлено**, см. врезку ниже.
- Основная масса кода — в `@node-red/editor-client` (**34 586 319 байт**
  распакованными, 306 файлов) и `@node-red/nodes` (2 846 443 байта, 606 файлов).

> **Почему не приводится точное число пакетов.** Граф зависимостей брался из
> deps.dev (`https://api.deps.dev/v3/systems/npm/packages/node-red/versions/4.1.13:dependencies`,
> а также `v3alpha`-вариант того же эндпоинта). Инструмент, которым эта JSON
> читалась в данной сессии, — суммаризирующий web-fetch, а не точный подсчёт:
> два обращения к одному и тому же эндпоинту дали **разные** числа узлов
> (673 и 550), а независимая проверка того же URL дала **490**. Ни одна из
> величин не воспроизводится, поэтому никакая из них не публикуется.
> Воспроизводимый подсчёт требует машинного разбора JSON (`jq '.nodes|length'`)
> в среде с сетевым доступом — в этой сессии сети из shell нет. Правило
> подсчёта, которое следует применить: длина массива `nodes` эндпоинта `v3`,
> включая корневой узел с `relation: SELF`.
>
> На выводы это не влияет, и это проверяемо: интервал размера (раздел «Размер
> артефакта») построен на двух измерениях — скачанных и промеренных `.tgz` двух
> самых больших пакетов (нижняя граница) и дельте официальных Docker-образов
> (верхняя граница). Ни одна из границ не умножает и не экстраполирует число
> пакетов; ранняя версия этого документа так делала, и вместе с числом убран и
> тот расчёт. Порядок величины — сотни пакетов — остаётся достаточным для
> единственного вывода, который из него делается: `npm pack` верхнего пакета
> непригоден, вендорить надо всё дерево целиком.

Варианты механизма:

| Механизм | Пригодность | Подводные камни |
|---|---|---|
| **Готовое дерево tar.gz** (`npm install -g node-red@4.1.13` на armv7 → `tar czf` из `/usr/lib/node_modules/node-red`) | **рекомендуется** — ровно то, что уже ожидает `nodered_install_offline()` | нужна armv7-машина (само устройство или `docker --platform linux/arm/v7`); дерево привязано к мажору Node на момент сборки, если внутрь попали нативные модули |
| Оффлайн-кэш npm (`npm install --cache ./c` → перенос → `npm ci --offline --cache ./c`) | рабочий, но лишний | кэш зависит от версии npm и целостности `_cacache`; `npm ci` всё равно исполнит lifecycle-скрипты и попытается собрать нативные модули на устройстве; по объёму больше готового дерева (метаданные + tgz + распакованное) |
| `npm pack` / `bundledDependencies` | не годится | 8 файлов, 97 KB — см. выше |
| Локальный registry (verdaccio) | не годится | требует сервиса и предварительного «прогрева» — на устройстве без интернета это лишняя инфраструктура |

### Нативные модули (главный риск на ARM)

Проверено по опубликованным `package.json`:

- **node-red 3.1.15**: `optionalDependencies: {"bcrypt":"5.1.0"}` — это нативный
  модуль (node-gyp / node-pre-gyp). Готовых armv7-бинарников у него нет, то есть
  на устройстве он либо компилируется (отсюда `build-essential python3` в
  `scripts/07-nodered.sh:40`), либо тихо пропускается как optional.
- **node-red 4.1.13**: `optionalDependencies: {"@node-rs/bcrypt":"1.10.7"}` —
  napi-модуль с платформенными подпакетами; armv7-вариант
  `@node-rs/bcrypt-linux-arm-gnueabihf` в npm существует (проверено:
  `dist-tags` → `{"latest":"1.10.7"}`).
- В обоих случаях **обязательная** зависимость — чистый JS `bcryptjs`
  (3.1.15: `2.4.3`; 4.1.13: `3.0.3`), то есть нативный bcrypt — только ускоритель.
- Других нативных пакетов в графе зависимостей не обнаружено — deps.dev
  показывает только семейство bcrypt. Это качественное наблюдение по содержимому
  графа; от точного числа узлов оно не зависит.

**Практический вывод: собирать payload командой с `--omit=optional`** — тогда
дерево полностью JS-ное, компиляции на устройстве нет вообще, и payload не
привязан к ABI конкретного мажора Node. Цена — bcrypt в `adminAuth` работает на
JS-реализации (медленнее при логине, функционально эквивалентно). Это
предположение о цене, не измерение.

### Размер артефакта

Точный размер без реальной armv7-сборки **не установлен**. Приводится не точка,
а **интервал между двумя измеренными границами** — обе получены без обращения к
числу пакетов в дереве.

**Нижняя граница — измерена напрямую.** Два самых больших пакета скачаны с
registry.npmjs.org и промерены в этой сессии (`gzip -t` — целостность
подтверждена, `tar tzv` — суммы совпали с `dist.unpackedSize`/`fileCount` из
метаданных реестра):

| Пакет 4.1.13 | `.tgz` (сжат) | Распакованными | Файлов | Сжатие |
|---|---|---|---|---|
| `@node-red/editor-client` | 9 348 021 B | 34 586 319 B | 306 | 3,70× |
| `@node-red/nodes` | 622 192 B | 2 846 443 B | 606 | 4,57× |
| **вместе** | **≈ 9,97 МБ** | **≈ 37,4 МБ** | 912 | — |

Payload не может быть меньше этого: обе позиции входят в него обязательно, а
всё остальное дерево — сверху.

**Верхняя граница — дельта официальных Docker-образов (сжатый размер, Docker
Hub API).** `nodered/node-red:4.1.13-20-minimal`, `linux/arm/v7` =
103 295 908 B; базовый `node:20-alpine`, `linux/arm/v7` = 45 704 008 B.
Разница ≈ **57 МБ сжатыми**, и это именно верхняя граница: в дельту входят ещё
и обвязка образа, и её системные пакеты.

**Итого: `node-red-4.1.13.tar.gz` — от ≈ 10 до ≈ 57 МБ.** Точку внутри
интервала назвать нечем: для этого нужен реальный `npm install` на armv7.
Занимаемое место на диске устройства после распаковки — **не менее 37 МБ**
(измеренный минимум выше); верхняя граница **не установлена**, поскольку
Docker Hub публикует только сжатые размеры. Для сравнения — уже вендоримый
MPLC4 ≈ 19 МБ (`scripts/09-mplc.sh`, `docs/vendor-integrations.md`).

Node.js tarball (официальный, nodejs.org):

| Версия | `.tar.xz` | `.tar.gz` |
|---|---|---|
| `node-v20.20.2-linux-armv7l` | 22 МБ | 43 МБ |
| `node-v22.23.2-linux-armv7l` | 26 МБ | 52 МБ |

### Нужно ли вендорить сам Node.js

**Да, для полноты — но не в текущем сценарии.**

- Ни один другой шаг установщика Node.js не ставит: grep по `scripts/` даёт
  упоминания `nodesource`/`node`/`npm` только в `scripts/07-nodered.sh`
  (и в dev-инструментах `scripts/dev/`). До шага 07 (`install.sh:117-119`)
  отрабатывают: `01-system.sh`, `02-network.sh`, `03-webserver.sh`,
  `04-flasher.sh`, `05-cloud-agent.sh` (безусловно, `install.sh:91-95`) и
  `10-rs485-roster.sh` (тоже безусловно, `install.sh:97` — несмотря на номер,
  он идёт до 07), затем опциональные `05-mqtt.sh` (`:107-109`) и
  `06-gateway.sh` (`:112-114`). Это полный перечень шагов до 07, и Node.js не
  ставит ни один из них (в `10-rs485-roster.sh` вхождений `node`/`npm` — 0). Node.js на устройство приносит именно
  официальный инсталлятор Node-RED — то есть **Node не гарантирован ничем, кроме
  шага 07**.
- В `etc/` Node-RED — единственный потребитель Node.js (grep по `etc/`: только
  `sa02m-web-service-ctl.sh` в контексте Node-RED). Значит смена мажора Node
  ничего больше на устройстве не ломает.
- `nodered_install_offline()` уже реализует правильную политику: Node-tarball
  распаковывается **только если `node` отсутствует** — на текущих устройствах с
  Node 20.19.1 он не тронется. Поэтому пин Node-RED 4.1.13 можно вкатить, не
  трогая Node вообще, а Node-tarball класть в payload как страховку для чистых
  образов.

### Стоимость по размеру репозитория: ноль

Существующий паттерн вендоринга **не кладёт бинарники в git**:

- `.gitignore:37-41` — `/vendor/` игнорируется целиком, с комментарием
  «Проприетарные бинарники не коммитим — они лежат локально на build-host».
- `scripts/09-mplc.sh:31-39` ищет payload по трём приоритетам:
  `$SA02M_MPLC_DIR` → `/opt/vendor-installers/mplc4` → `$REPO/vendor/mplc4`,
  и при отсутствии **корректно пропускает шаг с `exit 0`** (строки 41-46), не
  роняя установку.
- `tools/debian-rootfs/create-sa02m-rootfs.sh:299-333` копирует в rootfs →
  `/opt/vendor-installers/<sub>` **два жёстко перечисленных каталога**:
  `for sub in codesys mplc4` (строка 310). Не `vendor/*` — расширение перечня
  под Node-RED требует правки этого цикла (и условия на строке 307), см. врезку
  в разделе «Что сейчас в репозитории».

**Тот же паттерн подходит для Node-RED один-в-один**, и рантайм-половина уже
готова (`nodered_install_offline` читает `/opt/vendor-installers/nodered`) —
не хватает трёх шагов из списка выше, включая строку в сборщике rootfs.
Разница только в лицензии: Node-RED — Apache-2.0, а не vendor-EULA, поэтому
payload формально *можно* коммитить. Но десятки МБ бинарного tar в git (по
интервалу выше — от ≈10 до ≈57 МБ) остаются в истории навсегда;
последовательнее оставить его в gitignored `vendor/nodered/` и в rootfs-образе,
как CODESYS и MPLC4. **Прирост размера git-репозитория — 0 байт; прирост
образа rootfs — ≈ 10-57 МБ** (архив дерева Node-RED), плюс ≈ 22 МБ, если
класть рядом `node-v20.20.2-linux-armv7l.tar.xz`. В образе payload лежит
архивами; распаковка происходит уже на устройстве при установке.
