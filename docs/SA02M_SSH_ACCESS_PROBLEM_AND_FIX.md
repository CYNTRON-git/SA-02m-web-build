# Проблемы доступа по SSH (SA-02m) — причины и устранение

Краткая фиксация для репозитория: что наблюдалось на **рабочей** плате при нормальной работе на **тестовой**, и какие меры сняли симптомы.

## 1. Долгое установление соединения (задержка до приглашения, не обязательно «зависание»)

**Причина:** OpenSSH мог ждать обратный DNS (lookup по IP клиента).

**Устранение:**

- В `/etc/ssh/sshd_config`: `UseDNS no`
- В `/etc/hosts`: корректное имя хоста (например `SA-02`, `127.0.0.1 localhost SA-02`), чтобы не дергать лишние резолверы

## 2. Сессия зависает после успешной аутентификации (ключ проходит, канал не открывается)

**Причины (несколько, суммарно):**

| Источник | Механизм |
|----------|----------|
| **MOTD** (`/etc/update-motd.d/*`, в т.ч. `30-armbian-sysinfo`) через **`pam_motd`** | При каждом входе по SSH выполнялись скрипты с опросом железа/сенсоров; на рабочей плате это приводило к подвисаниям при открытии сессии. |
| **PAM `pam_systemd`** в `common-session` | Перегрузка/блокировки вокруг `systemd-logind` — типичный сценарий «вошёл по ключу — и тишина». |
| **Агрессивный опрос RTC / I2C из веб-CGI** (`status.cgi` и связанные цепочки) | Повторяющиеся `new_device` / шум `EBUSY`, нагрузка на шину и смежные подсистемы на фоне уже тяжёлого логина. |
| **Ранний опрос I2C** (`ca_02m.sh` и т.п.) без жёстких таймаутов | Конкуренция за I2C, в логах встречалось «I2C bus locked». |

**Устранение (направления):**

- Сделать скрипты в **`update-motd.d`** неисполняемыми (`chmod -x`) и/или **отключить `pam_motd` для `sshd`** в `/etc/pam.d/sshd`
- В **PAM**: убрать или закомментировать **`pam_systemd.so`** в сессии, где он провоцирует зависание; **`pam_loginuid`** для `sshd` при необходимости перевести в **`optional`**
- **CGI RTC:** guards, автопроба шины без безусловных повторных `new_device`, не дергать I2C в hot path без необходимости
- **`ca_02m`:** таймауты на `i2cget` / отключение автозапуска сервиса на время диагностики
- Дополнительно при разборе отключали/маскировали лишние сервисы (**mplc/mplc4, klogic**, тяжёлые armbian-monitor и др.), чтобы снять фоновую конкуренцию за шину и D-Bus

## 3. Полное зависание устройства (пропадает пинг, гаснет линк) при отладке по SSH

**Причина:** как правило не «неправильный ключ», а **класс команд**: потоковые **`journalctl -f`**, **`dmesg -w`**, массовые вызовы **`systemctl list-units`** и т.п. — на наблюдавшейся связке это уводило ядро/D-Bus в тупик.

**Устранение (правила работы):**

- Одноразовые команды с **таймаутом**, **без** долгих потоков логов по SSH
- Диагностика при недоступном SSH — через **веб** (`ssh_debug.cgi`, расширенные секции по периферии/сервисам/PAM/сети)
