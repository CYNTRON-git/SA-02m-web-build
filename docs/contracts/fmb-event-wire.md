# Контракт: провод событий Fast Modbus (шов с прошивкой MR-02m)

Домашний адрес контракта между мостом `sa02m-modbus-mqtt` и прошивками
модулей на шине RS-485 в части Fast Modbus (FC 0x46): форма кадра
`configure_events` (0x18) и грамматика записей события (0x11). Машинная
грамматика — на английском (`PROTOCOL.md` invariant 5); прозаические
пояснения — на русском.

Ключевой инвариант: **поколение формата определяет рукопожатие, а не догадка
парсера.** Обе грамматики валидируют длину точно, но длина не различает их
однозначно (§4); авторитетным считается контракт, подтверждённый ответом на
`configure_events`, и он кешируется на адрес слейва.

Сторона прошивки отсюда не проверяема: репозитории `CYNTRON-git/MR-02m` и
CE-02m-3 не объявлены в `.ai-dev/components.json`, поэтому всё, что ниже
помечено «не проверено», записано как непроверенное, а не как факт. Для
СЭ-02м-3 опорой служат эталонные кадры с CRC от команды СЭ
(CYNTRON-git/SA-02m-web-build#193) и снятые на стенде 1.135 (2026-09-29).

## 1. Два поколения `configure_events` (0x18)

Оба кадра — unicast, `[ADDR][0x46][0x18][DATA_LEN]…[CRC_L][CRC_H]`.

```text
legacy (build_fmb_configure_events):
  DATA_LEN = 5
  [TYPE int][REG_H][REG_L][COUNT][SETTING]
  TYPE int = внутренний код FMB_EVT_*: 0 COIL, 1 DISCRETE, 2 HOLDING,
             3 INPUT, 0x0F REBOOT; один SETTING на весь диапазон.

WB (build_fmb_configure_events_wb, эталон wb-mqtt-serial):
  DATA_LEN = 4 + COUNT
  [TYPE wire][REG_H][REG_L][COUNT][SETTING × COUNT]
  TYPE wire = внутренний код + 1: 1 COIL, 2 DISCRETE, 3 HOLDING, 4 INPUT,
             0x0F REBOOT (не сдвигается); отдельный SETTING на каждый регистр.
```

Ответ одной формы для обеих: `[ADDR][0x46][0x18][MASK_LEN][MASK…][CRC]`,
перед кадром возможны рецессивные байты арбитража. По WB-контракту `MASK` —
состояние ПОСЛЕ применения: бит на регистр (1 = событие включено),
`ceil(COUNT/8)` байт на диапазон, младший бит первым, каждый диапазон с
границы байта. Кадр с ошибочной записью не применяется целиком и остаётся без
ответа.

```text
WB subscribe 510..513 LOW, addr 14:  0E 46 18 08 04 01 FE 04 01 01 01 01 44 62
reply to 510/4 + 500/3 in one frame: 0E 46 18 02 0F 07 6B A8
WB unsubscribe (SETTING 0):          reply 0E 46 18 02 00 00 2F 9A
```

Что мост считает подтверждением:

- **СЭ-02м-3, WB** — только маску: CRC ответа верен и каждый запрошенный бит
  совпадает с запрошенной настройкой (биты выравнивания за `COUNT` не
  сравниваются). Нет ответа, короткий ответ, битый CRC или несовпавший бит —
  диапазон не применён, остаётся на классическом опросе; в журнале — увиденная
  маска и ожидаемая.
- **MR-02m, WB** — пока префикс `[ADDR][0x46][0x18]`, маска не проверяется:
  соответствие маски MR-02m контракту на стенде не подтверждено.
- **legacy (любой тип)** — префикс: legacy-прошивки маску не возвращают.

Кто какую форму принимает:

| Прошивка | legacy | WB |
|---|---|---|
| MR-02m ветки `feat/wb-event-wire` | отвергает | принимает |
| MR-02m ~1.0.10.4x (multi-record) | принимает | **не проверено** |
| MR-02m ≤ 1.0.10.38 | принимает | не отвечает (наблюдение стенда 136) |
| ДТВ | принимает | **не проверено, не пробуется** (§3) |
| СЭ-02м-3 ≥ 1.0.6.13 | `COUNT > 1` — отвергает без ответа, устройство живо (стенд 1.135, fw 1.0.7.5) | принимает, отвечает маской |
| СЭ-02м-3 ≤ 1.0.6.12 | опасно — §3 | опасно — §3 |

## 2. Порядок попыток и источник истины

1. `ce02m3` — только по версии прошивки (§3); кеш поколения на выбор формы
   для СЭ не влияет.
2. Известный контракт слейва (из предыдущего подтверждённого ACK) — первым.
3. Неизвестный слейв типа `mr02m`: WB, затем legacy.
4. Подтверждённый ACK записывает контракт в кеш поколения (на адрес).
5. Кеш сбрасывается на событии REBOOT (0x0F) и при регистрации устройства:
   модуль мог быть перепрошит из вкладки «Устройства RS-485» без рестарта
   моста. По той же причине REBOOT сбрасывает и прочитанную версию прошивки
   СЭ — следующий `configure_events` решается по версии, которая работает
   сейчас.

Цена неподтверждённого WB-зонда — один тайм-аут ACK (0.4 с) на диапазон
(`fmb_send_recv(frame, 5, 48, 0.4)`). Для слейва, который в итоге отвечает,
она платится только до первого успешного рукопожатия.

**Слейв, не подтверждающий НИ одну форму** (offline MR-02m), рукопожатия не
достигает никогда — для него удвоенный тайм-аут платится на КАЖДОМ проходе:
`configure_all` делает 3 попытки со сном 0.5 с, то есть при 2 диапазонах
`3×(2×0.4)+2×0.5 = 3.4 с` до релиза 1.0.5.50 и `3×(2×0.8)+2×0.5 = 5.8 с`
после — **+70 % к худшему залипанию порта**. Повтор после неудачного прохода
эскалирует (с 1.0.6.51): первый — через `FMB_RECONFIGURE_BACKOFF_S = 15 с`,
дальше окно удваивается на каждом неудачном проходе до
`FMB_UNSUPPORTED_BACKOFF_MAX_S = 15 мин` — слейв, который отвечает на
классический опрос, но никогда не подтверждает `configure_events`, стоит не
больше одного прохода в 15 мин, а не каждые 15 с (стенд 1.135, COM2,
`ce02m3-COM2-14`: было ~3.4 с из каждых 15 с шины и 1673 строки журнала в
час). Построчное «rejected» — WARNING только на первом неудачном проходе,
дальше DEBUG. Событие REBOOT (0x0F) и успешное рукопожатие сбрасывают окно:
следующий проход — сразу. Проход, в котором по правилу §3 не отправлено ни
одного `0x18` (СЭ с неизвестной или опасной прошивкой), тоже считается
неудачным: версия переспрашивается не чаще одного раза за окно, повторных
попыток со сном внутри прохода нет, причина пишется в журнал один раз.
Проверка — `py-unit`: `TestManagerUnsupportedBackoff` (legacy-ДТВ, которая
никогда не подтверждает), `TestManagerUnsupportedBackoffCeWb` (СЭ на WB,
маска не подтверждается), `TestManagerCeBlockedWireBackoff` (СЭ без `0x18`).
Порт разделяется с MPLC4, флешером и
MQTT-мостом по протоколу port lease (`docs/agent-rules/sa02m-domain.md`), так
что это залипание видно соседям по шине. Смягчение — ключ
`fmb_event_wire: legacy` на заведомо старом устройстве.

Ключ устройства `fmb_event_wire: auto | wb | legacy`
(`/etc/sa02m-modbus-mqtt.yaml`) перекрывает выбор: `auto` (умолчание) — по
таблице §3; `wb` — WB, затем legacy, на любом типе и без учёта версии
прошивки СЭ; `legacy` — только legacy, WB никогда. Нераспознанное значение
трактуется как `auto`. Явный ключ — решение оператора: на СЭ ≤ 1.0.6.12 он
снимает защиту §3.

## 3. Какую форму получает каждый тип при `auto`

| Тип | Форма `configure_events` | Основание |
|---|---|---|
| `mr02m` | WB, при молчании — legacy; подтверждённая форма кешируется (§2) | ветка `feat/wb-event-wire` принимает только WB, старые релизы — только legacy |
| `ce02m3`, прошивка ≥ 1.0.6.13 | только WB, подтверждение — по маске (§1) | с 1.0.6.12 СЭ на WB-проводе; legacy с `COUNT > 1` отвергается без ответа |
| `ce02m3`, прошивка ≤ 1.0.6.12 или неизвестна | `0x18` не отправляется вовсе; события не включаются, работает классический опрос; причина — одна строка в журнале | клин верхнего порта, ниже |
| `dtv` | только legacy | ДТВ WB-провод не получала; риск без пользы |

**Версия прошивки СЭ** — holding 320..323 = (major, minor, patch, build).
Читается один раз в `setup()` — до прогрева и до любого `0x18`, одна FC03×4 на
устройство, на пути опроса не бывает. Неудачное или короткое чтение
оставляет версию неизвестной; её переспрашивают перед следующим проходом
`configure_events` (не чаще окна отсрочки §2). Событие REBOOT версию
сбрасывает (§2, п. 5).

**Клин верхнего порта (причина — прошивка СЭ, найдена командой СЭ).** В СЭ
до 1.0.6.12 включительно `0x18`, пришедший на верхний порт, отвечался через
порт торцевого разъёма, а приёмник верхнего порта больше не включался: порт
глух до передёргивания питания, сторожевые таймеры довольны, самосброса нет.
1.0.6.11 принимала legacy-запись с `COUNT` 3/4 и клинилась на каждой;
1.0.6.12 отвергает legacy-запись с `COUNT > 1` без ответа (без клина), но
клинится на записи с `COUNT == 1`; с 1.0.6.13 ответ уходит в тот порт, откуда
пришёл запрос. Поэтому для СЭ ниже 1.0.6.13 безопасной формы нет вовсе, и
legacy-откат здесь — ровно опасный случай.

Случай 2026-07-23 на COM2 (`CHANGELOG.md` § 1.0.5.46, `f6c11646`) — это
legacy-запись: WB-кадр появился в мосте только в 1.0.5.50 (`a5d2b998`).
Время отправки причиной не было — запрос после прогрева клинил 1.0.6.11 так
же. Шлюз `classic_ready_for_fmb` (отправка только после успешного
классического опроса) остаётся, он безвреден, но исправлением клина не
является; по выводу команды СЭ он, вероятно, совпал с перепрошивкой
устройства (версию тогда не записали).

**События мощности на СЭ ≥ 1.0.7.6.** Там по умолчанию включены события
P/Q/S/f/PF (INPUT 518..546). Мост на них не подписывается: это пары int32, а
32-битное значение приходит двумя 2-байтовыми записями (младшее слово по
младшему адресу) в одном кадре; слово без пары означает перечитывание через
FC04 — они и так читаются классическим блоком 500..547. Поэтому после
каждого прохода, в котором подтверждён хоть один WB-диапазон (то есть после
регистрации и после REBOOT), мост шлёт WB-диапазон INPUT 518, `COUNT` 29,
`SETTING` 0 и ждёт нулевую маску. Отказ или молчание не мешают событиям U/I:
WARNING один раз, дальше DEBUG; диспетчер записи 518+ всё равно отбрасывает.
Ниже 1.0.7.6 этот кадр не отправляется.

## 4. Грамматики записей события (0x11) и их коллизии

Кадр: `[SLAVE][0x46][0x11][FLAG][N][DATA_LEN]{records}[CRC_L][CRC_H]`;
записи разбираются из `buf[6 .. 6+DATA_LEN-1]`, число записей = `N`.

```text
legacy record: [TYPE int][REG_H][REG_L][VALUE big-endian, длина по типу]
               COIL/DISCRETE 1 B, HOLDING/INPUT 2 B, REBOOT 0 B
WB record:     [LEN][TYPE wire][ID_H][ID_L][VALUE little-endian × LEN]
               wire 1/2 → LEN 1, wire 3/4 → LEN 2, wire 0x0F → LEN 0
```

Порядок байтов значения различается (BE против LE) — перепутанный даёт не
ошибку, а значение, уехавшее на порядки; пин — тест
`opt/sa02m-modbus-mqtt/tests/test_fmb_event_parsers.py`.

**Коллизии (проверены перебором, а не рассуждением):**

- WB-reboot `[00][0F][ID_H][ID_L]` — валидная legacy-запись `COIL, reg =
  0x0Fxx` той же длины. Коллизия не ограничена одиночной записью: в кадре
  `02 04 01 93 34 02 | 00 0F 00 05` (AI-значение + reboot) legacy-грамматика
  сходится по длине точно, потому что старший байт значения AI работает как
  код типа следующей legacy-записи.
- **Правило reboot (решающее).** Если кадр разбирается WB-грамматикой И
  содержит запись REBOOT — он читается как WB, **независимо от позиции этой
  записи в кадре и от кеша поколения**. Основание — шлюзовое свойство ниже:
  подлинный legacy-кадр не проходит WB-грамматику уже на ПЕРВОЙ записи, при
  любом числе записей и при любой первой записи, которую он может нести
  (включая legacy-reboot). Цена ошибки несимметрична: при потерянном reboot
  перепрошитый модуль теряет таблицу событий навсегда — `fmb_dispatch`
  отбросил бы запись по диапазону регистров, `configured` остался бы `True`,
  и в журнале не было бы ни одной строки. Пины —
  `test_wb_reboot_wins_over_legacy_cache`,
  `test_wb_reboot_wins_when_it_is_not_the_first_record`,
  `test_wb_reboot_wins_from_the_middle_of_a_frame`; обратная сторона (кадр
  подлинно legacy с legacy-reboot по-прежнему читается как legacy) —
  `test_rule_does_not_hijack_a_genuine_legacy_reboot_frame` (reboot второй
  записью) и `test_legacy_reboot_standing_first_is_not_hijacked` (первой, по
  всем 256 старшим байтам регистра).
- На двух записях коллизии есть и без reboot по типам (пары legacy-типов
  `(1,2) (1,3) (2,2) (2,3)`; пары WB-проводов с `0x0F`). Поэтому «длина
  сошлась точно» — не признак поколения, и вне правила reboot решает только
  подтверждённый контракт.

**Латентный инвариант, на котором держится безопасность автоопределения.**
WB-парсер принимает запись, только если её ВТОРОЙ байт — код провода
(`{1,2,3,4,0x0F}`), а ПЕРВЫЙ равен длине полезной части этого провода
(`wire_plen`). У legacy-записи это байт типа и старший байт регистра. Все пары
`(тип, старший байт регистра)`, с которых подлинный legacy-кадр может
НАЧАТЬСЯ, — это пары настраиваемых диапазонов (сегодня
`[(0,0), (2,0), (3,0), (3,1), (3,2)]`) **плюс reboot**, который диапазоном не
является, но первой записью стоять может, а его регистр ничем не ограничен
(значит все 256 старших байтов). **Ни одна из этих пар не проходит шлюз**
(reboot — потому что ни один провод не несёт 15-байтовую полезную часть).
Отсюда: такой кадр падает на ПЕРВОЙ записи, а значит не проходит
WB-грамматику целиком — при любом числе записей.

Пределы по типам (лимит = наименьший регистр, с которого столкновение
становится возможным): COIL — `0x0F00`, DISCRETE — **`0x0100`**, HOLDING —
`0x0300`, INPUT — предела нет (ни один провод не несёт 3-байтовую полезную
часть, поэтому INPUT-запись шлюз не проходит никогда). **Инвариант ломается,
как только появится модуль с событиями COIL ≥ 0x0F00, DISCRETE ≥ 0x0100 или
HOLDING ≥ 0x0300.** Заметьте: «старший байт регистра мал» — не то же самое,
что инвариант, и как факт неверно: СЭ-02м-3 INPUT 510..513 даёт старший байт
`0x02`; держит именно шлюзовое свойство, а не граница диапазона.

Закреплено тестами
`test_no_first_record_a_legacy_frame_can_carry_satisfies_the_wb_gate`
(шлюзовое свойство — общее, для любого числа записей; корпус включает reboot
по всем 256 старшим байтам) и
`test_configured_ranges_stay_below_their_collision_limit` (читаемое следствие
по типам). Их падение — сигнал «автоопределение больше не безопасно», а не
«поправьте тест». Корпусный тест
`test_single_record_legacy_frames_never_satisfy_wb_grammar` перебирает **только
одиночные записи** — сам по себе он общего случая НЕ доказывает и оставлен как
конкретный регресс-пин.

**Второй незаписанный инвариант: `COUNT ≥ 2`.** При `COUNT == 1` WB- и
legacy-кадры `configure_events` совпадают по длине и различаются только
байтом типа, то есть старая прошивка может ПОДТВЕРДИТЬ WB-кадр и настроить
события не того типа. Сегодня ни одна карта диапазонов не даёт `COUNT == 1`;
инвариант запинен у источника — `test_configured_ranges_never_yield_count_one`
перебирает `all_event_ranges()` (все `MR02M_MODULE_TYPES`, ДТВ, СЭ); саму
неотличимость двух форм при `COUNT == 1` пинит
`test_count_one_differs_only_in_the_type_byte`.

## 5. Что контракт не меняет

Всё правее `_dispatch` — топики MQTT, имена контролов, форматы и единицы
значений — прежнее байт-в-байт (`docs/MQTT_TOPICS.md` § «Fast Modbus
события»). Неразобранный кадр даёт ноль событий (fail-closed), диапазон без
подтверждения остаётся на классическом опросе.
