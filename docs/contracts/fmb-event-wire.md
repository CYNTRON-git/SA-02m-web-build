# Контракт: провод событий Fast Modbus (шов с прошивкой MR-02m)

Домашний адрес контракта между мостом `sa02m-modbus-mqtt` и прошивками
модулей на шине RS-485 в части Fast Modbus (FC 0x46): форма кадра
`configure_events` (0x18) и грамматика записей события (0x11). Машинная
грамматика — на английском (`PROTOCOL.md` invariant 5); прозаические
пояснения — на русском.

Ключевой инвариант: **поколение формата определяет рукопожатие, а не догадка
парсера.** Обе грамматики валидируют длину точно, но длина не различает их
однозначно (§4); авторитетным считается контракт, подтверждённый ответом на
`configure_events`, и он кешируется на адрес слейва.

Формат MR-02m проверен по объявленному компоненту `../MR-02m`, ревизия
`f3c5c6998c093519cba135a746ee053e140818e9`: обработчик
`shared/modbus/src/modbus_rtu_fc46_events.c`, `handle_fc46_set_event_priorities`
(shared/modbus `04ddc1ef6ab80d15f03292611ed2809cfa04f371`). Старый ACK проверен
по `shared/modbus/src/modbus_rtu_hw.c` той же библиотеки в ревизии
`fa37f21864e8984d8e4532fb3bdc24a7bf6fbbc7`. Проверка исходников не заменяет
проверку обмена с конкретной версией на стенде. Для СЭ-02м-3 опорой служат
эталонные кадры с CRC от команды СЭ
(CYNTRON-git/SA-02m-web-build#193) и снятые на стенде 1.135 (2026-09-29).

## 1. Два поколения `configure_events` (0x18)

Оба кадра — unicast, `[ADDR][0x46][0x18][DATA_LEN]…[CRC_L][CRC_H]`.

```text
legacy (build_fmb_configure_events):
  DATA_LEN = 5
  [TYPE int][REG_H][REG_L][COUNT][SETTING]
  TYPE int = внутренний код FMB_EVT_*: 0 COIL, 1 DISCRETE, 2 HOLDING,
             3 INPUT, 0x0F REBOOT; один SETTING на весь диапазон.

WB (build_fmb_configure_events_wb, эталон wb-mqtt-serial):
  DATA_LEN = 4 + COUNT
  [TYPE wire][REG_H][REG_L][COUNT][SETTING × COUNT]
  TYPE wire = внутренний код + 1: 1 COIL, 2 DISCRETE, 3 HOLDING, 4 INPUT,
             0x0F REBOOT (не сдвигается); отдельный SETTING на каждый регистр.
```

Оболочка ответа общая: `[ADDR][0x46][0x18][DATA_LEN][DATA…][CRC]`,
перед кадром возможны рецессивные байты арбитража. В legacy `DATA_LEN=1`,
`DATA=00` означает `flags=OK`, а не маску регистров. В WB `DATA` — маска
`MASK`. По WB-контракту `MASK` — состояние ПОСЛЕ применения: бит на регистр
(1 = событие включено),
`ceil(COUNT/8)` байт на диапазон, младший бит первым, каждый диапазон с
границы байта. Кадр с ошибочной записью не применяется целиком и остаётся без
ответа.

```text
WB subscribe 510..513 LOW, addr 14:  0E 46 18 08 04 01 FE 04 01 01 01 01 44 62
reply to 510/4 + 500/3 in one frame: 0E 46 18 02 0F 07 6B A8
WB unsubscribe (SETTING 0):          reply 0E 46 18 02 00 00 2F 9A
```

Что мост считает подтверждением:

- **WB, любой тип устройства** — только маску: адрес, функция и подфункция
  совпадают с запросом; кадр полный, CRC ответа верен, длина маски точная и
  каждый запрошенный бит совпадает с запрошенной настройкой (биты выравнивания за `COUNT` не
  сравниваются). Нет ответа, короткий ответ, битый CRC или несовпавший бит —
  применение диапазона не подтверждено, он остаётся на классическом опросе;
  в журнале — увиденная маска и ожидаемая.
- **legacy (любой тип)** — полный ответ соответствующего адреса с верным CRC
  и ровно одним байтом `00` (`flags=OK`). Префикс, ненулевой флаг, пустые данные
  или иной размер подтверждением не считаются. Маску WB к legacy не применяют.

Проверка маски действует и при явном `fmb_event_wire: wb` на ДТВ.
Повреждённый ответ не меняет кеш поколения.
Ответ `0x18` не содержит адреса диапазона и номера транзакции: корреляция
ограничена текущим запросом, адресом слейва и формой ответа. Для `COUNT ≤ 8`
нулевая WB-маска побайтно совпадает с legacy `flags=OK`; отдельный корректный
legacy-ответ при откате подтверждает старый формат, но не WB-подписку.

Кто какую форму принимает:

| Прошивка | legacy | WB |
|---|---|---|
| MR-02m ревизии из введения | `COUNT > 1` — отвергает | принимает, отвечает маской после применения |
| MR-02m ~1.0.10.4x (multi-record) | принимает | **не проверено** |
| MR-02m ≤ 1.0.10.38 | принимает | не отвечает (наблюдение стенда 136) |
| ДТВ до 1.0.1.49 | принимает | в автоматическом режиме используется legacy |
| ДТВ с 1.0.1.49 | старый запрос с общей настройкой диапазона отвергается | принимает, отвечает маской |
| СЭ-02м-3 ≥ 1.0.6.13 | `COUNT > 1` — отвергает без ответа, устройство живо (стенд 1.135, fw 1.0.7.5) | принимает, отвечает маской |
| СЭ-02м-3 ≤ 1.0.6.12 | опасно — §3 | опасно — §3 |

## 2. Порядок попыток и источник истины

1. В режиме `auto` СЭ и ДТВ выбирают форму по четырём регистрам версии прошивки (§3).
2. Известный контракт слейва (из предыдущего подтверждённого ACK) — первым.
3. Неизвестный слейв типа `mr02m`: WB, затем legacy.
4. Подтверждённый ACK записывает контракт в кеш поколения (на адрес).
5. Кеш сбрасывается на событии REBOOT (0x0F) и при регистрации устройства:
   модуль мог быть перепрошит из вкладки «Устройства RS-485» без рестарта
   моста. По той же причине REBOOT сбрасывает и прочитанную версию прошивки
   СЭ и ДТВ — следующий `configure_events` решается по версии, которая работает
   сейчас.

Цена неподтверждённого WB-зонда — один тайм-аут ACK (0.4 с) на диапазон
(`fmb_send_recv(frame, 5, 48, 0.4)`). Для слейва, который в итоге отвечает,
она платится только до первого успешного рукопожатия.

Частичный ACK разрешает доставку событий подтверждённых диапазонов. До
подтверждения всех диапазонов классический опрос устройства сохраняет
обычную частоту. При следующей попытке мост запрашивает оставшиеся диапазоны.

**Слейв, не подтверждающий НИ одну форму** (offline MR-02m), рукопожатия не
достигает никогда — для него удвоенный тайм-аут платится на КАЖДОМ проходе:
`configure_all` делает 3 попытки со сном 0.5 с, то есть при 2 диапазонах
`3×(2×0.4)+2×0.5 = 3.4 с` до релиза 1.0.5.50 и `3×(2×0.8)+2×0.5 = 5.8 с`
после — **+70 % к худшему залипанию порта**. Повтор после неудачного прохода
эскалирует (с 1.0.6.51): первый — через `FMB_RECONFIGURE_BACKOFF_S = 15 с`,
дальше окно удваивается на каждом неудачном проходе до
`FMB_UNSUPPORTED_BACKOFF_MAX_S = 15 мин` — слейв, который отвечает на
классический опрос, но никогда не подтверждает `configure_events`, стоит не
больше одного прохода в 15 мин, а не каждые 15 с (стенд 1.135, COM2,
`ce02m3-COM2-14`: было ~3.4 с из каждых 15 с шины и 1673 строки журнала в
час). Построчное «rejected» — WARNING только на первом неудачном проходе,
дальше DEBUG. Событие REBOOT (0x0F) и успешное рукопожатие сбрасывают окно:
следующий проход — сразу. Проход, в котором по правилу §3 не отправлено ни
одного `0x18` (СЭ с неизвестной или опасной прошивкой), тоже считается
неудачным: версия переспрашивается не чаще одного раза за окно, повторных
попыток со сном внутри прохода нет, причина пишется в журнал один раз.
Проверка — `py-unit`: `TestManagerUnsupportedBackoff` (legacy-ДТВ, которая
никогда не подтверждает), `TestManagerUnsupportedBackoffCeWb` (СЭ на WB,
маска не подтверждается), `TestManagerCeBlockedWireBackoff` (СЭ без `0x18`).
Порт разделяется с MPLC4, флешером и
MQTT-мостом по протоколу port lease (`docs/agent-rules/sa02m-domain.md`), так
что это залипание видно соседям по шине. Смягчение — ключ
`fmb_event_wire: legacy` на заведомо старом устройстве.

Ключ устройства `fmb_event_wire: auto | wb | legacy`
(`/etc/sa02m-modbus-mqtt.yaml`) перекрывает выбор: `auto` (умолчание) — по
таблице §3. Для МР, ДТВ и СЭ режим `wb` допускает WB и повтор в legacy,
а `legacy` выбирает только legacy. На СЭ ≤ 1.0.6.12 явный ключ снимает защиту §3.
Для RGBW тип 120 режим `wb` требует тех же подтверждений, что и `auto`,
и использует только WB. В режиме `legacy` RGBW остаётся на обычном опросе.
Нераспознанное значение трактуется как `auto`.

## 3. Какую форму получает каждый тип при `auto`

| Тип | Форма `configure_events` | Основание |
|---|---|---|
| `mr02m` | WB, без подтверждения — legacy; подтверждённая форма кешируется (§2) | текущий обработчик возвращает WB-маску, старый — legacy `flags=OK` |
| `led`, тип 120 с подтверждённой сигнатурой и HR122 = 1 | только WB с 1.0.2.2 | производители событий и обычные чтения описаны в [контракте RGBW](led-mb2ws.md) |
| `ce02m3`, прошивка ≥ 1.0.6.13 | только WB, подтверждение — по маске (§1) | с 1.0.6.12 СЭ на WB-проводе; legacy с `COUNT > 1` отвергается без ответа |
| `ce02m3`, прошивка ≤ 1.0.6.12 или неизвестна | `0x18` не отправляется вовсе; события не включаются, работает классический опрос; причина — одна строка в журнале | клин верхнего порта, ниже |
| `dtv`, прошивка с 1.0.1.49 | WB | формат WB для подписки и событий введён в 1.0.1.49 |
| `dtv`, старее 1.0.1.49 или версия неизвестна | legacy | сохраняется совместимость со старой прошивкой |

У ДТВ версия читается из HR320–323 перед подпиской. В прошивках 1.0.2.3 и
1.0.2.6 обработчик FC04 формирует события датчиков при чтении INPUT1–28.
Мост подписывается по WB на выбранные каналы INPUT1–22 и на быстрый блок
INPUT25–28. При автоопределении подписка охватывает INPUT1–22, а публикация
начинается после определения состава датчиков. INPUT23/24 (энергия радара)
не имеют MQTT-каналов. Расстояния INPUT29/30 читаются по FC04, состояния
выходов — по FC01. Полный FC04 сохраняется после подтверждения подписки.
Между полными чтениями `poll_presence_s` задаёт интервал для INPUT25–30 и выходов.

FC04 и события используют один формат MQTT. До 1.0.2.4 значение
`tvoc_zmod` равно INPUT19 × 0,01 мг/м³, а `iaq_zmod` содержит индекс
INPUT20 по шкале 0–500. С 1.0.2.4 это INPUT19 × 0,001 мг/м³ и рейтинг
Renesas INPUT20 × 0,01 по шкале 1–5. Если версия неизвестна, каналы с
зависимым от версии масштабом получают ошибку чтения. В версиях с регистром
состава датчиков (с 1.0.1.51) нулевое событие от датчика может означать
отсутствие измерения. Тогда ближайшее классическое чтение проверяет живость
DS18B20/LD2412 (INPUT65516, биты 8/9), режим внешнего датчика HR6 или
готовность ZMOD (INPUT349, бит 7). Для I²C INPUT65516 содержит снимок старта.
Мост читает INPUT65517 после проверки модели `SENSOR` в HR200–206.
INPUT65517 содержит текущую маску живости, когда `(word & 0xFEE0) == 0x8000`.
Слово `0x8000` означает, что свежих выборок нет. При отсутствии такой сигнатуры
или ошибке чтения мост сверяет температуру,
влажность или высоту со второй действительной величиной того же датчика в
одном чтении. Старые прошивки могут вернуть 0 для незадействованного адреса.
Ноль давления или eCO₂, как и измерение с неподтверждённым качеством,
оставляет последнее значение с ошибкой `r`.
Автоопределение сохраняет `0x8000` как значение беззнакового канала WB.
В знаковых каналах и у legacy эта комбинация означает ошибку.
Для PB2 и суммарного присутствия ноль непосредственно означает выключенное
состояние. См. [карту регистров ДТВ](https://github.com/CYNTRON-git/DTV-RS-485/blob/v1.0.2.6/MODBUS_VARIABLES.txt).

**Версия прошивки СЭ** — holding 320..323 = (major, minor, patch, build).
Читается один раз в `setup()` — до прогрева и до любого `0x18`, одна FC03×4 на
устройство, на пути опроса не бывает. Неудачное или короткое чтение
оставляет версию неизвестной; её переспрашивают перед следующим проходом
`configure_events` (не чаще окна отсрочки §2). Событие REBOOT версию
сбрасывает (§2, п. 5).

**Клин верхнего порта (причина — прошивка СЭ, найдена командой СЭ).** В СЭ
до 1.0.6.12 включительно `0x18`, пришедший на верхний порт, отвечался через
порт торцевого разъёма, а приёмник верхнего порта больше не включался: порт
глух до передёргивания питания, сторожевые таймеры довольны, самосброса нет.
1.0.6.11 принимала legacy-запись с `COUNT` 3/4 и клинилась на каждой;
1.0.6.12 отвергает legacy-запись с `COUNT > 1` без ответа (без клина), но
клинится на записи с `COUNT == 1`; с 1.0.6.13 ответ уходит в тот порт, откуда
пришёл запрос. Поэтому для СЭ ниже 1.0.6.13 безопасной формы нет вовсе, и
legacy-откат здесь — ровно опасный случай.

Случай 2026-07-23 на COM2 (`CHANGELOG.md` § 1.0.5.46, `f6c11646`) — это
legacy-запись: WB-кадр появился в мосте только в 1.0.5.50 (`a5d2b998`).
Время отправки причиной не было — запрос после прогрева клинил 1.0.6.11 так
же. Шлюз `classic_ready_for_fmb` (отправка только после успешного
классического опроса) остаётся, он безвреден, но исправлением клина не
является; по выводу команды СЭ он, вероятно, совпал с перепрошивкой
устройства (версию тогда не записали).

**События мощности на СЭ ≥ 1.0.7.6.** Там по умолчанию включены события
P/Q/S/f/PF (INPUT 518..546). Мост на них не подписывается: это пары int32, а
32-битное значение приходит двумя 2-байтовыми записями (младшее слово по
младшему адресу) в одном кадре; слово без пары означает перечитывание через
FC04 — они и так читаются классическим блоком 500..547. Поэтому после
каждого прохода, в котором подтверждён хоть один WB-диапазон (то есть после
регистрации и после REBOOT), мост шлёт WB-диапазон INPUT 518, `COUNT` 29,
`SETTING` 0 и ждёт нулевую маску. Отказ или молчание не мешают событиям U/I:
WARNING один раз, дальше DEBUG; диспетчер записи 518+ всё равно отбрасывает.
Ниже 1.0.7.6 этот кадр не отправляется.

## 4. Грамматики записей события (0x11) и их коллизии

В кадре `[SLAVE][0x46][0x11][FLAG][N][DATA_LEN]{records}[CRC_L][CRC_H]`
поле `DATA_LEN` задаёт точный размер записей. В WB `N` включает все ещё
неподтверждённые события устройства. Переданных записей может быть меньше.
В legacy `N` совпадает с числом записей. Мост проверяет длину, CRC и весь
набор записей перед публикацией. До кадра он пропускает до 32 байтов
арбитража, включая ложные заголовки. Байты после конца кадра нарушают проверку.

Например, `05 46 11 01 02 06 02 04 01 D0 04 00 6B B9` передаёт одно
значение IR464 = 4 при двух событиях в очереди. Если бюджет мал даже для
одной записи, `05 46 11 01 01 00 DC ED` сообщает только размер очереди.
Оба кадра дают следующему запросу подтверждение `05 01`. После одного
ответа без записей мост завершает текущую серию и продолжает по расписанию.
Значения каналов, поколение формата и граница опустошения FIFO сохраняются.
Пустую очередь WB обозначает `0x12`. В обычном опросе СА `0x11` с нулевыми
`N` и `DATA_LEN` отклоняется. [Спецификация WB](https://github.com/wirenboard/wb-modbus-ext-scanner/blob/main/docs/protocol.ru.md)

На встроенном UART при скорости от 57600 бод мост запрашивает до 33 байтов
данных событий. Даже при 12 байтах арбитража и 8 байтах обрамления ответ
занимает до 53 байтов и помещается в приёмный FIFO с запасом на эхо запроса.
При большем числе событий мост подтверждает каждый принятый пакет и
продолжает чтение очереди. Для остальных линий предел данных составляет
128 байтов.

```text
legacy record: [TYPE int][REG_H][REG_L][VALUE big-endian, type-specific length]
               COIL/DISCRETE 1 B, HOLDING/INPUT 2 B, REBOOT 0 B
WB record:     [LEN][TYPE wire][ID_H][ID_L][VALUE little-endian × LEN]
               wire 1..4: LEN 1..8, wire 0x0F: LEN 0
```

Мост декодирует полное значение WB. Для существующих каналов МР, ДТВ, СЭ
и LED он передаёт в MQTT однобайтовые COIL/DISCRETE и двухбайтовые HOLDING/INPUT.
Например, четырёхбайтовая освещённость WB-MSW v3 с IR9 не имеет такого
отображения. Мост учитывает эту запись при подтверждении пакета и передаёт
остальные совместимые значения из того же пакета.

Порядок байтов значения различается (BE против LE) — перепутанный даёт не
ошибку, а значение, уехавшее на порядки; пин — тест
`opt/sa02m-modbus-mqtt/tests/test_fmb_event_parsers.py`.

**Коллизии (проверены перебором, а не рассуждением):**

- WB-reboot `[00][0F][ID_H][ID_L]` — валидная legacy-запись `COIL, reg =
  0x0Fxx` той же длины. Коллизия не ограничена одиночной записью: в кадре
  `02 04 01 93 34 02 | 00 0F 00 05` (AI-значение + reboot) legacy-грамматика
  сходится по длине точно, потому что старший байт значения AI работает как
  код типа следующей legacy-записи.
- **Правило reboot для штатных ширин СА.** Если весь кадр состоит из записей WB
  штатной ширины для каналов СА и
  содержит запись REBOOT — он читается как WB, **независимо от позиции этой
  записи в кадре и от кеша поколения**. Основание — шлюзовое свойство ниже:
  подлинный legacy-кадр не проходит эту проверку уже на ПЕРВОЙ записи, при
  любом числе записей и при любой первой записи, которую он может нести
  (включая legacy-reboot). Цена ошибки несимметрична: при потерянном reboot
  перепрошитый модуль теряет таблицу событий навсегда — `fmb_dispatch`
  отбросил бы запись по диапазону регистров, `configured` остался бы `True`,
  и в журнале не было бы ни одной строки. Пины —
  `test_wb_reboot_wins_over_legacy_cache`,
  `test_wb_reboot_wins_when_it_is_not_the_first_record`,
  `test_wb_reboot_wins_from_the_middle_of_a_frame`; обратная сторона (кадр
  подлинно legacy с legacy-reboot по-прежнему читается как legacy) —
  `test_rule_does_not_hijack_a_genuine_legacy_reboot_frame` (reboot второй
  записью) и `test_legacy_reboot_standing_first_is_not_hijacked` (первой, по
  всем 256 старшим байтам регистра).
- На двух записях коллизии есть и без reboot по типам (пары legacy-типов
  `(1,2) (1,3) (2,2) (2,3)`; пары WB-проводов с `0x0F`). Поэтому «длина
  сошлась точно» — не признак поколения, и вне правила reboot решает только
  подтверждённый контракт.

Если в кадре WB есть записи других ширин, правило reboot не применяется.
При известном формате WB мост декодирует пакет целиком. При формате legacy
он требует полного разбора в legacy. Для неизвестного формата полный валидный
legacy-разбор имеет приоритет перед предположением о расширенной записи WB.
Если для адреса уже установлен WB и начало записей имеет заголовок штатной
ширины WB, ошибка любой записи отклоняет весь пакет. Например, обрыв
`02 04 00 09 01` внутри значения INPUT9 сохраняет прошлое подтверждение.
Для адреса с неизвестным или подтверждённым legacy-форматом те же пять байтов
допускают полный legacy-разбор как HOLDING1024 = 2305.

**Инвариант автоопределения для штатных ширин СА.**
У штатной записи WB второй байт — код провода
(`{1,2,3,4,0x0F}`), а ПЕРВЫЙ равен длине полезной части этого провода
(`wire_plen`). У legacy-записи это байт типа и старший байт регистра. Все пары
`(тип, старший байт регистра)`, с которых подлинный legacy-кадр может
НАЧАТЬСЯ, — это пары настраиваемых диапазонов (сегодня
`[(0,0), (2,0), (3,0), (3,1), (3,2)]`) **плюс reboot**, который диапазоном не
является, но первой записью стоять может, а его регистр ничем не ограничен
(значит все 256 старших байтов). **Ни одна из этих пар не проходит шлюз**
(reboot — потому что ни один провод не несёт 15-байтовую полезную часть).
Отсюда: такой кадр падает на ПЕРВОЙ записи, а значит не проходит
проверку штатных ширин целиком — при любом числе записей.

Пределы по типам (лимит = наименьший регистр, с которого столкновение
становится возможным): COIL — `0x0F00`, DISCRETE — **`0x0100`**, HOLDING —
`0x0300`, INPUT — предела нет (ни одна штатная ширина СА не допускает 3-байтовую полезную
часть, поэтому INPUT-запись шлюз не проходит никогда). **Инвариант ломается,
как только появится модуль с событиями COIL ≥ 0x0F00, DISCRETE ≥ 0x0100 или
HOLDING ≥ 0x0300.** Заметьте: «старший байт регистра мал» — не то же самое,
что инвариант, и как факт неверно: СЭ-02м-3 INPUT 510..513 даёт старший байт
`0x02`; держит именно шлюзовое свойство, а не граница диапазона.

Закреплено тестами
`test_no_first_record_a_legacy_frame_can_carry_satisfies_the_scalar_wb_gate`
(шлюзовое свойство — общее, для любого числа записей; корпус включает reboot
по всем 256 старшим байтам) и
`test_configured_ranges_stay_below_their_collision_limit` (читаемое следствие
по типам). Их падение — сигнал «автоопределение больше не безопасно», а не
«поправьте тест». Корпусный тест
`test_single_record_legacy_frames_never_satisfy_scalar_wb_grammar` перебирает **только
одиночные записи** — сам по себе он общего случая НЕ доказывает и оставлен как
конкретный регресс-пин.

**Второй незаписанный инвариант: `COUNT ≥ 2`.** При `COUNT == 1` WB- и
legacy-кадры `configure_events` совпадают по длине и различаются только
байтом типа, то есть старая прошивка может ПОДТВЕРДИТЬ WB-кадр и настроить
события не того типа. Сегодня ни одна карта диапазонов не даёт `COUNT == 1`;
инвариант запинен у источника — `test_configured_ranges_never_yield_count_one`
перебирает `all_event_ranges()` (все `MR02M_MODULE_TYPES`, ДТВ, СЭ); саму
неотличимость двух форм при `COUNT == 1` пинит
`test_count_one_differs_only_in_the_type_byte`.

## Порядок событий выходов MR после команды

MR-поллер принимает выходное состояние по правилам
[подтверждения команд MQTT](mr-module-control.md#подтверждение-команд-mqtt).
После команды адресованный DO/AO временно получает состояние только из
обычного чтения: старое значение может оставаться в FIFO модуля даже тогда,
когда запрос событий отправлен уже после успешного readback.

Прошивка МР-02м версии 1.0.12.23 формирует событие HOLDING со значением
0 или 1 по адресу канала DO 1–16 (`shared/modbus/src/fast_mb_events.c`,
ревизия `e591faf0a058dc5a8bfd3aaafd26072deeddf30b`). Мост подписывается также на COIL по тем же
адресам для модулей, передающих однобайтовое состояние. Оба формата проходят
общую проверку команды и канала. Выключенный в настройках канал DO, DI, AO
или AI сохраняет состояние MQTT при приходе события.

При равном приоритете арбитраж выигрывает меньший адрес. Чтобы непрерывный
поток младшего модуля не задерживал события старших, после двух последовательных
полных опросов с подтверждённым DATA мост по очереди выставляет адреса подписчиков
выше ответившего как нижнюю границу `min_slave`. В ту же очередь входят
модули, ожидающие собственного `0x12` после записи и успешного чтения.
Между очередными порогами ротации идёт полный опрос от адреса 1. Для модуля с
контрактом WB повтор флага в корректном WB-пакете DATA означает
повтор подтверждения, даже когда новые события вытеснили прежние записи.
Для legacy мост сравнивает весь пакет. При повторе мост один раз выставляет
адрес этого модуля как `min_slave` и передаёт его подтверждение. Так модуль может обработать
подтверждение после победы в арбитраже. Затем мост продолжает ротацию, даже
если пакет повторился снова. Каждый запрос передаёт адрес и флаг последнего
полностью принятого и разобранного DATA. До первого DATA оба поля равны нулю.
Широковещательный ответ WB `FD 46 12 52 5D` и адресный шестибайтовый
ответ МР завершают серию опроса, сохраняя это подтверждение. При пустой шине дополнительные
запросы нужны только модулям, ожидающим собственного `0x12`. Нижняя
граница оставляет все адреса выше неё в арбитраже с обычными приоритетами.
До ответа нужного модуля состояние выхода продолжает обновлять классический опрос.

Менеджер перед UART-запросом снимает необязательный контекст
`fmb_query_context()` и время начала. После освобождения транспорта он
передаёт события через `fmb_dispatch_observed`, если поллер поддерживает этот
метод; остальные поллеры сохраняют трёхаргументный `fmb_dispatch`.
Контекст и доставка не выполняются под блокировкой UART. Старое поколение
команды и запрос, начатый до более нового обычного чтения, не публикуют
выходное значение и не очищают его ошибку. Несколько записей одного канала
внутри принятого пакета сохраняют порядок FIFO.

Карантин канала снимается только после успешного свежего чтения и следующей
подтверждённой границы пустой очереди. Ею является ответ **этого** настроенного
ведомого `0x46/0x12`: ровно шесть байтов после существующей обработки префикса
арбитража, правильный CRC, адрес `1..247` не ниже `min_slave` запроса, бюджет
`max_data >= 6`. Широковещательный ответ WB не указывает владельца очереди.
МР также отвечает адресным `0x12`, если бюджет меньше одной записи. В пределах
сеанса мост учитывает и ранее запрошенный размер: если ответ на широкий
запрос мог потеряться, меньший бюджет сам по себе не доказывает пустоту.
Приём DATA уточняет размер удерживаемой партии. До подтверждения границы
канал обновляет классический опрос. На быстрых UART мост сохраняет предел 33.

У промежуточной прошивки МР 1.0.12.25 при смене мастера могла остаться целая
партия, превышающая начальный бюджет нового мастера. На первый малый запрос она
отвечала тем же адресным `0x12`, что и при пустой очереди. При холодном старте
СА эти состояния по такому ответу неразличимы. В рабочих версиях, выдающих
целые записи в пределах бюджета, для следующей записи достаточно шести байтов.
[Форматы и подтверждения WB](https://github.com/wirenboard/wb-mqtt-serial/blob/master/src/modbus_ext_common.cpp)

Поколение запроса должно совпасть с текущим поколением MR-команд, а начало
запроса — быть строго позже завершения свежего чтения канала. Соседний ведомый,
неизвестный адрес, незавершённое/повреждённое сообщение, лишний суффикс,
пустой пакет `0x11`, таймаут и старый callback карантин не снимают. Перед каждой
транзакцией метаданные результата очищаются. Канал без свежего чтения остаётся
защищённым, даже когда другой канал уже готов.

Обычный опрос сохраняет текущую настроенную периодичность; запросов чтения на
каждое событие и отдельного цикла опустошения FIFO нет. Состояние ограничено
числом выходов/зарегистрированных ведомых. Продолжительный карантин попадает
в ограниченную по частоте диагностику с причиной и возрастом. Протокол FMB
не имеет nonce: защита закрывает локальные гонки и старую FIFO-историю,
не обещает обнаруживать произвольное физическое воспроизведение кадров.

## Отсчёты AI при смене типа датчика

Событие INPUT по адресу `403 + 7*(ch-1)` несёт сырое слово без типа
датчика. После подтверждённой смены типа, включая смену в парном канале и
восстановление при запуске, мост публикует отсчёт из свежего чтения FC03.
Следующие обычные чтения продолжают обновлять канал. Мост возобновляет
публикацию событий канала после корректного ответа о пустой очереди от этого
же модуля, если запрос отправлен после чтения. Та же граница действует, когда
обычный опрос обнаружил изменение типа в регистрах. Другие каналы остаются
доступны для событий.

При первом подключении или после неполного чтения мост сохраняет ошибку
чтения `r`, пока FC03 не подтвердит тип и отсчёт канала. Для парного N это
включает чтение источника P, даже когда его публикация выключена. Код типа
`0` означает выключенный датчик только после чтения регистра. Первый свежий
отсчёт мост публикует сразу. Для перехода на события нужен последующий
ответ этого модуля `0x12` о пустой очереди.

Событие перезагрузки МР сбрасывает подтверждение типа и источника отсчёта
для каждого AI этого адреса. Для него снова требуется чтение FC03 и ответ
его собственной очереди `0x12`. Это относится и к записям измерений,
следующим за событием перезагрузки внутри одного кадра. Чтение или команда
смены типа, начатая до перезагрузки, не может подтвердить отсчёт после неё.
Каналы с незавершённой командой смены типа сохраняют состояние ожидания.

При пересечении запросов мост учитывает время их начала. Запоздалый ответ
из очереди не заменяет свежий отсчёт FC03 или данные после границы FIFO.
Запоздалое чтение FC03 не заменяет отсчёт из более нового запроса событий.
Внутри одного пакета мост обрабатывает отсчёты в порядке записи.

На парном модуле TC-K и трёхпроводные термосопротивления используют отсчёт P
для обеих ног. Событие P обновляет каждый включённый канал пары, в том числе
N при выключенном P. Отдельное событие N в таком режиме пропускается.

## 5. Что контракт не меняет

Всё правее `_dispatch` — топики MQTT, имена контролов, форматы и единицы
значений — прежнее байт-в-байт (`docs/MQTT_TOPICS.md` § «Fast Modbus
события»). Неразобранный кадр даёт ноль событий (fail-closed), диапазон без
подтверждения остаётся на классическом опросе.
