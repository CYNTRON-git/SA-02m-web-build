# Ответы транспорта прошивальщика

`modbus_rtu.find_matching_response()` — общий источник правил проверки ответа
для `serial_port.send_receive()`, `send_receive_tcp()` и `FlasherProtocol`.
Получение некоторого количества байтов само по себе не подтверждает запись
блока: принимается один полный кадр с допустимым CRC и полями текущего запроса.
Независимая проверка в `FlasherProtocol` распространяется и на внедрённый
транспортный callback, который не использует штатные UART/TCP-функции.

## Соответствие запросу

| Запрос | Обязательные поля ответа |
|---|---|
| Стандартный RTU | Тот же адрес и функция; исключение — та же функция с установленным bit 7 |
| FC01/FC02 | Число байтов равно округлённому вверх числу запрошенных битов, делённому на восемь |
| FC03/FC04 | Число байтов равно удвоенному числу запрошенных регистров |
| FC05/FC06 | Тот же адрес элемента и записанное значение |
| FC16 | Тот же начальный регистр и количество регистров |
| FC17 (`0x11`) | Vendor-defined payload с byte count 1–246; содержимое не задаётся этим контрактом |
| FastModbus `FD 46 08` | Ответ `FD 46 09` с тем же серийным номером и теми же правилами для внутреннего PDU |

CRC проверяется до подтверждения обмена. Для обычных успешных FC05/FC06/FC16
и обычных исключений сохраняются оба ранее поддержанных порядка байтов CRC.
Обычные ответы чтения и FastModbus требуют прежний порядок LSB first.
Повреждённое исключение не принимается по одной форме. Полное исключение
возвращается вызывающему как ошибка, а не успех; FastModbus exception занимает
ровно 11 байтов (`7 + 2 + 2`) и не ждёт истечения всего таймаута.

Полный посторонний кадр с корректным CRC пропускается целиком; его payload не
рассматривается как вложенный ACK. Другой адрес, serial, функция, регистр или
количество не продвигает прошивку. Следующий подходящий ответ в том же
ограниченном окне может завершить обмен. Отдельные старые `parse_response()` и
`parse_fast_modbus_response()` сохраняют свои интерфейсы; проверка
соответствия запросу выполняется на описанной выше границе.

## Эхо и пределы ожидания

Вход может содержать ведущее эхо запроса, его произвольную фрагментацию,
фрагменты ответа и ограниченный шум. Полное известное эхо длинного запроса
отбрасывается до поиска ответа. Пока накопленные байты являются только
неполным префиксом такого запроса, они не трактуются как ACK внутри эха.

Для обычных FC05/FC06 корректный ответ идентичен запросу: единственный такой
кадр принимается и без отдельного эха. Программно отличить его от одного
лишь TX-эха невозможно. Редкий FC16 ACK также может целиком совпасть с
восьмибайтовым началом длинного запроса. До получения остальных байтов эха
он остаётся неоднозначным; один такой точный ACK допускается при завершении
исходного окна ожидания (`final=True`). Если продолжение префикса уже пришло,
обрывок не подтверждает обмен. После полного ведущего эха следующий ACK
может завершить обмен сразу. CRC и ACK не доказывают физическую запись Flash.

Буфер обмена ограничен 1024 байтами. UART/TCP читает не больше оставшегося
места плюс один байт для обнаружения переполнения; превышение вызывает явную
ошибку и не продолжает накапливать данные. Ошибка внедрённого callback
возвращается в существующем формате ошибки протокола с ограниченным
диагностическим префиксом.

Без необязательного бюджета сохраняются исходный монотонный deadline, один
`write`/`sendall`, serial `flush`, пауза после TX, отмена и обработка TCP EOF/ошибок. Посторонние кадры
не продлевают срок. Отмена и обрыв TCP не преобразуются в успешный ответ.
Транспорт не добавляет повторов, сканирования, готовностных запросов,
перезапуска образа или новых пауз между блоками. Последовательность прошивки,
индексированные окна, старые загрузчики и правила повторов остаются в
`flash_protocol.py`; владение UART — в [контракте портов](port-ownership.md).

## Общий бюджет настройки UART

`make_serial_send_rtu_persistent(..., deadline=None)` принимает необязательный
абсолютный срок по `time.monotonic()` и передаёт его в
`send_receive(..., deadline=...)`. Он общий для всех обменов через этот callback:
ограничивает ожидание локальной блокировки, начальную задержку, запись, ожидание
очереди TX и чтение. По истечении callback возвращает `None` и не повторяет запрос.
Ошибка внутри обмена закрывает открытый транспорт после его завершения; отказ
до входа в обмен ничего не пишет. Общий `close()` остаётся обязанностью вызывающего.
Прямой `send_receive` может сообщить `TimeoutError` или ошибку serial;
это не доказательство, что модуль не применил запись.

Для ручной настройки семейство сначала определяется обычным запросом. После
свежего опознания MR с AI тот же открытый callback принимает необязательный
`exchange_deadline` для каждого последующего обмена. При наличии обоих
сроков действует более ранний. Пересекающиеся адреса регистров CE сохраняют
исходный режим транспорта.

В этой ветке нет неограниченного `flush`/`tcdrain`. До записи проверяются
доступность `out_waiting`, пустая исходная очередь и достаточный остаток времени.
Неизвестная или уже занятая очередь означает отказ до TX. Резерв времени равен
длительности **всего фактического запроса** на фактической скорости и формате
символа UART плюс прежняя пауза переключения в RX. Запись и опрос очереди должны
завершиться до начала этого резерва. `write_timeout` и `timeout` ограничиваются
оставшимся временем и восстанавливаются в `finally`, включая ошибки и отмену.
Частичная запись не дописывается и не повторяется автоматически.

Нулевой `out_waiting` не доказывает пустоту аппаратного FIFO, поэтому после него
выдерживается весь резерв. При частичной записи, отмене до завершения drain,
тайм-ауте записи или незавершённом drain сбрасывается только очередь этого обмена,
затем выдерживается тот же резерв до возврата и закрытия транспорта. В течение
этого времени UART и lease остаются у вызывающего. Отмена до TX ничего не пишет;
отмена после TX не сокращает защитную паузу. Это ограничение программного ожидания
с учётом штатных тайм-аутов драйвера, а не гарантия жёсткого реального времени ОС.

Консервативная пауза увеличивает стоимость последовательности. Например, для
запроса из 8 байтов в формате 8N2 при 19200 бод резерв составляет 8,59 мс, из них
4,58 мс — полный запрос, добавленный после проверки пустой очереди. Для 256 таких
обменов один резерв занимает около 2,20 с из бюджета 20 с, без времени ответов и
планировщика. При 1200 бод такой же резерв для 256 обменов уже превышает 20 с:
срок остановит операцию, полного применения обещать нельзя. Для FastModbus и
других размеров кадров резерв вычисляется по их фактической длине.

Обычные вызовы и маршруты прошивки без `deadline` сохраняют прежнее поведение.
Callback не создаёт фонового UART-писателя; вызывающий закрывает транспорт до
освобождения lease.

## Проверка

Регрессии находятся в `test_response_correlation.py`,
`test_serial_response_framing.py` и `test_flash_transport_composition.py`
каталога `opt/sa02m-flasher/tests/` и выполняются строкой `py-unit-flasher`.
Они проверяют поля/CRC, каждую границу разбиения эха, редкую коллизию,
исключения и пределы, а также настоящий PTY и локальный socketpair через
`FlasherProtocol`. Эти проверки не измеряют межбайтовые интервалы внутри кадра
физического UART и сами по себе не устанавливают причину обрывов COM4.

`test_serial_deadline.py` проверяет частичную/блокирующую запись, неподдерживаемый
drain, неосвобождающуюся очередь, чтение, отмену, восстановление тайм-аутов и
закрытие после защитной паузы. Проверка на настоящем PTY подтверждает один точный
запрос и ответ без повторов; время PTY не является измерением физической линии.
