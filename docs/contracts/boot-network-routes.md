# Контракт: статические маршруты из конфига интерфейса восстанавливаются

Домашний адрес механизма, который возвращает в таблицу маршрутизации
статические маршруты, объявленные строками `post-up`/`up` в
`/etc/network/interfaces.d/<if>.conf`, когда `ifup` их так и не применил.
Машинная грамматика (имена файлов, ключи, строки журнала) — на английском
(`PROTOCOL.md` invariant 5); пояснения — на русском.

Смежные контракты: `docs/contracts/boot-network-dns.md` — та же цепочка отказа
`ifup` и та же лестница восстановления (здесь на них только ссылки);
`docs/contracts/ethernet-iface-naming.md` — писатели `interfaces.d`.

---

## 1. Гарантия

> На настроенной SA-02m каждый **поддерживаемый** (§3) статический IPv4-маршрут,
> объявленный строкой `post-up`/`up` в `/etc/network/interfaces.d/<if>.conf`,
> присутствует в основной таблице маршрутизации в пределах одного прохода
> лестницы восстановления после того, как у `<if>` есть carrier и IPv4-адрес, —
> независимо от того, дошёл ли `ifup` до стадии `post-up`, и после любого
> link cycle, который его сбросил. Механизм никогда не выполняет строку
> конфига, не трогает маршрут по умолчанию, не меняет и не удаляет
> существующий маршрут и никогда не роняет вызывающего.

«Один проход» — не дольше `CHECK_INTERVAL` сторожа (30 с по умолчанию) после
первого прохода, увидевшего carrier и адрес. На загрузке худший случай ≈ 60 с
задержки старта `net-watchdog` + 30 с.

Обычно маршрут приходит раньше — одним из двух путей:

- **Проход coldboot.** Он идёт сразу после `networking.service`.
- **Перепроверка после link cycle.** Link cycle `fix-eth@` идёт на загрузке,
  когда PHY медленно согласует линк. На смену carrier у `eth0` ядро не шлёт
  uevent (измерено на стенде, §8), поэтому правил udev на линк для `eth0`
  нет. Между проходами сторожа на появление линка не реагирует
  ничто. Поэтому `fix-eth.sh` сам перечитывает carrier после цикла. При `1`
  тот же проход идёт в ветку «carrier есть» и вызывает этот механизм.

Худший случай по-прежнему действует в трёх случаях. В каждом маршрут
подхватывает следующий проход сторожа:

- **Линк вне цикла.** Линк появился после перепроверки carrier, после выхода
  юнита `fix-eth@` или без цикла вовсе (например, кабель подключили позже,
  §8). Он ждёт следующего прохода сторожа: до 30 с, на загрузке — плюс 60 с
  задержки старта.
- **Ворота bootstrap в `fix-eth.sh`.** Пока работают `networking.service` или
  `ifup@<if>`, `fix-eth.sh` выходит до вызова этого механизма (§4). Это
  касается и прохода после link cycle. `eth1` объявлен как `allow-hotplug`,
  поэтому `ifup@eth1` — реальный юнит.
- **Пропуск coldboot.** Coldboot по той же причине пропускает свой проход
  (`ifup_in_progress`, §4).

Условие (названное, не скрытое): работает хотя бы один из
`net-watchdog.service`, udev `fix-eth@` (для `eth0` — только по add/bind
интерфейса; строки `eth1` на линк не проверены) или
`sa02m-eth-coldboot.service` — те же условия, под которыми уже живёт
восстановление маршрута по умолчанию.

## 2. Отказ, который это лечит

Стенд `192.168.1.135`, 2026-10-29: после перезагрузки пропал маршрут
`192.168.10.0/24 via 192.168.1.100`, прописанный в `eth0.conf` строкой
`post-up ip route add … || true`. Клиенты из сети 192.168.10.x сутки не видели
MQTT-брокер. В таблице были только `default via 192.168.1.1 dev eth0 onlink`
(флаг `onlink` выдаёт, что его вернул `inet-failover.sh`, а не `ifup`) и
подключённая /24. Плата при этом пинговалась и отдавала панель — отказ
**молчаливый**.

Два независимых триггера:

1. **`ifup` обрывается до `post-up`.** Цепочка «поздний carrier → шаг `gateway`
   падает → `ifup` обрывается до хуков» описана один раз — в
   `boot-network-dns.md` §2. Строки `post-up` выполняются в той же стадии, что
   и хуки `if-up.d`, и пропускаются тем же обрывом.
2. **Link cycle сбрасывает все маршруты.** `fix-eth.sh` и
   `sa02m-eth-coldboot.sh` опускают и поднимают интерфейс (CHANGELOG 1.0.7.12
   называет этот сброс); после цикла восстанавливается только маршрут по
   умолчанию. Объявленный маршрут не возвращался до следующей перезагрузки.

## 3. Механизм

`/usr/local/sbin/sa02m-routes-ensure.sh [<iface>|--all]` (без аргумента —
`--all`), **всегда выходит с кодом 0**.

1. Один проход `awk` по `<if>.conf` разбирает строки — **ни одна не
   выполняется**. Конфиг без маршрутных строк (каждая заводская плата) стоит
   один `awk` и ни одного вызова `ip`.
2. Если есть хотя бы один поддерживаемый маршрут и у интерфейса есть IPv4-адрес
   (`ip -4 -o addr show dev <if>`), для каждого: `ip -4 route show exact <dst>`;
   пусто — `ip -4 route add <dst> via <via> [dev <if>] [metric <m>] [onlink]`,
   все токены отдельными аргументами.
3. **Заполняет пробел, а не спорит.** Маршрут к тому же префиксу с **любым**
   шлюзом или метрикой оставляется как есть.
4. **`add`, а не `replace`** — даже если в конфиге написано `replace`. Добавление
   выполняется только при пустом `show exact`, поэтому результат тот же, но если
   кто-то (ifup, оператор) вставил маршрут между проверкой и добавлением, ядро
   отвечает `EEXIST`, а `replace` молча перезаписал бы чужой шлюз. Повторная
   проверка после `EEXIST` гасит эту гонку без записи в журнал.

### Поддерживаемая грамматика

Учитываются только строки внутри стансы `iface <if> inet …` этого же
интерфейса (стансу завершает любая строка `iface`, `mapping`, `auto`,
`allow-*`, `source`, `source-directory`, `rename`, `no-auto-down`,
`no-scripts`). CRLF допустим.

| Строка (`post-up`/`up` …) | Что делает хелпер |
|---|---|
| первое слово не `ip`/`route` (хук KLogic, `sleep`, `sh -c` …) | ничего, молча — **если** в строке нет обёрнутой команды маршрута (см. ниже) |
| `ip [<опции>] <не route> …` (`ip addr`, `ip link`, `ip -s link`) | ничего, молча — с той же оговоркой |
| `ip route del\|delete\|flush\|show\|list\|get …`, голый `ip route` | ничего — с той же оговоркой |
| `ip route add\|replace default\|0.0.0.0/0\|0/0\|<x>/0 …` | ничего, молча — маршрутами по умолчанию владеют другие (§5); с той же оговоркой |
| `ip [-4\|-f inet] route add\|replace <dst> via <IPv4> …` в строгой форме ниже | **применяется** |
| `ip -6 route …` / `ip -f inet6 route …`, `ip <любая другая опция> … route …` (например `-n <netns>`), `route …` (net-tools), `ip route append\|change\|prepend…`, любая иная форма `add`/`replace` | пропускается, одна строка в журнал |

`route` везде можно сократить, как это делает сам `ip`: `r`, `ro`, `rou`, `rout`
(`ip r add …` — это `ip route add …`). Сокращения действия (`ip r a …`) не
распознаются и попадают в журнал.

**Обёрнутая команда маршрута** — в команде строки встречается слово
`ip` (можно с путём и открывающей кавычкой, скобкой или `$(`), а за ним слово
`r`…`route`, либо пара слов `route add`: `post-up sleep 5 && ip route add …`,
`post-up /bin/sh -c "ip route add …"`, `post-up ip route del X; ip route add X …`.
Такая строка **никогда не применяется**, но попадает в журнал как непонятая
(только номер строки). Хук без такого текста (`/home/klogic/adjust-eth0 || /bin/true`,
`sh -c "echo up"`) остаётся молчаливым.

**Чего хелпер не видит вовсе:** маршрут, который добавляет вызываемый строкой
скрипт или бинарник (`post-up /usr/local/bin/my-routes.sh`), — читается только
текст конфига. Такой маршрут хелпер не восстановит и в журнал не запишет.

`ip` допускается как `ip`, `/sbin/ip`, `/usr/sbin/ip`, `/bin/ip`, `/usr/bin/ip`.
Строгая форма после `add|replace`:

| Часть | Правило |
|---|---|
| `<dst>` | IPv4 `a.b.c.d` или `a.b.c.d/1…32`, без ведущих нулей в октетах (`010` — восьмеричное для части разборщиков) |
| `via <IPv4>` | **обязателен** |
| `dev <if>` | только имя этого же интерфейса или `$IFACE` / `${IFACE}`; без `dev` — хелпер тоже не передаёт `dev` |
| `metric <n>` | `0` или число без ведущих нулей, до 9 цифр |
| `onlink` | флаг |
| хвост | любое число из `>/dev/null`, `1>/dev/null`, `2>/dev/null`, `2>&1`, затем необязательно `\|\| true` (`/bin/true`, `/usr/bin/true`, `:`) |
| `#…` | комментарий до конца строки — только когда строка уже полна |

Каждое ключевое слово — не больше одного раза. Всё остальное (`table`, `src`,
`proto`, `scope`, `;`, `&&`, `` ` ``, `$(`, кавычки, `*`, управляющие символы,
чужой `dev`, нет `via`) — строка пропускается целиком, никогда не применяется
частично или «по догадке». Границы: строка длиннее 1024 символов
(`MAX_LINE_LEN`) и маршруты сверх 16-го (`MAX_ROUTES`) — тоже пропуск.

### Журнал (`logger -t sa02m-routes-ensure`)

Пишет **только** когда что-то сделал или не смог:

| Событие | Строка | Частота |
|---|---|---|
| маршрут добавлен | `<if>: route <dst> via <via>[ dev …][ metric …][ onlink] added (ifup never applied it)` | при каждом добавлении |
| строки не разобраны | `<if>: N route line(s) in <if>.conf not understood and skipped (line(s) …)` — только номера строк, никогда текст конфига | раз за загрузку на содержимое конфига (правка конфига снова включает) |
| добавление не удалось | `<if>: route <dst> via <via> could not be added: <первая строка ошибки ip, без управляющих символов, до 200 символов>` | раз за загрузку на пару (интерфейс, сеть) |

Маркеры «уже сообщено» лежат в `/run/sa02m-routes-ensure/` (tmpfs, живут до
перезагрузки). Плата, пишущая `added` каждую загрузку, — видимый сигнал, что
`ifup` всё ещё обрывается; делать журнал молчаливым — регресс.

## 4. Где вызывается

Обёртка `routes_ensure` (guard `-x`, `timeout 10`, вывод погашен, `|| true`)
стоит рядом с `dns_ensure` в обоих скриптах лестницы:

| Точка вызова | Зачем |
|---|---|
| `etc/fix-eth.sh` — ветка «carrier и адрес есть» | каждый проход сторожа (30 с): маршрут, сброшенный link cycle или так и не применённый |
| `etc/fix-eth.sh` — после успешного восстановления (`ifdown`/`ifup`) | повторный `ifup` мог снова не дойти до `post-up` |
| `usr/local/sbin/sa02m-eth-coldboot.sh` — ветка `carrier already up` (перед `continue`) | проход на загрузке сразу после `networking.service` |
| `usr/local/sbin/sa02m-eth-coldboot.sh` — после мягких рестартов PHY | эти рестарты сами сбрасывают маршруты |

В `fix-eth.sh` оба вызова стоят после ворот `iface_bootstrap_in_progress`
(`networking.service` или `ifup@<if>` ещё работают — ничего не делать). В
coldboot обёртка проверяет то же самое (`ifup_in_progress`: `ActiveState`
`activating`/`deactivating` у `networking.service` или `ifup@<if>.service` —
оба `Type=oneshot`) и в этом случае пропускает проход; маршрут подхватит
следующий проход сторожа (§5).

**Собственного юнита нет** — решение Оператора (2026-10-29, вариант F1-A).
Проход на загрузке уже даёт coldboot; отдельный юнит потребовал бы записи в
`services.enable` обоих генераторов манифеста и второго bootstrap-шима (см.
`boot-network-dns.md` §7) — большая цена за проход, который уже есть.
Следствие: если выключены и `net-watchdog`, и coldboot, и udev `fix-eth@`,
маршрут не восстанавливается (§1, условие).

## 5. Что этот механизм НЕ делает

- **Не трогает маршруты по умолчанию.** Ими владеют восстановление в
  `fix-eth.sh`, `inet-failover.sh` и хуки `dhclient`; строку установщика
  `post-up ip route replace default … dev eth1 metric 100` хелпер молча пропускает.
- **Не меняет и не удаляет** существующие маршруты — только добавляет
  отсутствующие.
- **Возвращает маршрут, удалённый вручную, пока строка остаётся в конфиге**
  (решение Оператора F3, 2026-10-29): конфиг — это объявление, как и для `ifup`
  на следующей загрузке. Чтобы убрать маршрут насовсем, удалите строку из
  `<if>.conf`, затем `ip route del …`.
- **Никогда не выполняет строку конфига** — ни `eval`, ни `sh -c`; в `ip`
  попадают только токены, прошедшие якорные регэкспы.
- **Не поддерживает** IPv6, маршруты без `via` (только `dev`), `table`/`src`/
  `proto`/`scope` и синтаксис `route add` из net-tools — такие строки
  пропускаются с записью в журнал.
- **Не повторяет хук KLogic** `post-up /home/klogic/adjust-<if>`, который
  упавший `ifup` тоже пропускает: это запуск чужого бинарника, вслепую его
  повторять нельзя.
- **Не пишет `interfaces.d`.** Сохранение сетевых настроек из панели переносит
  строку маршрута, уже записанную в конфиг, только в строгой форме и только
  дословно; что именно переносится, а что отклоняет сохранение, —
  `ethernet-iface-naming.md` §5.4.
- **Не меняет поведение позднего `ifup`.** Строка без `|| true` сделала бы
  поздний `ifup` неудачным на `EEXIST`, но в том же состоянии он и сегодня падает
  на «address File exists», а восстановление в `fix-eth.sh` сначала делает
  `ifdown` (который сбрасывает маршрут).
- **Не вмешивается в идущий `ifup`.** Окно: интерфейс `allow-hotplug`, его
  `ifup@<if>` уже назначил адрес, но ещё не дошёл до `post-up`. Добавь хелпер
  маршрут в этот момент, собственная строка `ifup` без `|| true` упала бы на
  `EEXIST`, и `ifup` пропустил бы следующие хуки. Поэтому оба места вызова
  ждут: `fix-eth.sh` — за воротами `iface_bootstrap_in_progress`, coldboot — за
  `ifup_in_progress` (§4). Остаток окна — `ifup`, запущенный вне systemd
  (например, панелью через `/sbin/ifup` напрямую) в ту же секунду, что и проход
  сторожа; он не отслеживается и принят как узкий.

## 6. Деградация

| Условие | Поведение |
|---|---|
| хелпер отсутствует (частичный деплой) | обёртки защищены `-x` → пропуск, сегодняшнее поведение |
| `ip` не найден | тихий no-op, код 0 |
| у интерфейса нет IPv4-адреса | только проверка адреса, ничего не добавляется, тихо; повтор на следующем проходе |
| строка маршрута не разбирается | строка пропускается, одна запись в журнал за загрузку на содержимое конфига |
| `cksum` не сработал (пустая контрольная сумма) | запись о непонятых строках пишется на каждом проходе — в сторону видимости, не тишины |
| `ip route add` вернул ошибку | одна запись за загрузку на (интерфейс, сеть), код 0; повтор каждый проход |
| `/run/sa02m-routes-ensure` недоступен для записи | маркеры не пишутся → записи журнала повторяются каждый проход (в сторону видимости, не тишины); код 0, маршрут всё равно добавляется |
| хелпер завис | `timeout 10` в обёртке его снимает, проход лестницы продолжается |

## 7. Доставка на платы

Механизм доставки (`DST_RE`, `map_dst`) описан один раз — в
`boot-network-dns.md` §7.

| Файл | «Обновление веб» / `.sa02m` | `install.sh` / `--refresh` | Новый образ |
|---|---|---|---|
| `/usr/local/sbin/sa02m-routes-ensure.sh` | **да** (`usr/local/sbin/` → 0755) | да (`scripts/02-network.sh`) | да (установщик выполняется при сборке) |
| `/usr/local/sbin/sa02m-eth-coldboot.sh` | **да** | да | да + оверлей первой загрузки |
| `/usr/local/bin/fix-eth.sh` | **да, ярусом с 1.0.7.19** — `docs/contracts/web-update.md` («Ярусное назначение») | да | да + оверлей первой загрузки |

Проход на загрузке (coldboot) приходит с первым же обновлением. Ремонт из
`fix-eth.sh` — 30-секундный проход сторожа и перепроверка после link cycle —
приходит вместе с самим `fix-eth.sh`: по воздуху — по правилам яруса в
`docs/contracts/web-update.md`, через `install.sh` / `--refresh` и новый
образ — сразу.
**`--refresh` запускать без `--ip`**: с `--ip` установщик перезаписывает
`eth0.conf` и стирает строку маршрута, добавленную вручную
(`docs/contracts/installer-refresh-policy.md`).

Сам хелпер **не** входит в оверлей первой загрузки (как и `sa02m-dns-ensure.sh`):
клон, прошитый оверлеем без установщика, получает обёртки с `-x`-guard и
сегодняшнее поведение. Это тот же пробел, что у DNS-хелпера (пункт бэклога об
оверлее первой загрузки).

|---|---|

## 9. Приёмка на железе

Только после слияния, по слову Оператора и по `docs/deployment.md`:

1. Развернуть: «Обновление веб» до этой версии или новее, затем
   `sudo ./install.sh --refresh` **без `--ip`** (или `scripts/offline-full-update.sh`)
   — «Режим обновления» в `docs/deployment.md`. `--refresh` ставит `fix-eth.sh`
   сразу, не дожидаясь следующего обновления (§7). Перезагрузка не нужна:
   `net-watchdog` запустит новый `fix-eth.sh` на следующем проходе.
2. `ip route show 192.168.10.0/24` → `via 192.168.1.100 dev eth0` в пределах 30 с,
   если маршрута не было; `journalctl -b -t sa02m-routes-ensure` — одна строка
   `added` (или ни одной, если маршрут был).
3. Самый дешёвый пробник: `ip route del 192.168.10.0/24`, подождать один проход
   сторожа — маршрут вернулся, в журнале `added`.
4. Link cycle: выдернуть кабель eth0 на ~40 с, вернуть → маршрут на месте в
   пределах 60 с после линка; клиент из 192.168.10.0/24 подключается к брокеру
   на :1884.
5. Загрузка (FR-CABLE из `boot-network-dns.md` §9): включить без кабеля,
   воткнуть на ~T+40 с → маршрут в пределах 60 с после подключения;
   `systemctl --failed` пуст. Граница держится не из-за udev, а потому что
   проход coldboot (~T+55 с на 1.135) идёт после подключения кабеля; общий
   худший случай загрузки в §1 остаётся 60 + 30 с.
