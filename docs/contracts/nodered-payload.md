# Проверенная установка Node-RED

Панель и `scripts/07-nodered.sh` устанавливают один архив через
`etc/sa02m-vendor-install.py`. Доверенные версии, размеры, SHA-256, архитектура,
имена архивов и происхождение дерева находятся в `etc/vendor-payloads.json`.
Манифест поставляется с проверенным релизом в
`/usr/local/share/sa02m/vendor-payloads.json`; скачанный рядом с архивом файл
контрольных сумм не заменяет этот источник доверия.

## Получение и проверка

Первым проверяется точное имя архива в `/opt/vendor-installers/nodered`.
Корневой CLI установщика сохраняет `SA02M_NODERED_DIR`; панель не принимает
путь, URL или другой манифест от браузера. Если локального файла нет,
используется только HTTPS URL из манифеста с ограниченными перенаправлениями.
`url: null` означает неопубликованный архив: отсутствующий локальный payload
возвращает `payload_unavailable`. Резервного запуска скачанного root-скрипта нет.
Повреждённый локальный архив вызывает отказ, а не незаметную замену из сети.

Проверка размера и SHA-256 предшествует распаковке. Ограничиваются размер
архива, распакованного tar вместе с PAX-заголовками, число и размеры записей.
Абсолютные пути, `..`, дубли, устройства, FIFO, hardlink и выходящие наружу
символические ссылки запрещены. Относительные ссылки внутри дерева
сохраняются; ссылка не может быть родителем извлекаемого файла.

В распакованном дереве сверяются версия приложения, SHA исходных manifest/lock
и полный список файлов с размерами, режимами и хешами. Список входит в архив
как `.sa02m-inventory.json`; его SHA закреплён в релизном манифесте.
До изменения пользователей, служб и установленного runtime проходят проверки
всех нужных архивов и совместимости Node. Проверенное исполняемое содержимое
проверяется непривилегированным процессом.

## Состояние устройства

Совместимый существующий Node сохраняется. Проверяются `engines.node` всех
пакетов доставленного дерева, включая вложенные копии npm. Несовместимость
возвращает `node_upgrade_required` до изменений установки. Отсутствующий Node
берётся из закреплённого ARM-архива; ELF-архитектура и фактическая версия
проверяются. Он располагается в `/opt/sa02m-node/<version>`, а
`/usr/local/bin/node` создаётся только при отсутствии существующего бинарника.
Файлы Node, принадлежащие дистрибутиву, не заменяются. Смена мажора уже
установленного Node-RED требует отдельной миграции и возвращает
`major_upgrade_refused`.

Явная установка из панели использует `--activate`: включает и запускает
службу после успешной проверки. Маска службы вызывает `service_masked` до
изменений. `--preserve` сохраняет выключенный автозапуск и остановленную
службу; работающая служба перезапускается один раз. Обычный refresh завершает
ветку overlay до вызова этого helper — правило находится в
[политике refresh](installer-refresh-policy.md).

Перед изменениями helper проверяет также legacy-имя `node-red.service` через
PID 1. Отдельная загруженная или маскированная unit вызывает
`service_identity_conflict`; автоматической миграции нет. Alias допустим только
когда `Id`, `Names` и `FragmentPath` обеих записей подтверждают одну каноническую
`nodered.service`. Неполный ответ менеджера вызывает `manager_unknown`.

Корневой CLI сохраняет пользовательские `--nodered-user` и `--port`.
Имя учётной записи и домашний каталог проверяются; unit получает отдельный
drop-in с `User`, `Group`, `WorkingDirectory`, `EnvironmentFile` и `--userDir`.
Рекурсивного `chown` домашнего каталога нет. Потоки, зашифрованные credentials
и существующий `settings.js` не переписываются. В environment добавляются
только отсутствующие `NODE_OPTIONS` и `PORT`; записи выполняются относительно
открытого дескриптора каталога без следования ссылкам. Новая системная учётная
запись не удаляется при неудачной активации.

## Завершение и откат

Один root-owned lock запрещает параллельные установки. Приватная staging
область не является установленным runtime. Подмена дерева и файлов unit
сохраняет предыдущую копию; неудачная активация восстанавливает её и прежнее
состояние службы. Установщик не запускает фоновый daemon в своей группе
процессов: runtime принадлежит PID 1. Успех работающей службы требует
терминального systemd job, реального MainPID, соответствующих executable,
точной cgroup службы и рабочего каталога из установленного drop-in. После
штатной смены `process.title` на `node-red` Linux уже не сохраняет исходные
аргументы; такой title допустим только вместе с остальными признаками.
Сообщение о запуске потоков выбирается по доверенным полям журнала для текущих
unit, InvocationID и PID. Перед успехом менеджер и процесс проверяются повторно,
включая время создания процесса из `/proc`, чтобы смена или повторное использование
PID не подтвердили чужой запуск. Последний маркер ошибки или остановки запрещает
успех даже после более раннего сообщения о запуске потоков.

Общий бюджет helper — 540 секунд, включая подготовку и откат. Неизвестное
состояние менеджера не считается завершением и не запускает повторную
активацию. При невозможности подтвердить откат сохраняются резервные файлы
и диагностический путь; результат — `rollback_failed`, а не `ok:true`.
Успешная квитанция `/var/lib/sa02m/vendor/node-red.json` записывается после
проверки установленного дерева и считывается обратно. Она содержит хеши
runtime/inventory и фактическое действие с Node. Асинхронный результат панели
подчиняется [контракту служб](service-control.md).

## Сборка и проверка

`scripts/dev/build-nodered-payload.sh` вызывает единственный сборщик
`build-nodered-payload.py`. Он требует закреплённые Node/npm, выполняет
`npm ci --ignore-scripts --omit=optional` по исходному lock, сохраняет все
вложенные пакеты, проверяет отсутствие нативных модулей и нормализует tar/gzip
метаданные. Коллизия при переносе зависимостей вызывает ошибку. Выход включает
архив, `vendor-payloads.json`, `runtime-packages.json` и `build-receipt.json`.
Версии и хеши устанавливаемых библиотек не переписываются вручную.

ARM-архив Node производится из официального Node 22.23.5 с проверкой SHA.
Сборщик заменяет целиком каталог `lib/node_modules/npm` версией из
проверенного архива Node-RED. Публичные команды node, npm, npx и corepack,
заголовки и лицензии сохраняются. В `build-receipt.json` фиксируются URL
и SHA исходного Node, версия замены и отдельный SHA результата. При обновлении
пинов сохраните объект `native_node` из этой квитанции в
`vendor-src/nodered/native-node-receipt.json`. Проверка сборки сверяет его со
сборщиком, npm lock и релизным манифестом. Установщик
проверяет размер и SHA производного архива по релизному манифесту.

На этапе `build` `scripts/dev/test-vendor-install.py` проверяет отказ до
изменений, архивные атаки, транспорт, блокировку, ограничение процессов и
откат в изолированной файловой системе с имитацией менеджера служб.
`test-nodered-jsonata.mjs` проверяет выражения и регрессии доступа к
прототипам, для обычного прогона он устанавливает зависимости из lock-файла.

Обязательная проверка `nodered-runtime` на этапе `ship` сверяет релизный архив
и распакованное дерево с манифестом, затем проверяет палитру, внешние модули,
повтор после ошибки, каталоги RU/EN, JSONata, учётные данные после перезапуска
и MQTT. Запускайте `node .ai-dev/quality/run.mjs ship` в Linux с Node 22 в `PATH`.
`SA02M_NODERED_TEST_ROOT` указывает на распакованный каталог `node-red`,
а `SA02M_NODERED_TEST_RECEIPT` — на JSON с полем `archive`, где указан путь
к точному архиву относительно каталога этого JSON. Отсутствие входных данных
или расхождение с манифестом останавливает проверку. Итоговая квитанция
содержит SHA архива, inventory и исходных manifest/lock.

Приёмка ARM, реального systemd и установки на чистую плату выполняется
отдельно. Синтетическая палитра покрывает только включённые в тест модули.

Отсутствующий payload опционального стека сохраняет WARN/пропуск установщика.
Эта деградация и успешные функциональные тесты не означают допуск золотого
образа: свежая проверка всех доставленных зависимостей выполняется отдельно.
