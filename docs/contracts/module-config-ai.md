# Контракт: конфигурация AI-канала модуля (web-сторона флешер-демона)

Домашний адрес веб-контракта на **чтение и запись параметров аналогового входа
(AI)** модулей расширения MR-02м с AI (`12AI`, `6AI6AO`, `6AI2AO`) через флешер-демон
(`opt/sa02m-flasher`). Машинная грамматика (номера регистров, JSON-поля,
имена полей) — на английском (`PROTOCOL.md` invariant 5); пояснения — на
русском (`docLanguage: ru`).

Реестр он-wire регистров принадлежит прошивке (`MR-02m/MODBUS_VARIABLES.txt`) и
здесь только **читается**, не дублируется (см. «Источник истины»). Веб пишет и
декодирует **строго** по нему; расхождение — находка ревью.

Реализация: `sa02m_flasher/device_config.py` (снимок `_read_ai_channels`,
allow-list `_allowed_mr_holding_registers`), `module_profiles.py` (карта
регистров канала). UI — `www/network_config/static/js/flasher.js`
(`renderModuleAiTab`, `applyAiCalibration`, `applyAiLimit`), строки — `i18n.js`.

## Раскладка регистров канала (эталон `MODBUS_VARIABLES.txt:315,400–406,261–262`)

Логический канал AI: `base = 400 + (ch−1)×7`, шаг **7** (`ai_channel_base_register`,
`ai_channel_stride`). Блок из 7 слов на канал:

| Смещение | Регистр (AI1) | Тип | Смысл | Доступ |
|---|---|---|---|---|
| `base+0` | 400 | Holding | тип датчика (код 0..42) | R/W |
| `base+1/+2` | 401/402 | Input | измеренное (raw s32) | **только чтение** |
| `base+3` | 403 | Input | пересчитанное (scaled) | **только чтение** |
| `base+4` | 404 | Holding | калибровка (смещение int16) | R/W |
| `base+5` | 405 | Holding | нижний предел измерения int16 | R/W |
| `base+6` | 406 | Holding | верхний предел измерения int16 | R/W |

Флаги аварии — **Input 107** (ниже предела) / **Input 108** (выше), по одному
биту на логический канал (бит `ch−1`, до 16 каналов), одно парное чтение на
снимок (`ai_input_limit_flags_for_channel`).

## Снимок AI-канала (`_read_ai_channels`, поля JSON — стабильный контракт)

Каждый элемент `mr.ai.channels[]` несёт (потребляется задеплоенными, в т.ч.
кешированными, бандлами — поля **аддитивны**, старый бандл игнорирует новые):

| Поле | Тип | Источник | Смысл |
|---|---|---|---|
| `channel` | int | — | номер канала (1-based) |
| `register_base` | int | `ai_channel_base_register` | `base` канала (**никогда не пересчитывать из индекса на клиенте** — писать по нему) |
| `sensor_code` | int | Holding `base+0` | код типа датчика 0..42 |
| `sensor_label`, `sidebar_tag`, `ui_bucket` | str | производные от `sensor_code` | подписи/группа |
| `measured_raw`, `scaled_raw` | int/null | Input `base+1..3` | текущие значения |
| `calibration` | int (s16) | Holding `base+4` | смещение калибровки |
| `limit_low` | int (s16) | Holding `base+5` | нижний предел измерения |
| `limit_high` | int (s16) | Holding `base+6` | верхний предел измерения |
| `fault_low` | bool | Input 107, бит `ch−1` | ниже предела / обрыв |
| `fault_high` | bool | Input 108, бит `ch−1` | выше предела / КЗ |
| `fault_known` | bool | Полная валидная пара Input 107/108 | Только `true` разрешает интерпретацию двух bool-флагов |
| `filters` | obj/absent | Holding фильтров | `12AI`/`6AI6AO`; для `6AI2AO` — только при прочитанной с устройства версии ≥ `1.0.12.20` |
| `filters.known` | obj | Признаки `kalman`, `sps`, `avg`, `tau` | Полный ответ и допустимый диапазон каждого параметра |

**Применимость калибровки — не поле снимка.** Выводится на клиенте из
`sensor_code` (`ai_ui_uses_value_calibration`: температура ∪ напряжение ∪ ток;
скрыта для «Выключен» и «сухого контакта»). Единственный источник — `sensor_code`;
прежнее поле `calibration_applicable` (только-температура) **удалено** из снимка,
чтобы не иметь двух расходящихся источников. Старый кешированный бандл при
отсутствии поля падает на свой клиентский вывод (null-safe) — регрессии нет.

**Декод аварии (клиент, эталон `ai_input_limit_range_message`):** только для
активных/температурных режимов (`volt/curr/ntc/rtd/tc_k`). Температурные:
`fault_low`→«Обрыв датчика», `fault_high`(NTC/RTD)→«Короткое замыкание на линии».
Активные: «Ниже/Выше диапазона измерения». «Выключен»/«сухой контакт» — без аварии.

## Граница записи (allow-list, `_allowed_mr_holding_registers`)

Запись Holding-регистров разрешена **только** по закрытому списку. На каждый
AI-канал гранты — **ровно**:

- `base+0` (тип датчика),
- `base+4` (калибровка, `ai_calibration_holding_register`),
- `base+5` (нижний предел), `base+6` (верхний предел),
- регистры фильтров (Kalman/SPS/avg/tau) — по наличию capability `kind_has_mp_ai_adc_filters`.

`6AI2AO` имеет шесть AI с шагом 7, как `6AI6AO`; оба используют слоты
фильтров `6..11`. Для типа 12 версия берётся из свежего полного чтения
Holding `320..323`, а не из записи сканирования. Неизвестная версия или версия
ниже `1.0.12.20` исключает `filters` из снимка и закрывает их запись до FC06.
Основные настройки AI/AO при этом доступны. Адреса и границы типа описаны в
[контракте MR](mr-module-control.md).

### Подтверждение применения типа

Тип из Holding или Input `base+0` может отражать принятую команду до следующего
цикла АЦП. Снимок передаёт отдельно `mr.ai_apply.state`. Значение `idle`
требует двух одинаковых полных чтений Holding 569..572, сигнатуры `0xA101`,
флагов `READY` (ровно 1) и совпадающих положительных поколений принятия и
завершения. При смене типа поколение должно вырасти ровно на единицу. Сервер
ждёт завершения этого поколения, проверяет тип и повторно проверяет поколение.
Общий бюджет обмена составляет 20 с и 256 запросов. Команда отправляется один раз.

Поколения действуют в пределах одной загрузки. Для подтверждаемой операции
сервер читает серийный номер Holding 270..271 и время работы Input 105..106.
Прошивка фиксирует оба слова времени при чтении младшего. До первой записи
время работы должно превышать оставшийся бюджет операции с запасом в секунду.
При слишком недавнем запуске или неизвестном серийном номере запись отклоняется.
После последних данных и проверки поколения сервер снова проверяет номер и
непрерывность показания времени с учётом секундной точности. Подтверждение
относится к модулю, наблюдавшемуся при этих чтениях.

На прошивке без этой возможности ручная смена типа возвращает HTTP 409,
`ok:false`, `error_code:"AI_TYPE_ACCEPTED_UNCONFIRMED"` и снимок с
`ai_write.status:"accepted_unconfirmed"`. Окно показывает принятие команды.
Повторного запроса при обновлении страницы нет. Пределы и параметры АЦП
SPS/average/tau в этом режиме доступны для чтения. Ручные записи этих полей
сервер отклоняет до FC06. Калибровка и включение Калмана хранятся независимо
и могут быть записаны с проверкой результата.

На поддерживаемой прошивке ручная запись предела или параметра АЦП требует
свежего `idle`, чтения записанного значения и того же поколения `idle` после
записи. Успех сопровождается `ai_write.status:"confirmed"`. Защита самой
прошивки отклоняет зависимую запись, если применение началось после начального
чтения. Правила переноса приведены в [контракте файлов](module-config-file.md).

`base+1/+2/+3` (измеренное/пересчитанное, Input) — **никогда не записываемы**.
Запись любого регистра вне списка → `ValueError` в `write_allowed_holding`
(fail-closed, отказ, не ложный `ok`). Это граница безопасности: неверный/чужой
регистр из запроса отклоняется до какой-либо записи (`web-code-rigor.md`).

**Клампы записи (клиент):** предел и калибровка активных режимов — весь int16
`[−32768, 32767]`; калибровка температуры — ±100. Порядок `lo < hi` не
навязывается (как в эталоне). Запись — по `register_base` из снимка через
`signedToUint16`, под edit-guard (опрос 1 с не затирает набираемое значение);
при отказе поле откатывается к снимку.

## Идиома ошибок

Как в `mqtt-set-endpoint.md`: транспорт остаётся управляемым, ошибка — в теле
ответа демона; тишина/сбой чтения не выдаётся за успех. Опрос конфигурации —
модаль-скоуп (1 с, только при открытом окне), не на дашборд-хот-пути; авария
читает Input 107/108 одним парным чтением на снимок (O(1), не на канал).

Полный выбранный AI-блок требует целых Holding-настроек и Input-измерений.
Минимальный снимок требует Holding-настроек; измерения в нём не запрашиваются.
Неполный обязательный блок завершает снимок ошибкой; поведение окна при этом
определено в [контракте MR](mr-module-control.md#достоверность-снимка).
Флаги Input `107/108` остаются необязательной диагностикой: `fault_known` равен
true только при точном полном ответе с корректными CRC, slave и функцией.
Неудачное чтение сохраняет числовые измерения, а окно показывает «Статус аварий
недоступен». Полная нулевая пара означает отсутствие аварии. Старые bool-поля
сохраняются, но при false/отсутствующем `fault_known` не используются как
доказательство. Отключённый вход и сухой контакт не получают лишнего предупреждения.
Статус обновляется и при защищённом вводе пользователя.

Фильтры имеют независимые признаки достоверности Kalman и трёх параметров WB.
Неполный WB-блок делает все три параметра неизвестными. Допустимы Kalman 0/1,
SPS из списка поддержанных частот, average 0..50 (прочитанный 0 нормализуется
в 1), tau 0..65000. Полный ответ с недопустимым значением не разрешает запись.
Изменение одного поля фильтра отправляет его единственный регистр. Для WB окно
проверяет весь блок и состояние применения типа при выходе запроса из очереди.
Для Калмана достаточно признака самого поля и допустимого слота хранения.
Отсутствие `filters` означает отсутствие поддержки настроек фильтра в профиле.

Для необязательных настроек DO/DI/AO отсутствующий ключ минимального снимка
сохраняет прежние данные; явно возвращённый `[]` заменяет их неизвестным значением.
Ввод и групповое сохранение закрыты, пока не прочитаны все поля группы. Это
включает LIVE-уставку AO: неизвестные safe/watchdog блокируют всю группу до первой
записи. Нулевое прочитанное значение остаётся допустимым. Watchdog имеет отдельный
`inactivity_known`, получаемый из HR134; без true его числовое поле не доказательство.
Правила применяются в первоначальном отображении, при опросе и в обработчике записи.

Дополнительные поля совместимы по типам со старыми клиентами. Уже открытый старый
JavaScript игнорирует их и сохраняет прежние ограничения до обычного обновления
кэша выпуска/страницы; исправление не обещает обновить такой клиент удалённо.

## Валидирующая проверка

Автоматическая, `py-unit-flasher` (`opt/sa02m-flasher/tests/test_device_config.py`):

1. `test_allowed_holding_regs_grant_ai_channel_offsets` — для `6AI6AO` на каждый
   AI-канал `_allowed_mr_holding_registers` содержит `base`, `base+4`, `base+5`,
   `base+6` (и `base+4 == ai_calibration_holding_register`) и **не** содержит
   `base+1/+2/+3` (Input-регистры не записываемы).
2. `test_ai_snapshot_exposes_limit_and_fault_fields` — `_read_ai_channels` (с
   мокнутыми чтениями) отдаёт поля `limit_low/limit_high/calibration/fault_low/
   fault_high`, корректно декодит бит `ch−1` из слов Input 107/108 и **не** несёт
   поля `calibration_applicable`.

`test_mr_optional_validity.py` дополнительно проверяет реальные кодеки и HTTP,
необязательные отказы, домены и неизменное число чтений. Браузерная проверка
`test-mr-optional-validity.mjs` проверяет переходы авария/неизвестно/норма,
защищённый ввод и отсутствие запросов от недоступных групп в обеих темах и языках.

Что **не** проверяется отсюда (честный предел, аудит 2026-09-08 F17): сторона
прошивки — соответствие адресов `MR-02m/MODBUS_VARIABLES.txt` живому модулю
проверяется только на стенде; здесь регистры читаются, не дублируются. Строка
`py-unit-flasher` с 1.0.6.40 перечисляет этот файл в `covers`, поэтому правка
контракта перезапускает названные тесты.

- `MR-02m/MODBUS_VARIABLES.txt` — раскладка регистров канала AI (`:315,400–406`),
  флаги 107/108 (`:261–262`), кодировка пределов (`:405–412`).
