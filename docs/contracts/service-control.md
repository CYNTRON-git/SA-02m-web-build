# Асинхронное управление службами

До подтверждения активации список отражает доступные для чтения состояния служб.
Панель отключает кнопки и показывает причину ожидания или ошибки. Привилегированный
обработчик независимо проверяет владение эпохой перед регистрацией операции
и возвращает `migration_required` при отказе. Кэш списка становится доступным
только после публикации `owned-v1` с текущим boot ID. Порядок подготовки,
проверки и открытия операций определён в
[политике активации](installer-refresh-policy.md#активация-изолированного-python).

Авторизованный `POST cgi-bin/services_ctrl.cgi` с действующим CSRF-токеном принимает `id` службы и `action` (`start`, `stop`, `install`, `uninstall`). Ответ `ok:true,pending:true` подтверждает приём команды, а не её выполнение. Он содержит `id`, `action` и новый случайный `op_id` из 32 шестнадцатеричных символов нижнего регистра.

Панель читает `GET ?result=1&id=…&op_id=…`. Отсутствующий результат или результат другой операции означает `pending:true`. Завершить команду может только ответ с соответствующими `op_id`, `id`, `action`; ошибка предыдущей операции также не завершает новую. Служба сохраняет недоступные кнопки всех действий до завершения команды, в том числе после очередного обновления списка.

После соответствующего успешного результата панель сразу запрашивает полный список и независимо проверяет состояние службы. Кнопки остаются недоступными до этой проверки. Последующие попытки сохраняют интервал 2 с.

| Ограничение | Время |
| --- | --- |
| Один запрос списка, POST, результата или проверки состояния, включая полное чтение JSON | До 20 с, но не дольше остатка общего времени |
| Вся операция start/stop, начиная перед POST | 90 с |
| Вся операция install/uninstall, начиная перед POST | 600 с |

Управляемые CODESYS, CodeMeter и MPLC запускаются через PID1: демон не наследует файловые дескрипторы вызывающего helper. Неуспех или тайм-аут клиента systemctl не разрешает повторный запуск через init.d. Без работающего systemd мутация этих рантаймов возвращает `systemd_required`; резервные SysV/файловые проверки **чтения** остаются. Ручной запуск CODESYS на SMP/RT сохраняет прежнюю политику, CodeMeter запускается перед CODESYS, остановка идёт в обратном порядке.

Для install/uninstall предусмотрены шесть фиксированных transient units `sa02m-svcctl-{install,uninstall}-{codesys,mplc4,node-red}.service`. Команду и аргументы выбирает root helper из закрытого каталога. Внутренний режим допускается только при совпадении root, фактического MainPID и cgroup нужного unit; переменная окружения не является допуском. Родитель принимает команду без изменения служб, worker получает единственную cache lease и обычный UART guard. Смерть вызывающего процесса не снимает guard с живого worker. Ограничения: RuntimeMaxSec570с, остановка cgroup15с, ожидание родителя600с (+5с kill margin). Терминальный результат выдаётся после записи политики и проверки принадлежности работающего рантайма его обычному service cgroup.

Исключение для поставляемого CODESYS postinst: он сам запускает CODESYS без перенаправления в PID1. После успешного dpkg разрешена одна остановка init.d (45с +5с kill margin) **только** для доказанного нового процесса в собственном worker cgroup: PID, время рождения, root-owned pidfile и отсутствие второго/чужого runtime проверяются перед остановкой. Далее требуется подтверждённое исчезновение процесса и первый штатный запуск PID1. Это не запасной путь после ошибки systemctl. Неопределённая остановка не разрешает новый запуск. Проверки реальных процессов: `scripts/dev/test-service-worker.py`.

Для start/stop повторный запуск под защитой координатора по-прежнему ограничен300с и возвращает `guard_timeout`, а не `port_busy`. Install/uninstall не имеют отдельного таймера координатора: их ограничивает PID1 worker. Проверки: `scripts/dev/test-initd-bounded.sh`, `opt/sa02m-port-coordinator/tests/test_service_guard_timeout.py`.

По истечении времени панель показывает существующее сообщение ошибки, снимает локальное ожидание и обновляет список с тем же ограничением запроса. Отмена браузерного запроса не отменяет принятую системную операцию и не доказывает её завершение. Автоматического повтора POST нет. Ручное обновление при ошибке освобождает кнопку; поздний ответ старого поколения списка не заменяет новый.

Список использует один запрос systemd с ключами `Id`, `ActiveState`, `LoadState` для всех кандидатов установленных служб и один существующий пакет `is-enabled`. Полные однозначные записи связываются только по `Id`; каноническое имя вместо запрошенного alias, неполная или повреждённая запись и отказ пакета возвращают прежние отдельные проверки. Порядок каталога и кандидатов, определение установки, резервные проверки SysV/файлов, состояние процессов CODESYS/MPLC4 и отдельная политика автозапуска сохраняются. Helper публикует допустимый ответ в `/run/sa02m-svcctl/list.json` (0644); `GET services_ctrl.cgi` и `status.cgi?part=services` читают копию моложе10с без sudo или дополнительных запросов manager. Изменение службы в обход helper может быть видно с задержкой до10с.

Модуль `/usr/local/lib/sa02m-service-cache.sh` — единственный дом жизненного цикла кеша и проверки наследуемого дескриптора. До мутации helper под короткой общей блокировкой (не более2с) регистрирует уникальную kernel-backed lease, меняет поколение и удаляет копию. Приватный root-owned каталог `operations/` имеет режим0700, записи —0600, regular/single-link; максимум64 записи по4КиБ. FD8 резервируется до UART guard: занятый или чужой FD отклоняется. Координатор передаёт его только после проверки фиксированным executable verifier: inode, права и реальное исключение независимого flock. Присоединившийся дочерний helper не может завершить участие родителя.

Список собирается без общей блокировки и сохраняется лишь при неизменном поколении и пустом реестре. Пока операция активна или её исход неизвестен, возвращается свежий JSON без публикации кеша. Завершение меняет поколение после всех побочных эффектов и подтверждения терминальных jobs. Запись переживает SIGKILL; PID, op_id, UI-тайм-аут и возраст не доказывают завершение. Незаблокированная запись удаляется только после пакетной проверки всех записанных units: Job пуст и ActiveState не переходный. Запись worker остаётся до выхода его собственного unit; первое свежее чтение выполняет согласование, последующие используют обычный тёплый кеш. Ошибка блокировки/записи/manager не открывает публикацию. Проверки: `scripts/dev/test-service-cache-lifecycle.py`, `scripts/dev/test-service-worker.py`, `scripts/dev/test-status-cache.sh`.

Новый helper требует модуль до запуска; отсутствие означает `cache_module_missing`. Fullrefresh должен завершить старые выполняющиеся helper до совместной замены helper, модуля и координатора; удаление живого lock/реестра недопустимо. Runtime-кеш и leases не переносятся в образ как идентичность устройства.

MPLC использует общую политику `usr/local/lib/sa02m-mplc-policy.sh`. Значения таймеров имеют один источник — `opt/sa02m-mplc/systemd/mplc4.service`: startup45с, stop15с, failure mode terminate, KillMode=mixed. Из него **до** vendor install выводится постоянный drop-in; vendor может переписать base unit, но не отменить этот drop-in. Поддерживаются два проверяемых профиля: legacy oneshot с реально существующим `/etc/init.d/mplc4` и native vendor forking с `/opt/mplc4/start_mplc4.sh`, WorkingDirectory=/opt/mplc4, Restart=always. На fresh install без init.d сначала ставится canonical native template. Эффективные параметры проверяются до и после vendor; неожиданный override, включая infinity, вызывает `mplc_timeout_policy`.

Одна управляемая операция MPLC start/stop имеет абсолютный монотонный бюджет85с, включая настройку автозапуска, команду manager и подтверждение результата. Клиентский timeout не создаёт второго старта: наблюдается тот же job. Успех требует пустого Job, runtime и ожидаемой политики. При неудачном старте выполняется ограниченная остановка того же unit, которая отменяет автоматические повторы native Restart=always, сохраняя саму политику для следующего явного запуска. Остановка подтверждается PID1 и пустым cgroup; `reset-failed` не используется. Неизвестный исход возвращает `mplc_outcome_unknown`, а не успешный результат. Fullrefresh09 сохраняет прежнюю capture/apply таблицу и timestamp: один apply получает65с внутри общего85с бюджета, остаток предназначен для проверки/остановки. Повторного старта или расширения enable/mask policy при ошибке нет. Проверки: `scripts/dev/test-mplc-lifecycle.py`, `scripts/dev/test-mplc-systemd.py`; реальные45+15с проверяются только в явно разрешённом disposable PID1, без vendor runtime и плат.

Корневой helper проверяет идентификаторы до использования в путях, передаёт `op_id` через существующий повторный запуск под защитой координатора и публикует целый JSON атомарной заменой файла. Защита служб RS-485 описана в [контракте владения портами](port-ownership.md); результат веб-команды её не заменяет. Сбой самого vPLC при завершении не скрывается сбросом системного состояния ошибки.

Совместимость: прежний `GET` без `op_id` возвращает последний результат службы; вызов helper без третьего аргумента допустим. Хранится один последний результат на службу. Одновременные команды из разных вкладок могут перезаписать его, и ожидающая вкладка завершится тайм-аутом; чужой результат не выдаётся за её успешное выполнение. Старая панель без проверки `op_id` сохраняет прежнее поведение до загрузки обновлённого JS.

Кнопка моста Modbus→MQTT на вкладке MQTT использует этот же контракт для
`mqtt-bridge`: один POST, сопоставленный результат и проверка списка служб.
После них отдельный свежий `mqtt_status.cgi` подтверждает отображаемое состояние
моста и сохраняет независимые показания брокера. Пока операция ожидается, кнопка
показывает направление команды и остаётся заблокированной вместе с «Сохранить
и применить» и управлением той же службой на вкладке «Управление»; значок сообщает «Остановка моста» или
«Запуск моста». Общие 90 с включают POST и обе проверки. Старый или пришедший
не по порядку ответ статуса не заменяет новый; уход с вкладки делает её прежние
ответы недействительными, но не отменяет уже принятую команду и её общий срок.
Возврат на вкладку сохраняет локальное ожидание. После полной перезагрузки
страницы прежнее ожидание не восстанавливается и POST не повторяется: кнопка
ждёт нового статуса. Неизвестное состояние не определяет действие по тексту
кнопки. Ошибка остаётся рядом с кнопкой; при неопределённом результате действие
заблокировано до следующего успешного чтения статуса. Управление брокером и
политика автозапуска служб этим путём не меняются.

«Сохранить и применить» берёт ту же локальную блокировку до первого POST.
Она сохраняет конфигурацию с `restart:false`, затем последовательно выполняет
сопоставленные `stop` и `start` через существующий service-control и получает
свежий статус MQTT. Один срок 90 с включает сохранение, обе команды, их
результаты и чтение состояния. Это заставляет мост перечитать YAML и сохраняет
конечную семантику применения: мост активен, автозапуск включён. Старый
несопоставленный фоновый restart CGI из этого UI больше не вызывается.
Промежуточный `stop` отключает автозапуск, последующий `start` включает его;
если запуск не удался, мост может остаться остановленным и отключённым.
До завершения всех стадий запрещены повторное сохранение, переключение моста
и команды той же службы из «Управления», включая возврат на вкладку.
Ошибка до подтверждения сохранения не утверждает, что YAML записан. Если
запись подтверждена, а применение не завершилось, локальная ошибка прямо
сообщает это; подтверждение применения не показывается. Следующая стадия
после ошибки или неопределённого результата не отправляется. Автоматического
повтора мутаций нет; дальнейшая команда требует нового явного действия.

Проверки: `scripts/dev/test-service-operations.py` выполняет настоящий CGI и атомарную публикацию; под root он также проверяет полный путь helper → координатор → повторный helper и отказ MQTT при lease. `scripts/dev/test-service-operation-ui.mjs` проверяет корреляцию, блокировку кнопок, общий срок и зависание запроса/тела на каждой стадии. `scripts/dev/test-service-list-batch.py` выполняет настоящий POSIX helper с моделью systemd, сравнивает JSON и проверяет два вызова в обычном случае. `scripts/dev/status-reliability-browser.mjs` проверяет реальные клики и незавершённые HTTP-тела через общий fetch guard в RU/EN на desktop/mobile.

`scripts/dev/test-mqtt-bridge-control.mjs` выполняет функции MQTT и общий
service-control с моделью HTTP и часов: задержку, корреляцию, общий срок,
поздние ответы, блокировку повторных команд и смену вкладки, а также обе
стороны исключения Save/Stop на каждой стадии и частичные ошибки применения.
`scripts/dev/mqtt-bridge-control-browser.mjs` проверяет настоящие клики,
старый ответ после завершения, локальную ошибку и отдельный статус брокера
в RU/EN, обеих темах и двух ширинах. Эти проверки не запускают службы на плате.
