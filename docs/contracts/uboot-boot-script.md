# Контракт: U-Boot boot script (`boot.scr`)

Домашний адрес контракта для формата загрузочного скрипта SA-02m и для правила
«какой payload идёт по умолчанию». Машинная грамматика (имена полей, смещения,
имена файлов) — на английском (`PROTOCOL.md` invariant 5); пояснения — на русском.

Ключевое обещание: **`boot.scr`, собранный этим репозиторием, либо является
корректным U-Boot legacy script image, либо генератор падает громко и ничего не
выпускается.** Второе обещание, такое же несущее: **payload по умолчанию — тот,
на котором плату наблюдали загружающейся.**

Нарушение этого обещания дважды приводило к «мёртвой» плате (2026-08-03,
2026-08-05): образ выпускался с `boot.scr`, который проходил все проверки в
дереве и не загружал ни одну плату. Разбор — `docs/bugs/BUGLOG.md`.

## 1. Формат: 64 + 8 + N, без padding

`boot.scr` — это U-Boot legacy image (`include/image.h`) с `ih_type = 6`
(`IH_TYPE_SCRIPT`). Секцию данных такого образа `source` читает как
**multi-file image**: сначала таблица размеров, потом сам текст скрипта.

```
[0x00 .. 0x3F]   64 bytes  legacy uImage header
[0x40 .. 0x47]    8 bytes  size table: script_len (uint32 BE), 0 (uint32 BE)
[0x48 .. EOF ]    N bytes  текст скрипта, ВЕРБАТИМ, БЕЗ выравнивания
```

- `ih_size  = 8 + N` — покрывает таблицу И данные, не только данные.
- `ih_dcrc  = crc32(table + script)` — не `crc32(script)`.
- **Padding отсутствует.** Скрипт не дополняется до границы 4 байт.

Донорский артефакт с платы, которая загружается, — рабочий пример и якорь всех
проверок:

| Величина | Значение |
|---|---|
| Полный размер | **261** байт |
| Размер скрипта | **189** байт |
| Байты `0x40..0x47` | `00 00 00 bd 00 00 00 00` (`0xbd` = 189) |
| `ih_size` | **197** (`0x000000c5`) |
| Начало текста скрипта | `0x48` |

Арифметика замыкается только при наличии таблицы и отсутствии padding:
`64 + 8 + 189 = 261`. Writer с padding дал бы 264, writer без таблицы — 253.
Именно поэтому проверка `== 261` в тесте — дискриминатор padding.

Если таблицы нет, U-Boot читает первые четыре байта скрипта как длину
(`"# SA"` = `0x23205341`), и плата не доходит до ядра: ни пищалки, ни сети,
восстановление только через FEL.

**Не проверяется намеренно:** `ih_os` (`source` его не смотрит, а два
производителя различаются) и конкретное значение `ih_name` (производители
передают разный `-n`; проверяется только форма «32 байта, NUL-padded»).

## 2. Единственный дом формата — `tools/imaging/uboot-script.py`

Знание о байтах живёт в одном месте; и генераторы, и тест используют его, поэтому
writer и validator не могут разойтись.

| Команда | Назначение |
|---|---|
| `uboot-script.py resolve --repo-root DIR` | путь к payload (см. §3) |
| `uboot-script.py normalize SRC DST` | копия payload с CRLF → LF |
| `uboot-script.py build SRC OUT [--name N]` | mkimage-free reference writer |
| `uboot-script.py validate PATH` | побайтовая проверка (10 утверждений) |

Потребители: `tools/imaging/patch-firstboot-image.sh`,
`tools/debian-rootfs/pack-sa02m-image.sh`, `scripts/dev/test-uboot-bootscr.sh`
(quality row `uboot-bootscr-format`).

`mkimage` (`apt install u-boot-tools`) — **жёсткое требование** обоих
пайплайнов (`make-image.sh` шаг 0, `pack-sa02m-image.sh`). Встроенный writer —
референсная реализация и запасной путь для голой WSL-машины; его выход проходит
тот же validator, что и выход `mkimage`. Validator применяется к результату
**обоих** путей: неверный флаг `mkimage` ловится так же, как ошибка writer'а.

## 3. Payload: default и opt-in

| Файл | Статус |
|---|---|
| `etc/boot.cmd.sa02m.min` | **default** — 189 байт, проверен на плате |
| `etc/boot.cmd.sa02m` | **opt-in**, помечен `UNVERIFIED-ON-HARDWARE` |

**Выбор payload — аргументом командной строки, а не переменной окружения:**

| Producer | Как выбрать не-default payload |
|---|---|
| `patch-firstboot-image.sh` | `--bootcmd <path>` |
| `pack-sa02m-image.sh` | `--bootcmd <path>` |
| `make-image.sh` | `SA02M_BOOTCMD=<path>` (запускается БЕЗ sudo и пробрасывает значение дальше как `--bootcmd`) |

Почему аргумент, а не переменная: оба производителя запускаются через `sudo`,
а `sudo` с `env_reset` срезает окружение. Вернуть переменную формой
`sudo VAR=value cmd` нельзя — в `sudoers(5)` опция `setenv` по умолчанию
**выключена**, и такая команда просто отклоняется. Аргумент переживает `sudo`
на любом хосте, поэтому механизм не зависит от локальной политики sudoers.
`SA02M_BOOTCMD` остаётся удобством для **прямого вызова без sudo** (приоритет:
аргумент → переменная → default) и НЕ является механизмом, на который
рассчитан sudo-путь.

Приоритет и умолчание вычисляет один и тот же `uboot-script.py resolve`, поэтому
у двух производителей не может быть разных умолчаний. Использованный payload
логируется ВСЕГДА: `boot.cmd payload: … (default, hardware-verified)` либо
`WARN: NON-DEFAULT boot.cmd payload in use: …`.

**Скрипты вызываются через интерпретатор** (`sudo bash tools/…`), а не по пути:
все `*.sh` этого репозитория лежат в git с режимом 644, и любая проверка или
вызов, зависящие от x-бита, на свежем клоне молча пропускают шаг. Это пинится
тестом (секция E, реальный прогон вызова через shim-`sudo`, который моделирует
политику по умолчанию: отказ на `VAR=value` и `env_reset`).

Default-скрипт грузит **ровно** `zImage` и `sun8i-a40i-sk.dtb` — цепочки
fallback по именам DTB у него нет. Поэтому `patch-firstboot-image.sh` перед
записью `boot.scr` проверяет наличие обоих файлов на FAT p1 и падает с именем
недостающего.

Что default отдаёт по сравнению с opt-in вариантом (осознанно): `console=tty1`,
`loglevel=3 quiet`, `rw`, `panic=10` (нет авто-перезагрузки после kernel panic)
и fallback по DTB. Сохранено главное — `threadirqs` (защита от IRQ-шторма
I2C/PCA9536, `tools/imaging/README.md`).

**Следствие для образов из `pack-sa02m-image.sh`, прямым текстом:** этот
производитель дополнительно удаляет из DTB `/chosen/stdout-path` (чтобы earlycon
не мусорил в UART0 = RS-485-0/COM1). Вместе с отсутствием `console=` в default
payload это значит, что у таких образов **консоли ядра при загрузке нет вообще**
— ни на UART, ни на tty1. Это осознанный размен: тишина на Modbus RTU против
возможности наблюдать загрузку. Диагностика — по SSH и `journalctl -b` (лог
пишется полностью). Если для отладки нужна консоль, используйте opt-in payload
(`--bootcmd etc/boot.cmd.sa02m`, там `console=tty1`) — но помните его статус
UNVERIFIED-ON-HARDWARE.

**Оба payload'а пришпилены к LF** правилом `boot.cmd.* text eol=lf` в
`.gitattributes`: CR из CRLF-checkout попадает в `setenv bootargs …` буквально,
то есть в командную строку ядра, и сдвигает все смещения выше.

### Процедура промоушена (единственный способ снять UNVERIFIED)

Маркер `UNVERIFIED-ON-HARDWARE` в `etc/boot.cmd.sa02m` проверяется механически
(`scripts/dev/test-uboot-bootscr.sh`, пункт D2) — его удаление роняет beat
`build`. Снять его можно только так:

1. Плата **наблюдалась загружающейся** с `boot.scr`, собранного именно из
   `etc/boot.cmd.sa02m` (не из донорской копии).
2. Факт записан в `docs/bugs/BUGLOG.md`: дата, плата/серийный номер, версия
   образа.
3. Одним изменением правятся: маркер в файле, этот раздел контракта и, если
   меняется default, `DEFAULT_PAYLOAD` в `uboot-script.py` плюс пин D3 в тесте.

Промоушен «по ощущению, что скрипт полнее» — запрещён: именно это и было
источником обоих инцидентов.

## 4. Что этот контракт НЕ гарантирует

Что плата загрузится. Побайтовая проверка + наблюдённые 261/189 байт донора —
максимум доказательств без железа. Подтверждение на плате (прошить образ,
собранный исправленным пайплайном, увидеть пищалку и сеть) — шаг оператора
после merge, а не проверка ревью.
