# Контракт обновления веб: запуск, отмена и восстановление

Интернет-обновление и локальный пакет используют один привилегированный контроллер
`/usr/local/libexec/sa02m-update-control`. Формат подписанного пакета описан в
[OFFLINE_UPDATE_PACKAGE_V1.md](../OFFLINE_UPDATE_PACKAGE_V1.md).

## Авторизация и граница привилегий

CGI проверяют сессию и CSRF до вызова контроллера. Интернет-ветка дополнительно
проверяет свежий `check.json`: отсутствующий, повреждённый или устаревший ответ
даёт `E_CHECK_STALE`; отсутствие более новой версии — `E_NO_UPDATE`.
Пустое тело POST выбирает интернет-обновление; непустое тело должно быть JSON
объектом с единственным строковым полем `confirm_version`. Ошибочный JSON не
должен запускать интернет-обновление.

CGI не записывают root-журнал и не имеют разрешения на произвольный `sudo tee`.
Контроллер принимает только фиксированные операции `upload`, `inspect`, `apply`,
`online`, `cancel`, `factory-reset` и фиксированные пути. Multipart передаётся через stdin,
исходник Python передаётся отдельно. Проверка подписи повторяется при применении,
подтверждённая версия должна совпадать с версией пакета.

## Транзакции и ответы

`control.lock` сериализует управляющие запросы. Загрузка и подготовка дополнительно
берут `update.lock`, который launcher удерживает всё время скачивания и передаёт
runner. Журнал записывается атомарно с синхронизацией. Рабочая транзакция запрещает
замену пакета и запуск другого источника (`E_LOCK`). Повтор того же apply возвращает
тот же `transaction_id` без нового старта. `control.lock` берётся без ожидания:
два «Применить», пришедшие одновременно (двойной клик), дают второму
`E_LOCK` («update control busy»), а не идемпотентный ответ — панель показывает
ошибку; повторное нажатие после ответа первого запроса возвращает тот же
`transaction_id`. Незавершённая транзакция без живого
исполнителя после 120 секунд требует восстановления (`E_RECOVERY_REQUIRED`), а не
перезаписи журнала новым обновлением.

Принятый запуск возвращает HTTP 202 и JSON:
`{"ok":true,"http_status":202,"status":"running","legacy":{"status":"running"},"transaction_id":"…","stage":"validating"}`.
Это подтверждение принятой systemd-задачи, не успешной установки. Используется
`systemctl start --no-block`; окончательный результат получают через GET.
Отказ systemd даёт `E_CMD` и `stage=error`. CGI не пишет `update_status`.

Отмена загруженного, но не запущенного пакета завершает транзакцию `cancelled`.
На стадиях `validating` и `backing_up` ответ содержит `cancel_requested:true`;
runner продолжает до безопасной границы и подтверждает `cancelled` в GET.
Контроллер не останавливает процесс и не удаляет используемый пакет.
После резервного копирования runner под тем же `control.lock` повторно проверяет
отмену и только затем переходит в `applying`. Начиная с `applying` отмена запрещена
(`E_CANCEL`). Ожидающий подтверждения `uploaded` не считается зависшим runner.

## Владение UART и восстановление

До подготовки runner берёт исключительный `maintenance.lock` координатора и
проверяет отсутствие операций/невосстановленных служб. Блокировка наследуется
через self-reexec. Перед изменениями сохраняются активные состояния координатора,
флашера, MQTT и serial gateway. Потребители останавливаются до координатора,
возобновляются после него, только если работали до обновления; enable/masked не
изменяются. Неудачное восстановление не даёт успешного результата.

Долговечный `/var/lib/sa02m-update/maintenance` запрещает новые операции между
аварией, boot recover и verify. Он удаляется после успешной проверки либо полного
отката с восстановлением служб. Boot recover выполняется до UART-служб; проверка
и восстановление их состояния завершаются после загрузки через verify. Откат
файлов с ещё не восстановленными службами остаётся `rolling_back` с
`port_restore_pending:true`. Для snapshot=false boot recover ставит собственный
временный systemd condition guard до запуска UART units. Verify упорядочен после
их boot jobs, затем снимает только guard обновления; ранее остановленные
потребители не запускаются, enabled/masked-настройки не меняются. Чужие drop-ins
не удаляются. Если terminal journal уже записан, а питание пропало перед удалением
maintenance marker, boot recovery завершает удаление marker.

## Совместимость и подготовительный переход

Пакеты новой серии требуют `min_updater=1.0.7.5`. Кроме версии проверяется ответ
`runner capabilities`: `control_v1` и `port_maintenance_v1`. Отсутствующий или
несовместимый runner даёт `E_BOOTSTRAP_REQUIRED` до клонирования и копирования.
Неатомарный legacy rsync fallback удалён; вторым механизмом отката он не является.

| Исходная установка | Путь |
|---|---|
| Старый updater, отсутствующий controller/координатор или незащищённый state | Сначала проверенный checkout и `install.sh --refresh`; затем новый OTA-пакет |
| 1.0.7.5 с защищённым state и требуемыми capabilities | Интернет-обновление или подписанный локальный пакет |
| Незавершённая транзакция | Сначала штатный `runner reclaim` либо boot recovery, затем новый запуск |
| Ярусное назначение `/usr/local/bin/fix-eth.sh` (сторож статического IP, с 1.0.7.19) | Интернет-обновление: доставляется обновлением, следующим за тем, что поставило runner 1.0.7.19 (старый runner файл пропускает, не отказывает). Офлайн-пакет: только собранный с `--min-updater 1.0.7.19` и новее — плата с runner ≤ 1.0.7.18 отклоняет его до раскладки (`E_COMPAT updater < min_updater`); пакет с `min_updater` по умолчанию сторожа не несёт ([OFFLINE_UPDATE_PACKAGE_V1.md](../OFFLINE_UPDATE_PACKAGE_V1.md), «Допустимые назначения») |

Это матрица допуска, а не заявление о завершённых испытаниях всех исходных версий.
Результаты на платах фиксируются отдельно в аудиторском отчёте.

Перед изменением продукта refresh проверяет активные update-юниты, transient
runner, flock и журнал. Незавершённый, повреждённый или неоднозначный журнал,
symlink/hardlink требуют явного восстановления. Старый доступный на запись
`www-data` state не используется как доверенный: терминальный каталог сохраняется
рядом в `sa02m-update.untrusted-*` с режимом 0700; создаётся новый root state 0755,
incoming 0700 и security stamp. Загруженный старым CGI пакет остаётся в карантине
и должен быть загружен заново. Каталог карантина не обслуживается веб-сервером.

## Проверки границ контроллера

`opt/sa02m-update/tests/test_control_cgi.py` выполняет HTTP → настоящий CGI →
контроллер → валидатор с подписанным бинарным multipart; подменяется только systemd.
`test-update-control-boundaries.py` проверяет отмену во время backup, наследование
flock через exec, порядок восстановления служб, отказ старого bootstrap и защиту
миграции state. Старые файловые rollback/health harness изолируют UART-координатор;
проверка композиции и последовательные испытания на платах обязательны отдельно.

## GET — состояние (с 1.0.6.52: мёртвый раннер виден)

`GET /cgi-bin/web_update_apply.cgi` отдаёт поля транзакции (`stage`,
`progress_pct`, `files_done`/`files_total`, `error_code`, `error_message`, …),
`status`/`legacy.status` для старых бандлов и **два новых поля, всегда
присутствующих**:

| Поле | Значение |
|---|---|
| `runner_alive` | `true`/`false` — жив ли процесс/юнит раннера; `null`, когда транзакции нет |
| `stale` | `true`, когда одновременно: `stage` ∈ множеству «идёт» (`validating … rolling_back`), `runner_alive` = `false` и `updated_at` старше `WEB_UPD_STALE_AFTER_S` = 120 с (или не разбирается). Иначе `false` |

**Тест живости** (одно место — `cgi-bin/lib_web_update.sh`
`web_upd_runner_alive`, читается без привилегий; root-копия того же теста — в
`etc/sa02m-web-update-apply.sh`, потому что root-хелпер не должен source'ить
файл, который может писать `www-data`; с 1.0.7.5 CGI-копия считает живым и
`sa02m-update-download.service` — дом онлайн-пути, где launcher делает `exec`
раннера и transient-юнита нет, а root-копия его не считает: launcher и есть этот
юнит, повторный ручной запуск отбивает `launch.lock`). Основной детектор — **pid лока**:
каждая точка входа раннера берёт лок первой, и pid из
`/var/lib/sa02m-update/update.lock` считается живым, когда процесс существует
**и** его `cmdline` содержит `sa02m-update-runner` или `/sa02m-update/runner/`
(переиспользованный pid не считается). Дополнительно — на моменты до лока:
жив pid из легаси-лока хелпера (`/var/lib/sa02m-web-build/update.lock` — фаза
клонирования), **или** `sa02m-update.service` / `sa02m-update-verify.service`
имеет `ActiveState` ∈ `active|activating|reloading` (оба — `Type=oneshot`, у
которых `activating` и есть состояние «выполняется»; `is-active` для них
всегда отвечал бы «нет»), **или** запущен transient-юнит
`sa02m-update-apply-*.service`. Нет `systemctl` — эта половина `false`.

При `stale = true`: `status`/`legacy.status` = `"error"`; `error_code` =
уже записанный раннером код, иначе `"E_RUNNER_LOST"`; `error_message` = уже
записанное сообщение, иначе `update runner is not running (stage=<stage>, last
update <N>s ago) — reboot the board; verification completes at boot`; поле
`log` начинается с человеческой строки «Обновление прервано на этапе
«<стадия>»: перезагрузите плату — при загрузке проверка завершится сама.» —
единственный канал к СТАРОМУ кэшированному бандлу, который `stale` не читает,
а `log` выводит в журнал событий. CGI **никогда не пишет** транзакцию —
починка только `recover`/`verify` при загрузке (или `runner reclaim`).

Панель (`app/status.js`): `stale` — терминальное состояние (опрос
прекращается), строка «Обновление прервано на этапе «…». Перезагрузите плату —
при загрузке проверка завершится сама», прогресс-бар скрыт; `rolled_back` с
`error_message` показывает «Выполнен откат: <причина>». Старый кэшированный
бандл видит `status:"error"` и останавливается по своему легаси-пути (общая
строка «Ошибка обновления. См. Журнал событий.» — честно, но без причины).

## Жизненный цикл apply — гарантии (с 1.0.6.52)

| Этап | Кто выполняет | Что гарантируется | Чем проверено |
|---|---|---|---|
| Запуск из панели | `web_update_apply.cgi` → `sudo -n sa02m-web-update-apply` из воркера fcgiwrap → `exec` раннера | **G1.** Раннер, запущенный из панели, переживает каждый перезапуск служб, который делает его же health-gate: в самом начале `cmd_apply` он читает `/proc/self/cgroup` и, оказавшись в `fcgiwrap.service` (`KillMode=mixed` — `restart fcgiwrap` убивает всю cgroup SIGKILL'ом), перезапускает себя transient-юнитом `sa02m-update-apply-<txn8>` (`systemd-run`, `KillMode=process`), передаёт лок и выходит. **Не действует в обновлении, которое доставляет этот код** на плату ≤ 1.0.6.51: старый раннер `exec`'ит копию самого себя, и весь тот apply идёт под старым кодом (замирает на 85 %, завершается при загрузке — `docs/deployment.md`). Офлайн-путь и запуск по SSH не затрагиваются. Отказ `systemd-run` — «продолжить на месте» (в журнале), не отказ от обновления | `update-cgroup-escape`; на стенде — `systemctl status 'sa02m-update-apply-*'` в состоянии `running` во время `health: restarting fcgiwrap...` |
| Health-gate после deploy | раннер, `health_check` | **G3.** Требуемый юнит считается живым после **двух подряд** `active` в окне `SA02M_UPDATE_HEALTH_SETTLE_SEC` = 30 с (шаг 2 с) — `activating` ждёт, crash-loop (`activating`↔`active`) не проходит на одном сэмпле; `masked`/`disabled`, а также `ConditionResult=no` **при `ConditionTimestampMonotonic != 0`** (условие реально проверялось в эту загрузку; для юнита, старт которого не пытались выполнить, systemd тоже отвечает `no`, и такой enabled-юнит — регрессия, а не выбор оператора) — не требуется; при отказе в журнал идут последнее состояние и выдержка `systemctl status`, причина попадает в `error_message` (`E_HEALTH`). **Не прочитанный манифест — отказ, а не «нечего проверять»** (с 1.0.6.54): если чтение из манифеста списков `units_active`/`http_url`/`version_file`/`version`, наборов перезапуска (`restart`, `restart_if_active`, `restart_if_changed`) или `enable[]` завершилось ошибкой, шаг проваливается с `error_message` = `manifest read failed: …` (`E_HEALTH`, откат) и ничего не перезапускает; ключ, **отсутствующий** в манифесте (пустой `http_url`, нет `units_active`), по-прежнему означает «проба не настроена». Ошибка чтения `daemon_reload` — `daemon-reload` выполняется (безопасная сторона) | `update-conditional-restart` run 6, run 7; `health-gate-operator-disabled` |
| Recover при загрузке | `sa02m-update-recover.service` (`Before=nginx fcgiwrap`) | **G2.** Целое дерево (`files_done == files_total`, `VERSION` = `target_version`) на `verifying`/`committing` **никогда не откатывается по причине порядка загрузки**: recover не перезапускает и не проверяет ничего сам — ставит `boot_verify_pending=true` и запускает `sa02m-update-verify.service` (`--no-block`; fallback — transient-юнит с теми же `After=`); если запустить некого — транзакция остаётся на `verifying` (следующая загрузка повторит, панель покажет `stale`). Неполное дерево (и `applying`/`rolling_back`) откатывается как раньше (`E_POWER` + причина; по журналу, а если staging потерян — по архиву, атомарно и с исходом «rollback incomplete» при любом сбое: **G6**), но в контексте загрузки откат **ничего не перезапускает** — только `daemon-reload`: все юниты стартуют с восстановленного дерева, как только recover выйдет (набор перезапусков здесь загнал recover в его же `TimeoutStartSec=300` на стенде 1.135 — откат остался на `rolling_back` с локом и сторожем 0). Плата в таком остатке сходится за одну загрузку: журнал воспроизводится повторно, лок снимается, сторож восстанавливается по политике — в том числе когда последняя строка журнала оборвана (запись прервана питанием или нехваткой места: такая строка пропускается и пишется в журнал обновления, её файл не был переименован; с 1.0.6.54 — до этого откат падал на ней и каждая загрузка повторяла падение). SIGTERM от таймаута превращается в выход с EXIT-trap: лок остаётся для следующего recover, но сторож возвращается сразу | `update-recover-boot` R1–R3, R5–R7, R10, U1 |
| Остаток без перезагрузки | `runner reclaim` (через `scripts/sa02m-update-remedy.sh`) | Тот же recover во время работы для транзакции, чей раннер исчез: при живом раннере (лок занят) — ничего не делает и выходит с кодом 3 (скрипт на нём останавливается); `rolling_back`/`applying` — откат дозавершается с перезапусками (веб поднят); целое `verifying`/`committing` — **сначала наборы перезапусков, до которых погибший apply не дошёл** (fcgiwrap, `nginx -t` + reload, `restart[]`/`restart_if_*`; отказ `nginx -t` — откат с `E_HEALTH`), затем `sa02m-update-verify.service`, который запускается сразу и делает enable+tmpfiles+health-gate; терминальная стадия с оставшимся локом — лок снимается, сторож восстанавливается. При загрузке (recover) наборы перезапусков не выполняются никогда. На плате `reclaim` ещё не выполнялся — гарантия харнесса. Рецепт — `docs/deployment.md` «Ремонт застрявшего обновления без перезагрузки». Что не делается само: без перезагрузки и без вызова `reclaim`/нового apply остаток лежит — периодического вызова нет (решение о таймере — отдельное) | `update-recover-boot` R8a–e, M |
| Проверка после загрузки | `sa02m-update-verify.service` (`After=recover nginx fcgiwrap sa02m-devices-api`, static — без `[Install]`) → `runner verify` | Только `enable[]` + tmpfiles + health-gate, **без** restart-наборов (всё уже стартовало с задеплоенного дерева). Успех → `done`; отказ (включая отказ шага `enable[]` — непрочитанный манифест, с 1.0.6.54) → откат с `E_HEALTH` и причиной, verify не обрывается на середине. Идемпотентно: терминальная стадия — no-op, потеря питания посреди verify — повтор при следующей загрузке | `update-recover-boot` R4, R4d |
| Статус для панели | `web_update_apply.cgi` GET | **G4.** Транзакция без живого раннера сообщается как `stale` не позже 120 с после последнего `updated_at` (поля выше); панель останавливает опрос и называет следующий шаг | `web-update-apply-guard` секция G, `test-web-update-semver` раздел F |
| Runtime-watchdog | раннер, `install_imaging_lock`/`cleanup_imaging_lock`/`load_runtime_wdt_prev` | **G5.** Значение `RuntimeWatchdogUSec`, снятое на окно apply, восстанавливается после каждого завершённого apply/verify/rollback — через `exec`, cgroup-escape и перезагрузку: оно хранится в транзакции (`runtime_wdt_prev_usec`; пусто = снимать было нечего); транзакция старого хелпера без поля при живом `0` восстанавливает политику из `sa02m-watchdog.conf`, без политики — ничего не выдумывает и пишет WARN; новый hold над менеджером, уже стоящим на 0 под политикой (остаток убитого recover), запоминает значение политики, а не 0 | `update-recover-boot` W1–W3, `watchdog-hold` |
| «Перезагрузка» в панели | `reboot.cgi` | Живой раннер на `applying|verifying|committing|rolling_back` → `{"ok":false,"error_code":"E_UPDATE_RUNNING","error_message":"update in progress (stage=…)"}`, тост «Идёт обновление — перезагрузка отложена»; **`stale`-транзакция остаётся перезагружаемой** — перезагрузка и есть её путь восстановления. CSRF по-прежнему проверяется раньше | `web-update-apply-guard` секция R, `cgi-csrf-policy` |
| Второе «Применить» | controller + launcher + runner | **G7.** Ни живая, ни незавершённая мёртвая транзакция не перезаписывается. ### Общий журнал со сбросом конфигурации

`web_factory_reset.cgi` сохраняет обязательные `confirm_phrase=SA02M-RESET`
и `backup_ok=true`, session и CSRF. Подготовка журнала и асинхронный запуск
проходят через fixed root controller под теми же control/update locks.
Повтор возвращает прежнюю транзакцию; OTA и reset не заменяют журналы друг
друга. Update-cancel не отменяет reset. Общий валидатор принимает стадии
`confirmed/wipe/apply/verify` и source `web` только для `operation=factory_reset`.

OTA recovery не восстанавливает reset как обновление. Незавершённый reset,
включая `error`, сохраняется с диагностикой `E_RECOVERY_REQUIRED`. Требуется
root-проверка соответствия `transaction.json` и каталога `rollback/factory-*`
перед запуском `/usr/local/libexec/sa02m-factory-reset-runner rollback`.
Этот runner выбирает последний каталог: при нескольких несопоставленных
каталогах автоматический запуск запрещён; требуется ручной разбор.
Восстановление reset после физического отключения питания в текущем аудите
не проверено. Новый controller не расширяет эту гарантию.
