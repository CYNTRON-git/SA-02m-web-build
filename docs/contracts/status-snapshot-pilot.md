# Пилот фонового кэша dashboard

Пилот устанавливает только восемь файлов из `manifest.json` пакета. Он не доставляет остальные изменения ветки Home API, не меняет общую версию образа или `/var/lib/sa02m-web-build/deployed_commit`, не запускает `install.sh`/`update-www-only.sh`, не перезапускает MQTT, правила, MPLC или CODESYS. Функциональный контракт — [status-polling.md](status-polling.md).

## Подготовка на рабочей машине

После независимого review и фиксации изменений отдельным commit:

```bash
python3 scripts/pack-status-cache-pilot.py --base 36084cf --ref HEAD --output /tmp/status-cache-pilot
```

Скрипт читает только Git-объекты указанного commit. Архив содержит payload, SHA-256 каждого файла, точные назначения/режимы и `expected_before_sha256` из базы. Выходной каталог должен отсутствовать. Не заменять его произвольным архивом всего `www/` или `etc/`.

## До установки на 192.168.1.135

1. Проверить SSH fingerprint по действующей карточке доступа. Создать новый каталог `/root/sa02m-dashboard-pilot-<12 символов commit>-<24 случайных hex>` с владельцем root и режимом 0700. Все родители staging должны принадлежать root и запрещать запись группе/остальным; симлинки запрещены. Передать архив как `pilot.tar.gz` и Git-рецепт `recipes/scripts/status-cache-pilot-transaction.py` из этого же архива как `transaction.py`, оба с режимом 0600. Проверить транспортный SHA-256. Не извлекать произвольные пути архива на плате.
2. Запустить `/usr/bin/python3 -I "$stage/transaction.py" preflight --stage "$stage"`. Helper проверяет точный whitelist восьми назначений, источники, порядок, режимы, группы, все SHA-256 и ограниченный набор recipe-файлов. Сверяет текущие файлы с `expected_before_sha256`: `null` требует отсутствия. Симлинк, hardlink, специальный/слишком большой файл, неизвестный архивный путь или drift останавливают процедуру. Это первая установка: уже существующая политика collector требует отдельного разбора.
3. Preflight сохраняет immutable `preflight.json`: SHA-256 и метаданные каждого файла, `is-active`/`is-enabled`, device/inode/владельцев/режимы всех родителей. Apply повторно сверяет их, сохраняет ограниченно прочитанные байты старых файлов в root-only `backup-N` и durable `state.json` в том же staging. Новый stage не заменяет предыдущий журнал; повтор apply запрещён. Бэкап хранить до принятия результата оператором.
4. Записать состояние `nginx`, `fcgiwrap`, `mosquitto`, `sa02m-modbus-mqtt`, `sa02m-rules`; свободную память, loadavg; версии и конфигурацию блоков. `HARDWARE=0` не изменять. Снять браузерный baseline в новом контексте без sessionStorage, задержку HTTP и времена появления основных карточек.

## Доставка

Запустить `/usr/bin/python3 -I "$stage/transaction.py" apply --stage "$stage"`. Для этого пилота записи выполняет только включённый в Git-пакет helper, в одной board-side транзакции. Он открывает родителей через `O_DIRECTORY|O_NOFOLLOW`, закрепляет дескрипторы и сверяет сохранённые device/inode/владельцев/режимы перед операциями и после них. Каталоги web-root могут принадлежать `www-data`; менять их владельца или права целиком не требуется. Наблюдаемая подмена каталога или симлинк останавливают транзакцию; root-записи никогда не разрешаются через повторное раскрытие пути web-root.

Существующие файлы читаются через `O_NOFOLLOW` с пределом 2 MB и повторной проверкой inode/метаданных. Каждый новый файл создаётся через `O_EXCL` со случайным именем, записывается и получает права через свой дескриптор. После `fsync` журнал сохраняет ожидаемый новый inode; `rename` использует закреплённый `dir_fd`. Новое назначение публикуется через Linux `renameat2(RENAME_NOREPLACE)`: внезапно появившийcя путь не перезаписывается. Проверяются SHA-256/uid/gid/mode и идентичность inode. Родители, конечный файл и временный файл проверяются на concurrent drift; обнаруженный drift не перезаписывается автоматическим откатом. Журнал сохраняется для разбора и безопасного восстановления.

Гарантия для замены существующего файла: дескрипторы и no-follow исключают перенаправление root-записи через подставленный путь; проверки до/после обнаруживают наблюдаемый drift. Это не атомарное сравнение старого inode и замена (CAS): изменение в узком промежутке между последней проверкой и rename может быть заменено. Даже в этом случае rename заменяет саму запись каталога, не пишет в цель симлинка. Откат применяет ту же границу и отказывается от неизвестного текущего inode.

Порядок фиксирован: общий `status.cgi` до collector-wrapper, helper и Python до unit, JS/i18n до `index.html`. Владелец каждого файла — root, группа и режим — из строгого manifest. `sa02m_atomic_install` с pathname-аргументами в этом пилоте не используется. Helper не принимает произвольные назначения или обходные production-флаги.

После успешной проверки файлов helper выполняет `daemon-reload` и `enable --now` только нового collector, проверяет active/enabled. Для приёмки:

```bash
systemctl is-active sa02m-status-cache.service
systemctl is-enabled sa02m-status-cache.service
systemctl show sa02m-status-cache.service -p User -p Group -p MemoryCurrent -p CPUUsageNSec
```

Перезагрузка платы и fcgiwrap не нужны. `index.html` меняет `r=dashboard1` для двух изменённых JS-файлов, поэтому браузер получает новый код без ручного сброса кэша. Версия `v=1.0.7.36` остаётся версией базы пилота.

## Приёмка

- Без cookie новый CGI возвращает `error: unauthorized`. С действующей сессией `status_snapshot.cgi` выдаёт один JSON с `schema:1`, исходным временем измерений всех включённых частей и состояниями ошибок.
- После запуска сборщика дождаться первого заполнения медленных частей. Затем закрыть браузеры, сравнить два снимка через интервал: `priority._status_meta.measured_at` изменяется независимо от HTTP-клиентов. `/run/sa02m-dashboard` находится в tmpfs; постоянных телеметрических файлов на eMMC нет.
- Новая браузерная сессия получает все готовые карточки одним ответом. Проверить CPU/температуру/ОЗУ/диск, сеть, uptime, накопители, нагрузку, систему, службы, RS-485; отсутствие JS errors; два обновления. Сравнить с baseline, сохранить p50/p95 HTTP и времена заполнения. Несколько параллельных читателей не создают дополнительных сборщиков.
- `HARDWARE=0` остаётся выключенным; возраст аппаратного снимка неизвестен. Не нажимать реальные аппаратные кнопки ради теста: барьер старого снимка проверяется автоматическими тестами.
- При остановке только сборщика уже показанные значения не освежаются временем HTTP-ответа; интерфейс отмечает отказ/устаревание. Возврат сборщика восстанавливает обновления. Для этого теста systemd по умолчанию удаляет RuntimeDirectory при stop, что честно даёт ошибку endpoint.
- Проверить неизменность состояния служб дома и отсутствие новых ошибок collector/journal. Записать измеренную память и CPU за несколько минут; `MemoryMax=96M` — ограничение, а не ожидаемое потребление.
- Проверка автозапуска: enable и зависимости unit, затем холодный старт **одного сборщика**. Не называть это проверенным power-cycle всей платы.

## Откат

Запустить `/usr/bin/python3 -I "$stage/transaction.py" rollback --stage "$stage"` из сохранённого root-only staging. Helper сначала проверяет родителей, SHA-256 бэкапов и точные текущие inode/метаданные всех восьми файлов. При неизвестном изменении откат отказывается от записи; разбирать drift по журналу, не удалять чужие изменения. Тот же механизм с дескрипторами останавливает и отключает только `sa02m-status-cache.service`, атомарно возвращает прежние файлы с uid/gid/mode, удаляет только точные новые файлы и выполняет `daemon-reload`. Сохранённые состояния сервиса восстанавливаются. Прерывание между rename и обновлением журнала распознаётся по заранее сохранённому inode; повторный откат допустим. Проверить HTTP, вход и прежний порядок опроса. Не распаковывать общий старый web-root поверх других параллельных доработок.

Автоматические fixture-регрессии без служб и оборудования: `python3 scripts/dev/test-status-cache-pilot-transaction.py`. Они проверяют подмену родителей/симлинки, враждебные временные и конечные пути, инъекции manifest/архива, concurrent drift и восстановление после apply/прерывания. Production CLI требует Linux и uid 0; fixture-тесты вызывают ограниченное ядро через дескриптор временного дерева.

## Штатная установка

`03-webserver.sh` и `update-www-only.sh` вызывают `install-status-cache.sh` после доставки web-root. Установщик применяет общую политику служб: сохраняет осознанное disabled/masked состояние. Он заменяет только три системных файла атомарно и перезапускает только сборщик. Старый OTA без этих системных файлов остаётся совместимым: новый frontend один раз обнаруживает отсутствие snapshot endpoint/сборщика и использует прежний ограниченный планировщик. Для включения нового режима на такой плате нужен штатный refresh или этот пилот; один web-only OTA не объявляется установкой службы.
