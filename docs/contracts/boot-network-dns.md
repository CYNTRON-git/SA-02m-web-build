# Контракт: DNS после загрузки (`/etc/resolv.conf` не бывает пустым)

Домашний адрес механизма, который гарантирует резолвер на загруженной плате
SA-02m независимо от того, успел ли `ifup` доработать до конца. Машинная
грамматика (имена файлов, юнитов, ключей конфигурации) — на английском
(`PROTOCOL.md` invariant 5); пояснения — на русском.

Смежный контракт: `docs/contracts/ethernet-iface-naming.md` — там живут
канонические имена `eth0`/`eth1`, ворота udev и шов «панель ↔ сторонний
писатель» в `interfaces.d`. Здесь — только то, что происходит **после**
переименования: гонка `ifup` с поздним carrier и её последствие для DNS.

---

## 1. Гарантия

> На каждой загрузке настроенной SA-02m `/etc/resolv.conf` содержит хотя бы
> один `nameserver` и имя резолвится — насколько бы поздно ни поднялся линк
> PHY, — а `systemctl --failed` пуст.

Гарантия сформулирована на **фактической пересборке резолвера**, а не на «`ifup`
вернул 0». Сегодня это совпадает только случайно.

Две половины, отказывающие независимо:

| Половина | Что обеспечивает | Кто |
|---|---|---|
| **DNS** | резолвер пересобирается **независимо** от того, дошёл ли `ifup` до конца | `sa02m-dns-ensure.sh` + `sa02m-dns-ensure.service` + два места в лестнице восстановления |
| **Чистая загрузка** | `ifup@eth0` и `networking.service` перестают падать | `sa02m-wait-carrier.sh` + два drop-in'а |

Ни одна не заменяет другую: без первой DNS остаётся лотереей на одну неудачную
загрузку, без второй образ уезжает с двумя красными юнитами.

## 2. Отказ, который это лечит

Цепочка, наблюдавшаяся на стенде `192.168.1.136` (загрузка 2026-08-21):

```
переименование end0 -> eth0 даёт uevent
  -> /lib/udev/ifupdown-hotplug видит eth0 как `auto` (fallback-ветка)
  -> systemctl start ifup@eth0            (T+16.3)
  -> шаг `gateway` статического метода: ip route add default
     -> "Error: Nexthop device is not up"  (carrier ещё не согласован, T+18.3)
  -> ifup ОБРЫВАЕТСЯ ДО стадии if-up.d
  -> /etc/network/if-up.d/000resolvconf НЕ ВЫПОЛНЯЕТСЯ
  -> resolvconf никогда не обновляется -> /etc/resolv.conf ПУСТ
  -> networking.service (T+22.2) делает ifup -a и падает на уже назначенном
     адресе: "RTNETLINK answers: File exists"
```

Плата при этом пингуется и отдаёт панель — отказ **молчаливый** ровно до первой
попытки разрешить имя: обновление веба падает с
`Could not resolve host: github.com`.

Ключевой факт: `/etc/resolvconf/resolv.conf.d/base` на плате есть, он корректен
(два публичных nameserver'а), и ручной `resolvconf -u` немедленно чинит DNS.
**Никто на плате не запускал `resolvconf -u`** — единственным триггером был хук
`if-up.d`, который при упавшем `ifup` не выполняется. Отсутствие пути «в любом
случае» и есть дефект.

Маршрутную половину того же отказа закрыли в 1.0.3.27 (`fix-eth.sh` научился
восстанавливать default-маршрут при `linkdown`); DNS-половину — нет. См.
`docs/bugs/BUGLOG.md`, запись от 2026-08-21.

## 3. Механизм — две ступени резолвера

`/usr/local/sbin/sa02m-dns-ensure.sh [<iface>|--all]`, идемпотентный, **всегда
выходит с кодом 0**.

1. **Запись интерфейса.** Для каждого целевого интерфейса читает
   `dns-nameservers` (и `dns-search`/`dns-domain`) из
   `/etc/network/interfaces.d/<if>.conf`, валидирует каждый токен строгим
   IPv4/IPv6-регэкспом и — **только если `/run/resolvconf/interface/<if>.inet`
   отсутствует** — подаёт запись через `resolvconf -a <if>.inet`. Имя записи то
   же, что использует `000resolvconf`, поэтому настоящий `ifup` позже
   перезаписывает её штатно, а `if-down.d/resolvconf` штатно удаляет — утечки
   нет.
2. **Подметание fallback'ом.** Если после этого в `/etc/resolv.conf` по-прежнему
   нет ни одной строки `nameserver`, выполняется `resolvconf -u`, и
   `resolv.conf.d/base` материализуется.

**No-op**, когда запись уже есть, когда конфиг не объявляет nameserver'ов
(DHCP-интерфейс: своей записью владеет `dhclient`), когда `resolvconf` не
установлен и когда конфиг не разбирается.

**Пишет в журнал только когда действительно что-то записал** (`logger -t
sa02m-dns-ensure`). Это сознательно: плата, пишущая эту строку каждую загрузку,
— видимый сигнал, что `ifup` всё ещё падает. Делать этот лог безусловным или
молчаливым — регресс.

### Где он вызывается

| Точка вызова | Зачем |
|---|---|
| `sa02m-dns-ensure.service` (`After=networking.service`, `WantedBy=multi-user.target`) | детерминированный проход, не зависящий ни от одной ветки лестницы восстановления |
| `etc/fix-eth.sh` — рядом с восстановлением default-маршрута и после успешного восстановления | «кабель пришёл позже» |
| `usr/local/sbin/sa02m-eth-coldboot.sh` — на **обеих** ветках, включая ту, что делает `continue` при `carrier already up` | ровно на этой ветке дальше по лестнице не выполняется ничего |

Юнит обязателен — но **не** по той причине, что была верна до этого изменения.
Ветка `carrier already up, skip` в `sa02m-eth-coldboot.sh` больше не «дыра»:
именно она теперь и зовёт ступень. Причина в другом — оба вызова из лестницы
условны, и условия не наши:

- у `fix-eth.sh` есть ранние `return 0` (нет carrier; идёт bootstrap ifupdown),
  и он вообще не выполняется, если `net-watchdog.service` выключен;
- `sa02m-eth-coldboot.service` несёт `ConditionPathExists=…/eth0.conf` и может
  быть выключен оператором;
- оба зовут ступень из своей ветки, то есть работают ровно настолько, насколько
  верны их собственные предусловия.

Юнит — единственный проход, не зависящий **ни от одной** из этих ветвей. Это и
есть его работа: не «покрыть случай, который больше никто не покрывает», а
«покрыть случай, когда не сработало ничего».

## 4. Механизм — ограниченное ожидание carrier

`/usr/local/sbin/sa02m-wait-carrier.sh <iface>|--auto`: опрашивает
`/sys/class/net/<if>/carrier` раз в секунду до `1` или до истечения бюджета;
**всегда выходит с кодом 0**.

- Бюджет — `IFUP_CARRIER_WAIT_SECS` в `/etc/sa02m_network.conf`, по умолчанию
  **10 с**, `0` полностью выключает. Бюджет **общий** на все интерфейсы одного
  запуска.
- **Жёсткий потолок 120 с** внутри скрипта. `TimeoutStartUSec` у `ifup@` и
  `networking` — 5 минут; ожидание, приблизившееся к нему, превратило бы
  поздний PHY в FAILED-юнит, то есть ровно в тот отказ, который здесь лечится.
  Большее значение обрезается **с записью в журнал**, а не молча.
- Значение **читается**, а не `source`-ится: файл правится руками, а скрипт
  выполняется от root перед каждым `ifup`. Извлекаются только цифры —
  allow-list на границе (`web-code-rigor.md`).
- Перед опросом интерфейс поднимается (`ip link set <if> up`), потому что ядро
  отвечает `-EINVAL` на чтение `carrier` у административно опущенного
  устройства; без этого ожидание никогда не увидело бы живой линк и тратило бы
  весь бюджет каждую загрузку. `ifup` поднимает линк сам через несколько секунд
  — шаг лишь переносится раньше.
- Длительность ожидания пишется в журнал **каждый запуск** (`logger -t
  sa02m-wait-carrier`) — это телеметрия, по которой бюджет 10 с подтверждается
  или пересматривается **по измерению**, а не по ощущению.

### Почему drop-in'ы, а не `pre-up` в конфиге

`/etc/systemd/system/ifup@.service.d/sa02m-carrier-wait.conf` → `%I`
`/etc/systemd/system/networking.service.d/sa02m-carrier-wait.conf` → `--auto`

1. **Форма `interfaces.d/<if>.conf` не меняется.** У файла три писателя
   (установщик первой записью, ремонт `ensure_gw_dns`, панель через
   `apply.cgi`) плюс сторонний KLogic; чужая строка переживает сохранение из
   панели, но уничтожается первой записью установщика с `--ip`, а удаление
   ключа `gateway` заставило бы `ensure_gw_dns` вернуть его обратно — два
   писателя подрались бы в файле, который решает, доступна ли плата.
   Полное описание писателей — `ethernet-iface-naming.md` §5.
2. `ExecStartPre` выполняется **до** `ifup` и потому **не держит** ifupdown-lock
   во время ожидания; строка `pre-up` держала бы.
3. Живое применение из панели зовёт `/sbin/ifup` **напрямую**, мимо юнита, —
   оператор, сохраняющий настройки сети, не платит ни секунды задержки.

Нужны **оба** drop-in'а: с одним только `ifup@` `networking.service` успевает
запустить свой `ifup -a`, пока наш pre-step ещё ждёт, поднять интерфейс слишком
рано самому и вернуть ту же ошибку. С ожиданием на обоих путях побеждает тот,
кто начал первым, а второй видит интерфейс в `/run/network/ifstate` и
пропускает его — `File exists` исчезает как следствие, без смены владельца.

## 5. Что этот механизм НЕ делает

- **Не трогает линк, адрес и маршрут.** Только резолвер. Живую плату он
  выбить из сети не может — это и было причиной отвергнуть более дешёвый
  вариант «`fix-eth.sh` переподнимает интерфейс, когда DNS пуст».
- **Не удаляет** работающий резолвер: ступень 1 добавляет запись только когда
  её нет, ступень 2 работает только когда `nameserver` нет вообще.
- **Не меняет** форму `interfaces.d/<if>.conf`, ни одного поля JSON в CGI, ни
  одного ключа конфигурации, ни одного топика MQTT.
- **Не расширяет** права `www-data`: хелперы выполняются от root из root-овых
  юнитов и в sudoers-список панели не добавляются.

## 6. Деградация

| Условие | Поведение |
|---|---|
| хелпер отсутствует (частичный деплой) | вызовы в `fix-eth.sh` / coldboot защищены `-x` → пропуск, сегодняшнее поведение |
| `resolvconf` не установлен | тихий no-op, код 0 |
| конфиг не разбирается | не пишется ничего (никогда частичной или угаданной записи), код 0 |
| `resolvconf -a` / `-u` вернул ошибку | строка в журнал, код 0 |
| бюджет ожидания истёк | ровно сегодняшнее поведение — `ifup` идёт как шёл |
| `IFUP_CARRIER_WAIT_SECS=0` | ожидания нет вовсе, никаких побочных эффектов |

Ни одна ветка не может уронить юнит: безусловный `exit 0` в обоих хелперах
плюс префикс `-` у обоих `ExecStartPre`.

## 7. Достижимость обновлением по воздуху (OTA)

Достижимость складывается из **двух** независимых условий, и второе легко
упустить:

1. **Файл доезжает** — определяется `DST_RE` в `etc/sa02m-update-runner.sh` (и
   его копией в `scripts/pack-offline-update.py`): разрешены
   `/usr/local/{sbin,lib,libexec}/` и `/etc/systemd/system/sa02m-` (совпадение
   по префиксу).
2. **Юнит включается** — определяется списком `services.enable` в манифесте.
   Апдейтер включает (`systemctl enable`) **только** то, что перечислено там
   (`etc/sa02m-update-runner.sh`, цикл «enabled after apply»). Доставки файла
   недостаточно: без записи в списке симлинк в `multi-user.target.wants` не
   создаётся никогда, и приехавший юнит остаётся мёртвым навсегда.
   Поэтому `sa02m-dns-ensure.service` внесён в `services.enable` **в обоих**
   генераторах манифеста — онлайновом (`etc/sa02m-update-runner.sh`) и
   офлайновом (`scripts/pack-offline-update.py`); запись только в одном означала
   бы, что два пути обновления расходятся. Включение идемпотентно, а цикл
   апдейтера терпит любую ошибку (`systemctl enable … || true`), поэтому
   уронить установку обновления оно не может.
3. **…но на онлайновом пути запись в списке начинает действовать только со
   СЛЕДУЮЩЕГО обновления.** Офлайновый пакет несёт манифест, собранный на
   машине разработчика, — там новый список работает сразу. Онлайновое
   «Обновление веб» собирает манифест **на самой плате, тем апдейтером, который
   на ней уже стоит**, и делает это ДО развёртывания:
   `prepare_github_overlay` строит манифест из встроенного Python старого
   апдейтера, затем `self_reexec_before_deploy` пере-запускает тот же старый
   бинарник, и только после этого файлы попадают на диск. Значит плата,
   приезжающая с апдейтера < 1.0.6.6, получает юнит **выключенным**.
   Эту одноразовую дыру закрывает **bootstrap-шим** в
   `usr/local/sbin/sa02m-eth-coldboot.sh` — единственном месте, которое
   одновременно доезжает по OTA и уже включено на каждой установленной плате
   (`scripts/02-network.sh`). Шим одноразовый (маркер
   `/var/lib/sa02m-net/dns-ensure-enabled.once` пишется ДО попытки включения),
   трогает только состояние `disabled` (`enabled`/`static`/`masked` — это уже
   чьё-то решение, и оно не переопределяется), и никогда не роняет вызывающего.
   **Условие удаления шима:** когда во всём поле апдейтеры ≥ 1.0.6.6, оба
   генератора справляются сами и шим — мёртвый груз; блок помечен в коде.

| Файл | Приезжает по OTA? |
|---|---|
| `/usr/local/sbin/sa02m-dns-ensure.sh` | **да** |
| `/usr/local/sbin/sa02m-wait-carrier.sh` | **да** |
| `/usr/local/sbin/sa02m-eth-coldboot.sh` | **да** |
| `/etc/systemd/system/sa02m-dns-ensure.service` | **да** (префикс `sa02m-`) — и он же в `services.enable`, иначе юнит приехал бы мёртвым |
| `fix-eth.sh` | нет — и причина не в `DST_RE`: репозиторный путь `etc/fix-eth.sh` вообще не отображается `map_dst` (тот берёт из `etc/` только `sa02m-*`), поэтому до проверки префикса дело не доходит |
| оба drop-in'а `*.service.d/sa02m-carrier-wait.conf` | нет — каталог не начинается с `sa02m-` |

Следствие, точно: **вся DNS-гарантия (§3) достигает поля по OTA** — ради этого
ступени и дан собственный юнит, ради этого он внесён в `services.enable`, и
ради онлайнового пути существует шим. Что именно получает плата, обновившаяся
онлайн с апдейтера < 1.0.6.6:

| Момент | Что работает |
|---|---|
| сразу после обновления | ничего нового: юнит лежит выключенным, шим ещё не запускался |
| первая загрузка после обновления | проход ступени есть — **если** отработал `sa02m-eth-coldboot.service` (включён на каждой установленной плате, но несёт `ConditionPathExists=…/eth0.conf` и может быть выключен оператором): он зовёт ступень на обеих ветках, и тот же запуск включает `sa02m-dns-ensure.service` |
| вторая и последующие загрузки | полный механизм: и проход из лестницы, и независимый от ветвей юнит |

То есть **не хватает ровно одной загрузки** до того, как заработает независимый
от лестницы юнит, который §3 называет обязательным. На этой одной загрузке
покрытие держится на лестнице — а значит ровно с теми оговорками, что перечислены
в §3: если `sa02m-eth-coldboot.service` выключен или его `ConditionPathExists`
не выполнено, первая загрузка после обновления остаётся без ступени вовсе. Это
и есть точная цена онлайнового пути; говорить «ни одна загрузка не остаётся без
ступени» было бы сильнее, чем §3 позволяет.

**Только `enable`, без `start` — сознательное решение, с названной ценой.**
Юнит `Type=oneshot`, его работа — проход на загрузке, а список `restart[]`
апдейтера предназначен для долгоживущих служб и питает health-проверку. Тот же
выбор сделан в установщике (`sa02m_svc_apply … infra`, без `start`), так что
пути «установка» и «обновление» не расходятся. **Цена:** после обновления и до
следующей перезагрузки ступень на плате не работает. Для онлайнового обновления
это безобидно (плата только что разрешила имя сервера обновлений, значит DNS у
неё есть); для офлайнового обновления платы, у которой DNS уже мёртв, ступень
включится только со следующей загрузкой — вручную это `systemctl start
sa02m-dns-ensure.service`. Апдейтер плату не перезагружает.

Ожидание carrier (§4) требует полной переустановки
(`install.sh` / `offline-full-update.sh`) или нового образа; для золотого образа
это не ограничение, так как установщик там выполняется. Расширение списка
`DST_RE` — изменение поверхности безопасности апдейтера и решается отдельно.

## 8. Честность: что проверено и чем

| Утверждение | Чем подтверждено |
|---|---|
| цепочка отказа (§2) | журнал загрузки стенда 192.168.1.136 от 2026-08-21 + чтения с платы (`ifquery --allow`, `/lib/udev/ifupdown-hotplug`, пустой `/run/resolvconf/interface/`, рабочий `resolvconf -u` руками) |
| `ifup@` `TimeoutStartUSec` = 5 мин; systemd 255 | прочитано на плате |
| разбор конфигов, обе ступени, идемпотентность, деградация, границы ожидания | `scripts/dev/test-iface-dns-ensure.sh` (строка реестра `iface-dns-ensure`) |
| ожидание завершается на порту без линка | **только** `scripts/dev/test-iface-dns-ensure.sh` (истечение бюджета с `rc=0`, потолок, `=0` как выключатель). Хронометраж на стенде против постоянно бескарьерного `eth1` **запланирован, но не выполнялся** — см. строку ниже. Когда его выполнят, честная граница остаётся: у `eth1` нет стансы `auto`, поэтому это проверка *хелпера*, а не загрузочного пути |
| **сам фикс на реальном железе** | **НИКОГДА НЕ НАБЛЮДАЛСЯ.** На момент этой правки ни один пункт §9 не выполнен: ни один прогон FR-CABLE (ни до, ни после фикса), ни одной холодной загрузки с этой веткой, ни одного запуска хелперов на плате, ни одной проверки установщика на живой плате. Всё, что подтверждено выше, — это разбор кода и запуск в песочнице на dev-машине. §9 — не «регрессионное покрытие сверх проверенного», а **первое** подтверждение работоспособности, и до него гарантия §1 остаётся утверждением по построению |
| `IFF_UP` против carrier как причина отказа `gateway` | **не разведено сознательно** — ожидание `carrier == 1` подразумевает `IFF_UP`, поэтому фикс корректен при обеих трактовках. Разводить нужно только если пост-фиксный принудительный репро всё ещё падает |
| поведение на плате SA-02m-2 (2 Ethernet) | **пробел**: платы на стенде нет. Путь `eth1` DHCP + `allow-hotplug` покрыт рассуждением и юнит-тестом. Известное следствие: ожидание сработает и для `ifup@eth1`, стоив бюджета на загрузке с отключённым eth1 |
| частота исходного отказа | **неизвестна** и не оценивается: критерий «N чистых загрузок» здесь бессмысленен, доказательство — принудительный репро (§9) |

## 9. Приёмка на железе

Принудительный детерминированный репро вместо «нескольких загрузок»:

> **FR-CABLE:** включить питание с **отключённым** кабелем LAN; воткнуть кабель
> примерно на T+40 с (заведомо после `networking.service`).

FR-CABLE намеренно заставляет ожидание **истечь** (кабель приходит на T+40,
бюджет — 10 с): резолвер на этом прогоне приходит от ступени, а не от ожидания,
и это честный худший случай.

| Прогон | Сборка | Должно показать |
|---|---|---|
| FR-CABLE ×2 | до фикса | отказ **каждый раз**: `ifup@eth0` и `networking` FAILED, `/run/resolvconf/interface/` пуст, `getent hosts` не работает |
| FR-CABLE ×3 | эта ветка | нет упавших юнитов; `/run/resolvconf/interface/eth0.inet` появляется **в пределах 60 с** после включения кабеля; `getent hosts` работает; плата доступна всё время |

Проверка на каждой загрузке:

```sh
systemctl --failed --no-legend | wc -l          # == 0
grep -c '^nameserver' /etc/resolv.conf          # >= 1
ls /run/resolvconf/interface/                   # содержит eth0.inet
getent hosts github.com                         # код 0 (или имя, которое резолвит LAN площадки)
journalctl -b -u ifup@eth0 -u networking --no-pager | grep -c FAILURE   # == 0
journalctl -b -t sa02m-dns-ensure --no-pager    # какая ступень сработала
journalctl -b -t sa02m-wait-carrier --no-pager  # сколько реально ждали
```

Пять обычных холодных загрузок с кабелем — **покрытие регрессий, а не
доказательство**; доказательство — FR-CABLE. Прогоны на втором ядре (RT/SMP)
и на плате SA-02m-2 — названные пробелы, а не подразумеваемые «прошло».
