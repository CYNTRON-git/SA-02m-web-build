# Контракт: датчик присутствия MTDx62-MB (MTD262-MB / MTD062-MB, RS-485)

Единственный дом гарантий платы, относящихся именно к этому датчику: как его
узнаёт поиск прошивальщика, что может окно настройки на вкладке «Устройства
RS-485», как меняются адрес и скорость, как за датчиком следует запись моста
MQTT и что получает Алиса. Механика опроса мостом — общая для всех шаблонных
устройств и описана в `template-device.md`; здесь не повторяется.

## Проверено на железе

Реальный датчик, 2026-09-29 (ветка 1.0.6.69, замеры Оркестратора):

- Адаптер ПК, 9600 8N1, адрес 1: HR0..13 = `600, 60, 10, 30, 7, 7, 60, 1, 9600,
  0, 2, 0, 600, 1`; IR0..7 = `1, 3471, 148, 1, 1, 260, 0, 0`. HR14+ и IR8+ —
  исключение 2.
- Стенд 1.135, COM3 @19200, адрес 20: с человеком IR0..7 = `1, 3682, 141, 1, 1,
  260, 0, 0`; пустая комната — `0, 2992, 0, 1, 1, 260, 0, 0` (дистанция 0, а не
  маркер «нет цели»).
- FC06 в HR7 (адрес) и HR8 (скорость) датчик применяет **сразу**, ответа на
  прежней линии **нет**; после выключения питания новые значения
  **сохраняются**.
- FC06 в регистры настроек (HR3, HR4) отвечает обычно.
- Версия ПО — IR4..5, байты «резерв · старшая · младшая · ревизия»: стенд
  `0x0001, 0x0104` → **1.1.4**; радар IR6..7 → 0.0.0.

Эти дампы — фикстуры тестов (раздел «Проверка»).

## Опознание

Строка опознаётся как датчик, когда HR7 равен опрашиваемому адресу, HR8 — одна
из скоростей датчика, HR9 ∈ 0..2, IR0 ∈ {0, 1} и IR3 ∈ 0..6. Поиск
прошивальщика проверяет это только у строки без серийного номера (регистры
270–271 не ответили), только на RS-485 (не через TCP-шлюз) и только на линии
не быстрее 57600 — три коротких чтения, при совпадении ещё одно (версия ПО).
Опознанная строка получает сигнатуру `MTDx62-MB` и не находится в загрузчике:
прошивку ей не предлагают, двойной щелчок открывает окно.

## Окно настройки и маршруты

Окно — `www/network_config/static/js/flasher/mtd.js`, три вкладки: «Сведения»,
«Настройки», «Сеть». Новых маршрутов нет: снимок —
`POST /api/flasher/device_config/snapshot`, настройка —
`POST …/device_config/holding` (`reg` + сырое слово), смена линии —
`POST …/device_config/network`. Сессия и CSRF — центральные у демона
(`docs/decisions/selective-csrf-policy.md`); шина — под арендой порта
прошивальщика на всё время окна (мост и MPLC4 остановлены).

- Демон — единственный судья. Запись уходит на шину только для записываемого
  канала шаблона в его `min`/`max` (и для HR11 в 0–420) и только после того,
  как датчик заново опознан на шине. HR7–HR10 путь настройки не пишет никогда,
  что бы ни сказал шаблон. Нет шаблона — запись запрещена вся; у канала нет
  диапазона — он только для чтения. Ответ содержит прочитанное обратно
  значение (`read_back`), а не запрошенное.
- HR12 и HR13 окно показывает и не пишет; HR10 — показывает с
  предупреждением, когда передача включена.

## Смена адреса и скорости

- Запрос проверяется до любого обмена: адрес 1..247, скорость из списка
  датчика, **чётность только N** — мост открывает каждую линию RS-485 в 8N1
  (`template-device.md` §8). Датчик на O/E можно перевести на N.
- Скорость меняется, только если **каждая другая** запись моста на этом COM
  уже работает на целевой скорости: мост не обслуживает две скорости на одном
  порту. Это правило держит **только окно**: оно не предлагает запрещённую
  скорость и отказывает до запроса к демону; запись без скорости или порт на
  разных скоростях — скорость не меняется. **Демон это правило не проверяет**
  (он принимает любую скорость из списка датчика): запрос в обход окна может
  увести датчик на скорость, которую мост на этом порту не обслуживает.
- Пока на какой-либо промежуточной линии кто-то отвечает (ответ, исключение,
  битый кадр), не пишется ничего. После каждой записи датчик ищется по всей
  тройке HR7..HR9 — на новой линии, затем на прежней, с одним повтором.
  Ответ называет линию, на которой датчик **действительно** отвечает, — и
  когда смена остановилась на полпути.
- Пока идёт смена и перенос записи моста, «Закрыть» недоступна, а
  перезагрузка страницы спрашивает подтверждение.

## Запись моста следует за датчиком

После ответа демона окно читает `cgi-bin/mqtt_config.cgi`, находит **одну**
запись на этом COM со старым адресом и шаблоном `mtdx62-mb` и переносит её на
линию, которую **сообщил демон**, отправляя конфигурацию обратно с
`restart:false` (`flasher/bridge-relink.js`); мост перечитывает её, когда при
закрытии окна возвращается аренда порта. Нет записи — писать нечего; две —
не меняется ни одна, окно их называет; конфигурацию не удалось прочитать или
сохранить — окно пишет, что датчик уже на новом адресе, а запись MQTT нужно
исправить на вкладке MQTT.

Идентификатор устройства в MQTT не меняется (`mtdx62-mb-COM3-20` после
переезда на адрес 21): на нём история, привязки Алисы и сценарии. Следствие:
подпись «COMn a», выведенная из идентификатора, может показывать старый
адрес.

Если часть регистров датчик применил сразу, а часть — только после
перезапуска питания (`applies_after_restart`), запись моста переносится на
линию, где датчик отвечает **сейчас**; окно называет обе линии — текущую и ту,
на которую датчик перейдёт после перезапуска питания, — и просит после него
исправить запись на вкладке MQTT.

Остаётся вне досягаемости:

1. Браузер закрыт во время смены (до ≈13 с) — запись моста не перенесена,
   карточка «Устройств» показывает датчик офлайн, пока запись не поправят.
2. Программы MPLC4/CODESYS, опрашивающие датчик, — окно после успешной смены
   напоминает их проверить.
3. Запись через карточку «Устройств» (MQTT) проверяет только диапазон формата
   слова, а не `min`/`max` шаблона.
4. Датчик, оставленный пультом производителя на O/E, поиск 8N1 не находит.
5. Регистры, применяемые только после перезапуска питания, запись моста не
   догоняет: после перезапуска датчик уходит на новую линию, а мост опрашивает
   прежнюю, пока запись не исправят на вкладке MQTT (замер 2026-09-29 показал
   немедленное применение HR7/HR8, так что путь теоретический).

## Не проверено на оборудовании

- Применяется ли **изменённое** значение HR0–HR6 и HR11 сразу и сохраняется
  ли после выключения питания (замерена только запись того же значения).
- Как датчик принимает смену чётности (HR9) и проверяет ли чётность кадра;
  если он отвечает на чужой чётности битым кадром, переход на N будет
  отклонён без единой записи (безопасный отказ; так смоделировано в тестах).
- Перенос записи моста на реальной плате: мост после закрытия окна опрашивает
  новый адрес — проверка на стенде.
