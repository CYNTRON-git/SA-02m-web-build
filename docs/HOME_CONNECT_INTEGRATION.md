# Бытовые приборы BSH (Home Connect) на СА-02м

Руководство наладчика: как поставить клиент, завести своё бесплатное приложение
Home Connect, подключить аккаунт владельца по коду с телефона и что делать,
если что-то не работает. Точные правила (какие контролы публикуются, состояния,
лимиты, файлы, API) — в контракте
[contracts/home-connect.md](contracts/home-connect.md); установка на плату —
[deployment.md](deployment.md), раздел «Необязательный модуль Home Connect».

## Что это и чем не является

- Служба `sa02m-homeconnect` на плате получает из облака BSH Home Connect
  состояние приборов Bosch, Siemens, Neff, Gaggenau (посудомоечные и стиральные
  машины, сушилки, духовки, кофемашины, вытяжки, варочные панели, холодильники),
  привязанных к аккаунту владельца, и публикует их на локальном брокере MQTT
  как обычные устройства `hc-…`: работает ли программа, закончилась ли, сколько
  осталось, открыта ли дверь.
- **Только чтение.** Плата приборами не управляет: не запускает и не
  останавливает программы, не включает и не выключает. Это решение первого
  выпуска (Оператор, Q-E); на карточке это написано прямо.
- **Нужен интернет на плате** — данные идут из облака BSH, а не из локальной
  сети. Облако ЦИНТРОН в этом не участвует.
- **Необязательная установка.** Модуль не входит в заводской образ, его ставят
  отдельно (ниже).

```text
прибор ──Wi-Fi──► облако BSH Home Connect ──HTTPS──► СА-02м sa02m-homeconnect ──MQTT──► /devices/hc-…
                        ▲                                  (только чтение)
       телефон владельца: вход SingleKey ID по коду с карточки
```

## Что пока не проверено (важно для объектов в России)

Код клиента ничего из этого не зашивает, но на настоящем облаке BSH из
контейнера разработки это проверить было нельзя
(`docs/decisions/homekit-home-connect.md`, пункты G6 и G7; контракт §14):

- работает ли вход для аккаунтов SingleKey ID, созданных в России (BSH
  отключала своё приложение в России в 2022 году). С российского IP-адреса
  облако BSH на стенде **не ответило** (2026-09-28): соединение открывается,
  ответа нет;
- сколько живут код входа (5 или 10 минут) и ключ доступа;
- на каких адресах BSH показывает страницу входа (карточка открывает только
  `home-connect.com`, `home-connect.cn`, `singlekey-id.com`);
- приходит ли состояние «питание» (`power_on`) без права «Настройки» — если нет,
  этот контрол у прибора просто не появится.

Если на объекте облако BSH недоступно, карточка покажет «нет связи с облаком» и
«BSH недоступно из этой сети», а плата продолжит работать как обычно. Каждая
такая попытка расходует одно обращение из суточного лимита.

## Установка

```bash
sudo ./install.sh --refresh --with-homeconnect
# или только модуль, если install.sh уже отработал:
sudo bash scripts/06d-homeconnect.sh
```

Никаких загрузок из PyPI: модуль ставится и без интернета (интернет нужен
позже — самому клиенту). После установки служба выключена, на карточке
«Управление → Home Connect» — «выключен». Обычный `install.sh` обновляет уже
установленный модуль и без флага.

Плата, получившая новую версию только через «Обновление веб» (OTA), код клиента
уже несёт, но модуль на ней не установлен: карточка покажет «не установлен» —
нужен один прогон установщика.

## Шаг 1. Своё приложение Home Connect (Client ID)

Каждый интегратор регистрирует **своё** бесплатное приложение в кабинете
разработчика BSH и вставляет его Client ID на карточку (решение Оператора Q-B;
место под будущий общий ID ЦИНТРОН в настройках оставлено). Секрет приложения
не нужен и на плату не вводится.

По публичной документации BSH (из России не проверено):

1. Откройте кабинет разработчика `https://developer.home-connect.com/` и
   зарегистрируйтесь.
2. В разделе приложений зарегистрируйте новое приложение: любое имя, тип входа
   (OAuth flow) — **Device Flow**, адрес возврата не нужен. Если кабинет
   спрашивает аккаунт для тестирования — укажите e-mail аккаунта Home Connect
   владельца приборов: неопубликованное приложение может работать только с
   ним.
3. Скопируйте **Client ID** приложения (строка из латиницы, цифр, `_` и `-`,
   от 8 до 128 символов).

Для отладки без настоящего прибора в кабинете есть симулятор; клиент умеет
ходить к нему (`host = simulator` в конфиге), но карточка этот переключатель
не показывает — это настройка для стенда.

## Шаг 2. Подключить аккаунт владельца

На карточке «Управление → Home Connect»:

1. Вставьте Client ID в поле «Client ID приложения» → «Сохранить» (от 8 до 128
   символов: латиница, цифры, `_` и `-`; иначе карточка ответит «Недопустимый
   Client ID»).
2. «Включить» — служба запускается, состояние «не подключён».
3. «Подключить» — через несколько секунд карточка показывает **код входа**,
   ссылку «Войти на сайте Home Connect ↗» и QR-код; состояние «ждёт входа».
4. На телефоне владельца: отсканируйте QR (или откройте ссылку), войдите в свой
   аккаунт SingleKey ID и подтвердите код. Отдельное приложение на телефон
   ставить не нужно.
5. Карточка переходит в «подключение…», затем «подключён», появляется список
   приборов («Приборы: N») и «Поток событий».

Не успели за время жизни кода — «код истёк», нажмите «Подключить» ещё раз.
Владелец отказал во входе или Client ID не принят облаком — «не подключён» с
пояснением.

Код входа виден только на карточке за паролем панели и только пока идёт вход.
Ключи доступа хранит сама служба в файле, который не читает ни веб-панель, ни
кто-либо ещё, кроме неё; в журнал, в резервную копию и в образ платы они не
попадают.

## Что появляется на брокере

Каждый прибор — устройство `/devices/hc-<идентификатор прибора>` с контролами
вроде `running`, `finished`, `door_open`, `operation_state`, `active_program`,
`remaining_s`, `progress_pct`, `last_event` (полная таблица и правила значений —
контракт §4; публикуется только то, что облако реально присылает о конкретном
приборе). Прибор, о котором облако сообщило «отключён», или все приборы, пока
связь с облаком потеряна дольше 2 минут, помечаются `meta/error = "r"` —
последнее значение видно, но отмечено как недостоверное.

```bash
mosquitto_sub -h 127.0.0.1 -v -t '/devices/hc-+/controls/#'
```

Их читает всё, что читает брокер (Node-RED, SCADA, MPLC4 через MQTT), и их
можно привязать в «Умном доме» (ниже).

## Привязать прибор в «Умном доме»

«Управление → Умный дом → Комнаты и устройства → Выбрать канал»: приборы
Home Connect — отдельные карточки после модулей COM-портов (подпись
«Home Connect · марка»). Предлагаются только контролы «да/нет»:
«Дверь открыта», «Работает», «Программа завершена», «Включён», «Разрешён
удалённый старт», «Удалённое управление», «Местное управление», «На связи»
(в «Диагностике»). Текстовые контролы (`operation_state`, `active_program`,
`last_event`) не предлагаются — ни у Алисы, ни у HomeKit нет типа, который
честно их показал бы. Числа `remaining_s` и `progress_pct` пока тоже не
предлагаются: в пикере нет числового вида привязки; они по-прежнему доступны
по MQTT (выше).

- «Дверь открыта» привязывайте видом **«Открытие»** — в Алисе это датчик
  открытия, в «Доме» Apple — контактный датчик.
- Прочие «да/нет» — видом **«Состояние (только чтение)»**. Вид
  «Переключатель» при выборе канала прибора сам меняется на этот: прибором
  управлять нельзя, и плата хранит такую привязку только для чтения (Алиса
  ответит «действие недоступно», команда на прибор не уходит).
- Прибор без связи с облаком всё равно предлагается: привязать можно, а
  «Не отвечает» покажет сам «Умный дом».

## Сценарии с приборами

Сценарий на плате (`sa02m-rules`) создаётся в облачном редакторе сценариев
ЦИНТРОН, как любой другой; прибор в нём — устройство `hc-…` с контролом по
имени. Ниже два готовых рецепта (строки хранилища сценариев,
`docs/contracts/cloud-scenarios.md` §Store): замените
`hc-bosch-sms6zci49e-68a40e000001` на идентификатор своего прибора (виден в
`mosquitto_sub` и в выборе канала), а `SA-02m` — на идентификатор платы.
Уведомление (`notify`) попадает в очередь уведомлений облака.

Срабатывание — **по фронту** (`rises_above 0.5`): значение, которое сценарий
увидел первым после запуска службы, — отправная точка, а не событие; повтор
того же значения (клиент повторяет его раз в минуту) сценарий не запускает.
Поэтому уведомление приходит ровно один раз за окончание программы, а не при
каждом перезапуске платы.

**Важно:** если контрол прибора привязан в «Умном доме» видом «Переключатель»
или «Состояние», служба сценариев знает его под устройством «Умного дома»
(`<id устройства>` / `on_off`), а не под `hc-…`. Для такого контрола пишите
триггер на устройство «Умного дома»; триггер на `hc-…/<контрол>` срабатывать
перестанет.

Рецепт 1 — «Программа завершена» → уведомление:

<!-- recipe: hc_finished_notify -->
```json
{
  "name": "Посудомойка закончила",
  "type": "block",
  "enabled": true,
  "trigger": [
    {"kind": "state", "device": "hc-bosch-sms6zci49e-68a40e000001", "cap": "finished",
     "op": "rises_above", "value": 0.5}
  ],
  "action": [
    {"kind": "notify", "text": "Программа завершена"}
  ]
}
```

Рецепт 2 — дверь открыли во время программы → уведомление и светодиод
«Авария» платы на 5 минут: `end` в режиме `restore` через 300 с возвращает
светодиоду прежнее значение (режим `off` гасит только выходы `on_off`, а
`alarm_led` — отдельный контрол; если светодиод уже горел по другой причине,
`restore` его не погасит).

<!-- recipe: hc_door_open_running -->
```json
{
  "name": "Дверь открыта во время работы",
  "type": "block",
  "enabled": true,
  "trigger": [
    {"kind": "state", "device": "hc-bosch-sms6zci49e-68a40e000001", "cap": "door_open",
     "op": "rises_above", "value": 0.5}
  ],
  "condition": {"all": [
    {"kind": "state", "device": "hc-bosch-sms6zci49e-68a40e000001", "cap": "running",
     "op": "==", "value": 1}
  ]},
  "action": [
    {"kind": "notify", "text": "Дверь открыта во время работы"},
    {"kind": "set", "device": "SA-02m", "cap": "alarm_led", "value": 1}
  ],
  "end": {"after_s": 300, "mode": "restore"}
}
```

Не проверено на настоящем приборе: в каком порядке облако присылает «дверь»
и «состояние программы». Если прибор сначала сообщает «программа
остановлена», а потом «дверь открыта», рецепт 2 не сработает.

Оба рецепта проверяются тестом на плате
(`opt/sa02m-rules/tests/test_homeconnect_recipes.py`): тест берёт JSON прямо
из этого файла по меткам `recipe:`.

## Лимит запросов

BSH разрешает 1000 обращений в сутки на пару «приложение + аккаунт», включая
неудачные. Клиент бережёт лимит: с 800 обращений он перестаёт перечитывать
приборы и живёт только на потоке событий, при ответе «слишком часто» ждёт
столько, сколько сказало облако. Карточка показывает «Запросов сегодня: N из
1000»; «лимит API до ЧЧ:ММ» — ждать до указанного времени, ничего делать не
нужно. Отключение и повторное подключение аккаунта счёт не обнуляют.

## Отключить, выключить, сбросить

- **«Отключить аккаунт»** — стирает вход (ключи доступа) и убирает приборы
  этого аккаунта с брокера; Client ID и счёт запросов остаются. Чтобы вернуться
  — «Подключить» заново.
- **«Выключить»** (или «Стоп» в списке служб) — служба останавливается и
  убирает свои устройства с брокера; вход сохраняется.
- **Сброс к заводским настройкам** стирает вход в Home Connect (решение
  Оператора Q-F: при перепродаже плата не должна читать приборы прежнего
  владельца) и выключает модуль; сам модуль остаётся установленным.
- **Резервная копия** настроек несёт только конфиг (включён ли модуль и
  Client ID), но никогда не ключи доступа: после восстановления на другую
  плату нужно «Подключить» заново.
- **Снятие образа** для клонирования стирает вход автоматически
  (`docs/contracts/image-identity-reset.md` §8); на мастере образа модуль
  лучше не ставить вовсе (`deployment.md`, шаг 2b).

## Если что-то не работает

| Карточка показывает | Что значит и что делать |
|---|---|
| «не установлен» | модуль не ставился — `sudo bash scripts/06d-homeconnect.sh` |
| «нет компонентов» | нет `python3-paho-mqtt` — повторить установку (установщик ставит его сам) |
| «нет компонентов», «Нет доступа к настройкам» | конфиг клиента есть, но служба не может его прочитать (сбиты владелец, группа или режим — например, после восстановления): «Выключить», затем «Включить» — при запуске права восстанавливаются и проверяются от имени клиента, причина — в `journalctl -u sa02m-homeconnect`; не помогло — повторить `sudo bash scripts/06d-homeconnect.sh`. Проверка вручную: `sudo /usr/local/sbin/sa02m-daemon-access.sh check homeconnect` |
| «нет Client ID» | вставить Client ID своего приложения и «Сохранить» |
| «не подключён» | нажать «Подключить»; если сразу возвращается — проверить Client ID и тип входа приложения (Device Flow) в кабинете BSH |
| «код истёк» | «Подключить» ещё раз и войти быстрее |
| «нет связи с облаком», «BSH недоступно из этой сети» | нет интернета на плате или облако BSH не отвечает из этой сети — так было с российского IP на стенде (см. «Что пока не проверено»). Для повторного входа — «Подключить» ещё раз |
| «доступ отозван» | владелец отозвал доступ или сменил пароль — «Подключить» заново |
| «лимит API до ЧЧ:ММ» | суточный лимит BSH; ждать указанного времени |
| «Опрос на паузе до конца суток (UTC)» | израсходовано 800 обращений из 1000: клиент больше не перечитывает приборы, но события продолжают приходить (см. «Лимит запросов»); ничего делать не нужно |
| «Нет потока событий — данные могут устареть» | поток событий облака прервался; клиент переподключается сам, значения приборов пока помечены недостоверными |
| «ошибка», «Журнал: sa02m-homeconnect» / «Нет ответа от платы» | служба упала или не отвечает — «Выключить», затем «Включить»; журнал: `journalctl -u sa02m-homeconnect -b` |
| прибор с `meta/error = "r"` | облако сообщило, что прибор не в сети (Wi-Fi прибора), или связь с облаком прервалась |

Файлы, права и что именно проверяется автоматически — контракт §11 и §15.
